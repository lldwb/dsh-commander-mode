# 优化点与风险自查清单

供 agent 按需加载：在执行 `code-optimize` 的「规划任务」与「验证」两步时读。逐项过一遍，命中即处理；不适用项标注原因，不静默跳过。

## 0. 动手前先过阶梯（先决定要不要写）

在「1. 优化点」之前逐级自问，**命中即停在该级**，不必走完：

| 级 | 自问 | 命中后的动作 |
|---|---|---|
| ① 是否真需要 | 该诉求是否成立？不做能否达成目标？ | 不做，写明理由回报，不动代码 |
| ② 本仓是否已有 | 是否已有同类工具方法 / 模式可直接复用？ | 复用既有实现，不另起一套 |
| ③ 标准库 / 框架是否已能做 | 语言标准库、框架内置能力是否覆盖？ | 用内置能力，不手写等价实现 |
| ④ 既有依赖 / 平台特性是否覆盖 | 已装依赖、平台原生能力是否已解决？ | 用现有能力，不新增依赖 |
| ⑤ 能否用更小改动达成 | 能否靠删除、合并或复用达成同一效果？ | 优先删除与合并，**删除优于新增** |
| ⑥ 动手 | 以上均不成立 | 写**最小可用**改动 |

- 阶梯在**理解问题之后**跑，不替代理解：读清需求与相关代码、走通真实链路，再逐级自问。
- 任何一级都不接受"先留个抽象 / 配置项 / 扩展点，以后可能用得上"——未被要求的能力不加。
- 停在某一级的理由要能一句话说清，写进优化说明（对应「改动清单 → 为什么这样改」）。

## 1. 优化点（改什么）

### 1.1 可读性

| 检查项 | 判定 | 处置 |
|---|---|---|
| 命名 | 变量 / 方法 / 常量名与语义不符、缩写含混、同一概念多种叫法 | 改名并全量替换引用（含注释、日志、配置键） |
| 局部结构 | 方法过长、嵌套过深、条件分支可用早返回消解 | 拆小方法 / 卫语句提前返回，签名与返回不变 |
| 重复代码 | 同一逻辑出现 2 次以上、仅少量常量不同 | 抽公共方法 / 常量，差异部分参数化 |
| 死代码 | 不可达分支、无引用的私有方法 / 常量、被遮蔽的旧实现 | 全仓确认无引用后再删；有引用或不确定时只报告 |

### 1.2 性能

| 检查项 | 说明 |
|---|---|
| 循环内重复调用 | 循环条件与循环体内重复计算、重复获取的对象，上提到循环外（不改变可观测副作用） |
| 不必要的查询 / 远程调用 | 循环内逐条取数、重复取同一份数据 → 批量或缓存（缓存须写明失效方式） |
| 不必要的装箱与转换 | 基础类型与包装类型反复互转、重复的格式化 / 解析 |
| 集合使用 | 误用顺序集合做包含判断、未预分配容量、遍历中修改集合 |
| 字符串拼接 | 循环内拼接大字符串改用可变缓冲（或项目既有等价工具） |

### 1.3 单点定义（SSOT）

- 常量 / 错误码 / 配置 / 判定规则是否只在**一个权威位置**定义？
- 本次改动是否引入新的重复定义？能否改为引用既有定义？
- 仅当某处承担独立职责（供下游单独消费的产物、面向用户的索引）才允许特意重复；职责相同的复制迟早漂移。

## 2. 风险自查（动手前先确认）

### 2.1 先核可得性

- 依赖的数据、字段、接口（数据库列、三方接口响应、日志落点与截断限制）**先确认真实存在、格式与限制**，再写代码或规则，不凭假设。
- 在产出中写明「从哪取、为什么易漏」。

### 2.2 保持对外行为不变（必查）

| 维度 | 自查问题 |
|---|---|
| 接口返回 | 返回结构、字段、类型、空值处理、异常行为是否与改前一致？ |
| 页面交互 | 展示顺序、默认值、校验提示、触发时机是否一致？ |
| 既有流程 | 分支条件、执行顺序、幂等性、事务边界是否一致？ |
| 公共能力 | 改的是被多处调用的方法 / 常量时，是否核对了全部调用方？ |
| 副作用 | 日志、埋点、缓存、计数等可观测行为是否被无意改变？ |

判定：任一项无法确认时，不得认定"行为不变"——先补证据（读调用方 / 跑测试 / 人工验证），或降级为"只报告不改"。

### 2.3 范围自查

- 改动是否严格落在已规划的优化点内？有无顺手改动无关文件？
- 是否夹带了行为变更（新功能、缺陷修复）？有则拆出：缺陷 → `bug-fix`，行为新增 → `feature-dev`。
- 是否用**更小的改动**达成了同一效果？能靠删除、合并或复用既有实现达成时，不新增抽象、文件与依赖（见第 0 节）。

## 3. 发现真实缺陷时

- **不夹带修复**：本次优化范围外的真实缺陷（空指针、边界错误、逻辑错误等）不顺手改——修复会改变对外行为，越出本技能边界。
- **单列报告**：在汇报中给出「位置（`文件:行`）+ 现象 + 影响面 + 建议」，交用户决策；需要修复时转 `bug-fix`。

## 4. 有意简化必须标注

- 主动保留的简化（不做边界处理、只覆盖当前已知输入、用直白但更慢的写法等）要在**代码注释或产出说明**里写明三点：简化了什么、上限在哪（什么条件下不再成立）、后续如何升级。
- 不写明的简化等于隐性技术债：后续读者无法判断这是有意取舍还是疏漏。
- 简化的前提是**边界正确**：两种写法代价相当时取更不容易出错的那种。简化省的是代码量，不是正确性——输入校验、错误处理、安全与数据完整性不打折。
