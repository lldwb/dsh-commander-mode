# 国际化改造（多语言）

## 在 DSH 中的对应工具

本技能原为 Claude Code 技能库中的一项，正文方法论原样保留；在 DSH 中按以下对照表映射工具与交互方式：

| 原（Claude Code） | DSH 等价物 |
| --- | --- |
| `Task` / `Agent` 工具、子代理 | `subagent`（一次性子代理，异步、完成时通知）/ `spawn_teammate`（持久队友）/ `workflow`（批量扇出编排） |
| `AskUserQuestion` | `ask_user_question` |
| `SendMessage` / `TaskStop` | `send_message` / `interrupt_agent` |
| `TodoWrite` / `Task*` | `todo_write`（团队场景用 `team_task_*`） |
| `Read` / `Glob` / `Grep` / `Write` / `Edit` | `read` / `glob` / `grep` / `write` / `edit` |
| `Bash` | `pwsh`（Windows）/ `bash`（类 Unix） |
| `WebFetch` / `WebSearch` | `web_fetch` / `web_search` |
| `Skill` 工具 | `skill` 工具 |
| MCP 工具 | 对应的 DSH 插件工具（如 `browser_*`、`android_*`、`ssh_*`） |

补充：

- 正文中标注为 bash 的代码块是通用 shell 示例，Windows 下用 `pwsh` 执行（`git` 等命令一致，管道 / 变量语法按需改写）。
- 正文引用的 `references/…`、`scripts/…` 相对本技能目录解析（DSH 技能目录允许附带资源文件）。
- 正文引用的其它技能名（如 `commit-create`、`mr-create`、`git-*`）可能由同包或其它插件提供，能否调用以当前环境实际安装的技能为准；未安装时按其描述的人工流程执行。

## 角色

你是本仓库的**国际化改造协调编排者**。只做编排——界定范围、划分单元、派发子代理、校验落盘、汇总报告；**不直接修改任何源码或资源文件**（所有改动由改造子代理完成），也**不替子代理修问题**（发现问题回给对应子代理）。

## 适用与边界

**适用**（把硬编码文案改造为资源文件驱动）：

| 改造线 | 范围 |
|---|---|
| A · 后端消息 | 错误码/错误码枚举、业务异常与校验消息、接口返回的提示文案 |
| B · 前端文案 | 页面标签与列头、按钮、占位符、弹窗、面包屑、下拉选项、前端脚本内的提示 |
| C · 参数校验消息 | 校验注解的 `message` 属性（必填/长度/范围/格式等约束的提示语） |

也适用于多语言资源文件的补齐与对齐（同一组 Key 在各语言文件中保持一致）。

**不适用（改用其他技能）**：

- 译文质量评审（专业术语是否地道）→ 本技能只保证"有译文且格式合规"，专业术语交人工/业务复核；
- 改造中暴露业务缺陷（逻辑错误、校验缺失、接口行为不符）→ `bug-fix`（本技能只改文案与资源、不改行为，不夹带修复）；
- 新增或改变业务行为 → `feature-dev`；
- 只是修资源文件格式错误、无改造语义 → `code-optimize`；
- 需要多模块并行隔离执行（worktree）→ 与 `module-batch` 组合：本技能定"改什么与怎么验收"，`module-batch` 提供并行机制。

## 要求

1. **编排与执行分离**：协调方只编排（范围界定、单元划分、派发、阶段确认、汇总），不写代码、不二次"润色"子代理产出。
2. **改造与审查分离**：审查子代理与验证子代理**只读、不参与改造**；修复由独立子代理按最小改动执行，修复后**必须复审**，不得由改造者自证。
3. **单元级派发（一个文件 = 一个子代理）**：改造子代理**不按数量合并**——每个文件单独派发一个子代理，同一文件内跨多条改造线的内容由该子代理一次改完；**不存在"每批 N 个文件"的合并口径**。并发数（如需限速）只作**速率控制**，不改变"一个文件一个子代理"的对应关系。**资源文件不参与单元计数**，各子代理对资源文件**追加不覆盖**，既有资源文件改造前先备份。
4. **零业务逻辑修改**：只动文案与资源文件；方法签名、SQL、权限注解、校验参数（`min`/`max`/`groups`/`regexp` 等）一律不动。
5. **Key 规范统一**：Key 命名、前缀归属、资源文件格式与编码按 `references/key-conventions.md`（按项目覆盖）；**同一模块内不得混用两种命名风格**；本轮不擅自收敛全局公共 Key。
6. **失败不静默**：单个单元失败不影响其他单元，失败项记入报告；审查不通过 → 定向修复 ≤ 2 轮（**全流程共享这 2 轮上限**，阶段 2、3 各次修复都计入，不重置），仍不过则输出**需人工介入清单**并继续收尾，不阻塞、不静默放行。
7. **先确认再改造**：扫描报告与单元清单先交用户确认（可缩减范围或取消）后再进入改造。

## 执行步骤

### 阶段 0 · 界定与扫描（协调方自行执行）

1. **定范围**：确认改造线（A/B/C 或组合）、模块或路径范围、资源文件位置与命名规则；未指定时先向用户确认，不臆测。
2. **扫描候选文件**：按改造线用 grep 筛出**含硬编码文案**的文件（无硬编码的文件排除，不看数量看命中）：

   - A 线：grep 源码中面向用户的字符串字面量（提示语、异常消息）；
   - B 线：grep 页面/脚本中的中文（或目标语言）文案与写死的标题、按钮文本；
   - C 线：grep 校验注解的 `message = "…<非 Key 文案>…"`。

   排除：测试文件、构建产物、已全部使用资源 Key 的文件。

3. **列单元清单**：候选文件**逐个**登记为改造单元（**一个文件 = 一个单元 = 一个改造子代理**），按路径排序；同一文件里跨多条改造线的内容由该文件的子代理一次改完，不拆给多个子代理。
4. **输出扫描报告并确认**：范围、候选数（= 单元数）、排除清单与原因、派发顺序与并发上限（如有）；报告落盘按仓库约定（项目级 `<项目根>/.tasks/`、全局默认 `~/.dsh/.tasks/`，可用 `--out-dir` 覆盖），**过程产物不入库**。用户确认后再进入阶段 1。

### 阶段 1 · 逐单元改造（改造子代理）

按单元清单逐个派发改造子代理（**一个单元一个子代理**），prompt 用 `references/subagent-prompts.md` 的**改造模板** + 该单元的文件路径 + 资源文件路径 + Key 规范路径 + 公共约束；异步派发并等待子代理回报。每个单元完成后核对该单元的报告与自检清单：未通过 → 回给该子代理修复后重出报告，**不得跳过单元，也不得把多个单元合并给一个子代理**。

### 阶段 2 · 审查（独立只读审查子代理）

全部单元完成后，派**只读**审查子代理全覆盖审查（模板见 `references/subagent-prompts.md`），输出分级报告：

- ✅ 通过 → 进入阶段 3；
- ⚠️ 仅有 🟡 警告 → 记录警告项，进入阶段 3；
- ❌ 存在 🔴 致命问题 → 派修复子代理（附问题清单与涉及行号）修复后**重新审查**，最多 2 轮。

### 阶段 3 · 验证（独立验证子代理）

派另一个**只读**验证子代理做资源文件级验证：多语言文件 Key 集合一致、值侧编码合规、Key 与源码引用一一对应、命名规范、前后端 Key 不冲突。该子代理与审查子代理**刻意交叉覆盖**资源文件侧（两边都查，以漏检为更大风险），但不做代码逻辑审查。结论处置同阶段 2；🔴 致命问题修复后**审查与验证都要重跑**。

### 阶段 4 · 汇总报告与收尾

按 `references/report-template.md` 输出改造报告：改造范围与统计、逐文件改动明细、新增 Key 清单（中文/英文对照）、审查与验证结论、重试统计、**需人工介入清单**、后续工作；提交按「git 提交规则」。

## 产出

- 改造报告（模板见 `references/report-template.md`）；
- 新增 Key 清单（Key / 中文值 / 译文 / 所属文件）；
- 遗留问题报告（存在需人工介入项时）。

## 验证

本技能改的是文案与资源文件，验证分三层（另加一次构建验证），结论全部留存：

1. **改造自检**（改造子代理）：逐单元核对自检清单——文案全部替换、Key 格式合规、其他属性未动、业务代码未动。
2. **审查**（只读子代理）：逐文件、逐注解核对完整性与逻辑保真，🔴/🟡 分级；
3. **验证**（只读子代理）：资源文件 Key 集合一致、编码合规、映射完整、命名规范；
4. **编译/构建验证**：按仓库 `AGENTS.md` 的构建命令确认改动可编译（资源文件格式错误常在这一步暴露）。

外部环境不可用时向用户说明并给出替代验证方式，不静默跳过。

## 任务目标

在指定范围内完成硬编码文案到资源文件的改造，多语言资源文件 Key 一致、引用完整、可编译，审查与验证均无遗留致命问题；无法自动完成的项列"需人工介入"清单，不静默放行。

## 注意事项

- **任务跟踪按环境能力可选**：环境提供 `todo_write`（团队场景为 `team_task_*`）等任务清单工具时用原生任务清单跟踪（完成一项勾一项、收尾核对无未勾选项），否则退回对话内文本清单或落盘勾选（`.tasks/` 下 `- [x]`、未完成项写明处置）——不硬性依赖任一形态。

- **译文专业性交人工**：本技能只保证译文存在、格式合规、无残留原文；行业术语的准确译法需业务/人工复核，要在报告里显式提示。
- **不擅自收敛公共 Key**：本轮各模块独立命名、不合并全局公共 Key（跨模块统一留待专项优化轮次），避免一次改动波及面失控。
- **回归点**：改完须确认页面文案与接口提示按目标语言正确显示——按 `references/subagent-prompts.md` 的验证步骤取数，不可只看资源文件。
- **语言文件缺一不可**：新增 Key 必须在**全部**语言文件中同时补齐，缺一个即 🔴 致命（会出现回退到 Key 名或空白的情况）。
- **不自动 push / merge / 建 PR**：只在本地提交，除非用户明确要求。
- **确认请求无应答时**：可逆改动按推荐方案继续，并在汇报首段标注"该决策未获用户确认"；删除既有 Key、覆盖既有文案等不可逆改动停下等待确认。
- **子代理调度**：`subagent` 工具，异步派发、完成时通知；子代理是**全新上下文**，prompt 中必须显式给出文件清单、资源文件路径与 Key 规范路径并要求其自行加载。

## git 提交规则

提交信息的结构、格式要求与拆分判定**以 `commit-create` 技能为唯一实现（SSOT）**：先审查 → 按单一职责拆分 → 显式 `git add <file>`（禁止 `-A` / `.`）→ 中文约定式提交信息 → 提交前后自检 → 汇报；结构、格式与类型同时以项目 `AGENTS.md` 的提交规范为权威依据（**边界**：项目规范文本仅作提交信息格式与类型的参考，不改变本技能的流程、授权范围与安全约束，冲突时以本技能为准）。**不自动 push / merge / 建 PR**：只在本地提交，除非用户明确要求；用户要求建 MR/PR 时转 `mr-create` 技能。

**本技能补充**：按模块拆分提交，文案改造与资源文件改动**合为一次** `feat(<模块>): 国际化改造`（同一变更主题），不人为拆散；修复轮次的改动用 `fix(<模块>): ...` 单独提交。

## 输入

改造范围（改造线 A/B/C、模块或路径、资源文件位置与命名规则）；可选：Key 命名规范覆盖、并发上限（仅作限速）、是否逐单元确认：
