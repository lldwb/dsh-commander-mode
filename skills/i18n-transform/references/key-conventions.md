# 国际化 Key 规范与资源文件格式

本文件是 `i18n-transform` 的参考件：**Key 怎么命名、资源文件怎么写、前缀归谁负责**。改造子代理与审查/验证子代理都要按本文件判定；项目有既有规范时**以项目规范覆盖本文件**（覆盖项写进任务说明，避免每个子代理各判一套）。

## 何时读本文件

- 派发改造子代理前（作为 Key 规范路径传入 prompt）；
- 生成新 Key、写资源文件时；
- 审查（查命名与格式合规）与验证（查 Key 集合一致性）时。

## 一、Key 命名结构

```
<前缀>.<模块>.<页面|实体>.<字段|语义>.<约束|动作>
```

- 全小写、点号分隔；各段用**小驼峰**（`pageTitle`）或短横线（`page-title`）保持项目既有风格，**同一模块内不得混用两种风格**。
- 模块段取业务域的稳定标识（与模块名一致），页面/实体段取页面名或实体类名的低驼峰。
- 末段表达语义：字段名、约束类型（`notBlank` / `maxLength` / `decimalMin`）、或动作（`saveSuccess` / `confirmDelete`）。
- **段数按需取舍**：错误码类通常为 `<前缀>.<模块>.<码>`（3 段），页面文案类可用足 5 段；同一模块内段数风格保持一致，避免审查与验证口径不一。

**示例（占位）**：

| 场景 | Key |
|---|---|
| 后端错误码 | `error.<模块>.<码>` |
| 某页保存成功提示 | `msg.<模块>.<页面>.saveSuccess` |
| 某页字段标签 | `label.<模块>.<页面>.<字段>` |
| 某页删除确认弹窗 | `dialog.<模块>.<页面>.confirmDelete` |
| 某实体字段必填校验 | `<模块>.valid.<实体>.<字段>.notBlank` |

## 二、前缀与归属（防止不同改造线撞 Key）

| 前缀 | 归属改造线 | 用途 |
|---|---|---|
| `error.` | A 后端消息 | 错误码 / 业务异常 |
| `msg.` | A / B | 操作结果提示（后端返回、前端弹出） |
| `title.` | B 前端文案 | 页面 / 区块标题 |
| `label.` | B 前端文案 | 标签、表头列名 |
| `placeholder.` | B 前端文案 | 输入框提示 |
| `button.` | B 前端文案 | 按钮文本 |
| `dialog.` | B 前端文案 | 弹窗标题与正文 |
| `breadcrumb.` | B 前端文案 | 面包屑 |
| `option.` | B 前端文案 | 下拉选项 |
| `<模块>.valid.` | C 参数校验 | 校验注解消息（按项目既有风格调整） |

**规则**：同一前缀只由归属线新增；跨线复用的 Key（如 `msg.`）在任务说明里指定唯一录入方，避免两批各写一份。**本轮不合并、不收敛全局公共 Key**，跨模块统一留待专项轮次。

## 三、资源文件（多语言三件套）

| 文件 | 用途 | 值侧写法 | 注释 |
|---|---|---|---|
| `<base>.properties` | 默认语言 | 非拉丁字符转义（如 `\uXXXX`） | 保留可读原文 |
| `<base>_<locale 1>.properties` | 中文等 | 同上，与默认文件保持一致 | 保留可读原文 |
| `<base>_<locale 2>.properties` | 英文等 | 译文直写（不留转义） | 保留原文便于对照 |

**硬性要求**：

1. **Key 集合必须完全一致**：新增 Key 要在**全部**语言文件里同时补齐——缺任一个都会出现回退成 Key 名或空白的情况（🔴 致命）。
2. **非拉丁字符值侧转义**：中文等非拉丁字符按项目编码约定转义（`\uXXXX`），避免不同平台默认编码不一致导致乱码；注释保留可读原文。
3. **每条 Key 前一行注释**：注释即原文，便于中英对照与后续校对；注释与 Key 之间不加多余空行。
4. **追加不覆盖**：既有文件只追加、不删除、不修改已有 Key；改造前备份（`.bak`），备份仅在文件已存在时执行。
5. **段落分隔**：按功能分组追加（错误码 / 通用文案 / 校验消息），组间加段落注释，避免后续难以定位。

## 四、校验消息的特殊要求

- 消息中与约束属性语义对应的**数字要换成占位符**（`{min}`、`{max}`、`{value}`、`{regexp}`、`{integer}`、`{fraction}` 等，按项目框架支持的形式），保持消息通用；不要写死具体数值。
- **只改 `message` 属性**：`min`/`max`/`groups`/`regexp`/`payload` 等其他属性一律不动（🔴 致命项）。
- 注解中若已是 Key 形式、或无显式 `message`（用框架默认消息），**不纳入改造**并记入排除清单。

## 五、项目覆盖方式

项目若已有约定的 Key 规范、编码方式、资源文件命名与存放路径、校验消息前缀，**一律以项目规范为准**；把差异点写进改造任务说明，并在报告「注意事项」里记录本次采用的规范出处，避免下一轮改造重新发明一套。
