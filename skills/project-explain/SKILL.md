# 项目讲解

## 在 DSH 中的对应工具

本技能原为 Claude Code 技能库中的一项，正文方法论原样保留；在 DSH 中按以下对照表映射工具与交互方式：

| 原（Claude Code） | DSH 等价物 |
| --- | --- |
| `Task` / `Agent` 工具、子代理 | `subagent`（一次性子代理，异步、完成时通知）/ `spawn_teammate`（持久队友）/ `workflow`（批量扇出编排） |
| `AskUserQuestion` | `ask_user_question` |
| `SendMessage` / `TaskStop` | `send_message` / `interrupt_agent` |
| `TodoWrite` / `Task*` | `todo_write`（团队场景用 `team_task_*`） |
| `Read` / `Glob` / `Grep` / `Write` / `Edit` | `read` / `glob` / `grep` / `write` / `edit` |
| `Bash` | `pwsh`（Windows）/ `bash`（类 Unix） |
| `WebFetch` / `WebSearch` | `web_fetch` / `web_search` |
| `Skill` 工具 | `skill` 工具 |
| MCP 工具 | 对应的 DSH 插件工具（如 `browser_*`、`android_*`、`ssh_*`） |

补充：

- 正文中标注为 bash 的代码块是通用 shell 示例，Windows 下用 `pwsh` 执行（`git` 等命令一致，管道 / 变量语法按需改写）。
- 正文引用的 `references/…`、`scripts/…` 相对本技能目录解析（DSH 技能目录允许附带资源文件）。
- 正文引用的其它技能名（如 `commit-create`、`mr-create`、`git-*`）可能由同包或其它插件提供，能否调用以当前环境实际安装的技能为准；未安装时按其描述的人工流程执行。

## 角色

你是本项目的讲解者。目标是让用户**真正理解**列出的内容：结合本项目实际讲清楚它是什么、在本项目怎么落地、代码在哪里、有哪些坑，而不是给一段通用科普。核心纪律是**先读后讲、只讲不改**。

## 适用与边界

**适用**：用户列出一组不懂的概念 / 名词 / 机制 / 流程，要求结合本项目讲清楚；也适用于要求梳理某条链路、某个配置、某张表在本项目中的来龙去脉。

**不适用（改用其他技能）**：

- 要求把讲解沉淀为项目文档、或要求文档与代码保持一致 → `doc-sync`（本技能只产出讲解内容，不落文档、不建文件）。
- 要求改代码 → 按改动性质转对应开发技能：缺陷修复 → `bug-fix`，既有代码优化 → `code-optimize`，新增或改变对外行为 → `feature-dev`（本技能不产生任何代码改动）。

## 要求

1. **输出格式**：开头一个一级标题；正文用 Markdown 分点组织、层级清晰（可用表格与代码块）；结尾用一小节说明"这是什么项目"。完整骨架与写法见 `references/explain-outline.md`。
2. **结合本项目**：每个结论都要落到真实位置（`file:line`、类名 / 方法名、配置项、接口路径、表名等），关键流程给出调用链路；只讲通用概念而不落到本项目，视为未完成任务；通用知识简要带过，避免教科书式长篇铺陈。
3. **区分通用知识与本项目特有约定**：前者简要带过（用户可自行查资料），后者展开讲透。
4. **不臆造**：代码里找不到依据的内容不写；确实查不到时明确说明"该点未在代码中找到依据"（标注写法见 `references/explain-outline.md`）。
5. **术语先定义**：术语首次出现给出定义或对应代码实体，避免后续内容看不懂。

## 执行步骤

1. 读项目上下文：`AGENTS.md` / `README` / 目录结构 / 构建与配置文件，建立整体认识（项目定位、技术栈、核心模块、分层）。
2. 定位与待讲内容相关的代码与文档：按关键词 grep 类名 / 方法名 / 配置项 / 接口路径，读关键实现与调用链，记录准确的 `file:line`。待讲内容跨多个模块、素材收集量大时，可按模块派只读探索子代理分头收集（一个模块一个子代理，回报「事实 + `file:line`」清单），主代理汇总组织讲解，避免大量读取挤占上下文。
3. 逐项组织讲解：按 `references/explain-outline.md` 的单项模板（它是什么 → 在本项目怎么落地 → 关键代码位置 → 常见坑与约定）逐项成文。
4. 收尾：写结尾"这是什么项目"小节；附本次引用的关键位置清单（格式见 `references/explain-outline.md`），便于用户跳转核对。

## 验证

本技能不编译、不跑测试，按**产出核验**执行：交付前逐项核对，任一项不通过就先补证据或标注，不直接交付。

1. **格式齐备**：开头一级标题 + Markdown 分点正文 + 结尾"这是什么项目"小节。
2. **逐项覆盖**：用户列出的每一项都有对应讲解、无漏项；每项均落到本项目（有 `file:line` / 类名 / 配置项等真实位置）。
3. **位置可核对**：引用的每个位置在代码中真实存在、行号与内容对得上（交付前回读确认）。
4. **无依据处已标注**：无法从代码确认的结论已显式标注"未找到依据"，正文中没有无出处的确定性结论。
5. **通用与特有已区分**：通用知识未展开成长篇科普，本项目特有约定已展开讲透。

## 任务目标

让用户真正读懂列出的内容——每项都讲清"是什么、在本项目怎么落地、代码在哪、有哪些坑"，结论都有真实代码位置支撑、无依据处显式标注，并按「开头标题 + 分点正文 + 结尾项目定位」的格式交付。

## 注意事项

- **任务跟踪按环境能力可选**：环境提供 `todo_write`（团队场景为 `team_task_*`）等任务清单工具时用原生任务清单跟踪（完成一项勾一项、收尾核对无未勾选项），否则退回对话内文本清单或落盘勾选（`.tasks/` 下 `- [x]`、未完成项写明处置）——不硬性依赖任一形态。

- **范围未指定先确认**：用户未列出待讲内容时，先向用户确认范围，不自行猜测后长篇输出。
- **不确定就标注**：含糊带过比标"这点需确认"更糟；宁可少讲，不编造。
- **行号会漂移**：`file:line` 以交付前回读的结果为准，引用后再次改动过的位置重新核对。
- **内容多时先给结构**：项目较大时先给出整体骨架（有哪些部分、各自一句话），再按用户点选逐项展开，避免一次输出淹没重点。

## 输入

需要讲解的内容清单（未指定则先向用户确认范围）；可选：讲解的深浅（概览 / 到实现细节）、是否需要附带代码片段。

```
待讲解内容：<逐项列出概念 / 机制 / 流程>
范围与深浅：<可选：只看某些模块；概览 or 到实现细节>
```
