# 讲解产出模板

供 agent 按需加载：在 `project-explain` 的「执行步骤」第 3、4 步与「验证」环节读。给出可直接照抄的文章骨架与逐项写法；示例中的 `<占位符>` 按项目实际替换。

## 1. 文章骨架

```markdown
# <讲解主题>

<一句话说明本次覆盖哪几项、各自的定位>

## 1. <概念 A>

### 它是什么
<一句话本质 + 解决什么问题>

### 在本项目怎么落地
<本项目实际用法与约定：配置在哪、入口在哪、由谁调用、边界在哪>

### 关键代码位置
- 定义：`<项目根>/<路径>/<类名>.<ext>:<行号>` — <该处做了什么>
- 调用链：`<入口类>#<方法>` → `<服务类>#<方法>` → `<数据访问类>#<方法>`

### 常见坑与约定
<本项目特有的注意事项 / 易错点 / 禁止用法；无依据则整条省略>

## 2. <概念 B>
...

## 这是什么项目

- **定位**：<项目解决的问题 / 服务的业务>
- **技术栈**：<语言、框架、构建工具、数据存储>
- **核心模块**：<按目录或分层列出主要模块及一句话职责>

## 附：本次引用的关键位置

| 位置 | 说明 |
|---|---|
| `<项目根>/<路径>/<文件>:<行号>` | <支撑了哪条结论> |
```

## 2. 单项模板（对每一个待讲内容）

### 2.1 它是什么

一句话本质 + 解决什么问题，避免教科书式长篇铺陈；顺带指出它在本项目里对应哪个代码实体。

> 写法示例：`<概念> 是 <一句话本质>，用于解决 <问题>；在本项目中对应 <类名 / 配置项 / 表名>。`

### 2.2 在本项目怎么落地

写**项目事实**而不是框架通用用法：配置写在哪个文件、入口在哪个类、由谁调用、生效范围与边界在哪。这一段是"结合本项目"的主体，缺了就是通用科普。

### 2.3 关键代码位置

`file:line` + 简短说明；只贴最小必要的代码片段，不整段摘抄。

```markdown
- 定义：`<项目根>/<路径>/<类名>.<ext>:<行号>` — <该处做了什么>
- 入口：`<项目根>/<路径>/<类名>.<ext>:<行号>` — <从哪个入口触发>
- 调用链：`<入口类>#<方法>` → `<服务类>#<方法>` → `<数据访问类>#<方法>`
```

行号以交付前回读的结果为准；引用后被改动过的位置重新核对。

### 2.4 常见坑与约定

本项目特有的注意事项、易错点、禁止用法（如约定俗成的配置位置、易踩的默认值、禁止的调用方式）。

**没有依据就跳过这一条**，不硬凑、不把通用坑写成"本项目的坑"。

## 3. 结尾「这是什么项目」小节

固定放在正文之后，三条以内，每条结论都要能从项目文件读得：

```markdown
## 这是什么项目

- **定位**：<这个项目解决的问题 / 服务的业务，来源：`README` / `AGENTS.md`>
- **技术栈**：<语言、框架、构建工具、数据存储，来源：构建与配置文件>
- **核心模块**：<按目录或分层列出主要模块，各一句话职责>
```

读不到的条目如实写「未从代码中找到依据」，不套用同类项目的常见形态。

## 4. 引用位置清单

附在正文末尾「这是什么项目」小节之后，便于用户跳转核对：

```markdown
## 附：本次引用的关键位置

| 位置 | 说明 |
|---|---|
| `<项目根>/<路径>/<文件>:<行号>` | <该位置支撑了哪条结论> |
```

- 只列正文真正引用过的位置，不堆砌无关文件。
- 位置多时按讲解项分组，不排成无序长列表。

## 5. 无依据处如何标注

**原则**：查不到就不写确定性结论；宁可标注存疑，不含糊带过、不臆造。

```markdown
- <结论 A>：已确认，见 `<项目根>/<路径>/<文件>:<行号>`。
- <结论 B>：该点未在代码中找到依据——`<关键词>` 全仓检索只出现在注释 / 文档，无对应实现；如项目另有约定请补充。
- <结论 C>：推测为 <X>（依据：<某处代码的旁证>），**未确认**；需要时按 <验证方式> 核实。
```

**禁止写法**：把通用知识写成"本项目的实现"；用"应该是""通常是"替代出处；引用未回读的行号；对查不到的点直接略过不提。
