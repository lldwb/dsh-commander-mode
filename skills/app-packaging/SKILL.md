# 打包与分发

## 在 DSH 中的对应工具

本技能原为 Claude Code 技能库中的一项，正文方法论原样保留；在 DSH 中按以下对照表映射工具与交互方式：

| 原（Claude Code） | DSH 等价物 |
| --- | --- |
| `Task` / `Agent` 工具、子代理 | `subagent`（一次性子代理，异步、完成时通知）/ `spawn_teammate`（持久队友）/ `workflow`（批量扇出编排） |
| `AskUserQuestion` | `ask_user_question` |
| `SendMessage` / `TaskStop` | `send_message` / `interrupt_agent` |
| `TodoWrite` / `Task*` | `todo_write`（团队场景用 `team_task_*`） |

| `WebFetch` / `WebSearch` | `web_fetch` / `web_search` |
| `Skill` 工具 | `skill` 工具 |
| MCP 工具 | 对应的 DSH 插件工具（如 `browser_*`、`android_*`、`ssh_*`） |

补充：

- 正文中标注为 bash 的代码块是通用 shell 示例，Windows 下用 `pwsh` 执行（`git` 等命令一致，管道 / 变量语法按需改写）。

- 正文引用的其它技能名（如 `commit-create`、`mr-create`、`git-*`）可能由同包或其它插件提供，能否调用以当前环境实际安装的技能为准；未安装时按其描述的人工流程执行。

## 角色

你是本项目的**分发工程师**。目标只有一个：让使用者**拿到产物就能用**——不装开发环境、不看构建文档。顺序固定：**先定产物形态 → 再定构建在哪跑 → 最后定怎么交付**；形态未定就动手构建，返工率极高。

## 适用与边界

**适用**：

| 场景 | 说明 |
|---|---|
| 单文件可执行 | 把脚本 / 应用打成目标机无需安装运行时的单个可执行文件（Node SEA 见 `references/node-sea.md`） |
| 产物形态决策 | 在裸目录 / zip / 单文件 / 安装包之间选定形态并产出可分发件 |
| 产物体积压缩 | 安装包太大、要压到附件限额 / 带宽目标内：运行时裁剪 + 换压缩算法（方法见 `references/runtime-trimming.md`）——**先量化构成再动手** |
| 跨平台构建 | 多平台 × 多架构产物的构建编排（本地多环境或 CI matrix） |
| CI 构建与分发 | 按 tag 或手动触发构建，产物发到 Release 附件 / 制品库，附校验和（见 `references/ci-distribution.md`；发 Release 的 GitHub 机制坑位清单见 `references/github-release-pitfalls.md`） |
| 版本注入 | 产物内版本号与 git tag 一致（`--version` 可查），并产出校验和清单 |

**不适用（改用其他技能）**：

- 构建 / 打包**报错**的定位与修复 → `bug-fix`；
- 只管版本号、tag、Release 正文的发版流程（不涉及产物）→ 按项目自身的发版规范（如 `AGENTS.md` 的发版章节）；
- 合并请求（MR/PR）生成 → `mr-create`；
- 仅 CI 配置的结构性改造 / 迁移 → `refactor`。

## 要求

1. **产物形态先定**（形态决定构建方式与分发渠道，反过来必返工）：

   | 形态 | 适用 | 代价 |
   |---|---|---|
   | 裸目录 | 内部工具、目标机已有完整环境 | 传输与权限易丢，无版本封装 |
   | zip / tar.gz | 多文件产物、需保留目录结构 | 使用者要解压；**解压后可能丢可执行位** |
   | 单文件可执行 | 面向不懂技术的使用者、目标机无运行时 | 体积大（内嵌运行时）、调试信息少 |
   | 安装包 | 需写入系统位置 / 注册项 / 快捷方式 | 制作与签名成本最高，每平台一套 |

   判据是**使用者要在目标机上做几步操作**：要「双击就能跑」就单文件；要「放进 PATH 的命令行工具」就 tar.gz + 安装说明；要「像正规软件那样卸载和升级」才上安装包。
2. **运行时依赖先盘点**：产物是否要求目标机预装运行时（Node / Python / JVM）？要求则写明**最低版本**（写进 `--version` 输出或 README），不要求就得内嵌（用体积换零依赖）。
3. **平台矩阵要含架构**：`Windows x64` / `macOS arm64` / `Linux x64` 是**三个不同产物**，别默认「都是 x64」；苹果芯片与 x64 产物不能互用（走 Rosetta 是使用者的选择，不是你的）。
4. **交叉构建有边界**：纯资源打包可跨平台；**原生模块、字节码 / 快照 / 代码缓存、需平台签名的产物必须对应平台构建**（详见两个 references）。拿不准时按「不跨」处理，用对应平台 runner 或本地机器。
5. **产物必须实测**：在**干净环境**（无开发依赖的机器 / 全新容器）跑一次——`--version` 与冒烟命令退出码；只在构建机上「能跑」不构成证据。
6. **版本号单一来源**：产物内版本从版本文件或 git tag 注入，**不在多处各写一份**；分发文件名与 tag 一致（`<应用名>-<版本>-<平台>-<架构>.<扩展名>`）。
7. **交付带校验和**：产物旁给 `SHA256SUMS`（或每产物一行），下载方有办法核对。
8. **分发渠道按持久性与形态选**：CI 中间产物用 **Artifacts**（有保留期、会打 zip、**剥可执行位**）；给人下载的用 **Release 附件**（长期保留、原始文件）。二者不可混用，详见 `references/ci-distribution.md`。
9. **体积先量化再裁剪**：要压安装包体积时，先摸解压后构成、逐项测「压缩后贡献」，再决定删什么 / 换什么算法——决策依据是压缩后体积不是解压态大小；删运行时组件后必须跑启动冒烟，且清楚 CI 冒烟测不出硬件能力退化（详见 `references/runtime-trimming.md`）。

## 执行步骤

1. **盘点**：目标平台 / 架构清单、运行时依赖、现有构建脚本与 CI 配置；项目已有产物约定时**从既有约定**，不另起一套。
2. **定形态与渠道**：按「要求 1 / 8」给结论，交用户确认——这一步的选择决定后面全部工作。
3. **打通单平台本地构建**：先把**一个**平台的产物做出来并实测（`--version` + 冒烟），再谈多平台。
4. **多平台编排**：按「能跨则跨、不能跨则对应平台」逐个产物决定在哪构建；上 CI 时用 matrix（模板 `assets/workflow-build-release.yml`）。
5. **分发**：产物发到 Release 附件 / 制品库，附校验和；命名含版本、平台与架构。
6. **验证**：按下方「验证」在干净环境实测，核对下载链接可达、校验和一致。

## 验证

- **干净环境实测**：在目标平台（或对应 runner）上，下载 / 复制产物后直接运行——`--version` 输出与 tag 一致、冒烟命令退出码 0、无「缺少运行时 / 缺少动态库」报错；
- **零假设**：在没装开发环境的机器或全新容器里跑（构建机与 CI 上能跑都不构成证据）；
- **校验和**：`sha256sum` 结果与发布的 `SHA256SUMS` 一致；
- **可访问性**：Release 附件链接可下载（`/releases/download/<tag>/<文件>`），文件名与文档里写的一致；
- **下载 / 更新链路实测**：有自更新 / 下载消费端的项目，发版后在打包产物上真机跑一遍「检查更新 → 下载 → 替换」，确认**下载到的是产物不是 JSON / HTML**、附件挑得对、版本号能更新。单文件产物（SEA / bundle）通常吃 `NODE_OPTIONS --require`，可挂代理预载走真网络；`isPackaged()` 类判断有显式标志的，拷一份可执行文件伪装打包态即可端到端（真下载、真替换、替换后逐字节核对）；产物已是最新版、手头没有旧版可跑时，临时把版本号改回上一版重新打包一份「伪装旧版使用者」的产物再跑（打包内嵌的是打包时刻的版本号，跑完立即还原版本号）。校验和证明的是**完整性**（下到的就是发布的那份），不防**篡改**（清单与产物同源，防篡改要签名）；清单取不到时按「跳过」还是「拒绝」想清楚——镜像渠道可能只发正文不带清单。

## 任务目标

产出**使用者拿到就能用**的产物并交付：形态与平台矩阵明确、构建可复现、版本号与 tag 一致、校验和齐备、分发链接可用。

## 注意事项

- **任务跟踪按环境能力可选**：环境提供 `todo_write`（团队场景为 `team_task_*`）等任务清单工具时用原生任务清单跟踪（完成一项勾一项、收尾核对无未勾选项），否则退回对话内文本清单或落盘勾选（`.tasks/` 下 `- [x]`、未完成项写明处置）——不硬性依赖任一形态。

- **产物不进 git**：二进制产物用 Release 附件 / 制品库交付；提交进仓库会让体积不可逆增长。
- **「CI 绿了」不等于产物可用**：CI 只证明构建成功，不证明能在目标机运行——实测环节不可省。
- **模板里的外部版本号要现核**：`assets/` 下模板引用的 action、运行时版本会过时，套用前按官方最新核对；模板给的是**结构与坑位**，不是最新版本号。
- **平台支持现状要现查**：打包工具对平台 / 架构的支持会变（如某工具只测 macOS arm64），套用前用官方文档确认目标平台在支持列表内，别照搬旧经验。
- **签名时机不可颠倒**：任何二进制改动（注入、替换图标、改写资源）都会让已有签名失效——**先改后签**。

## 输入

待打包的应用（入口 / 构建脚本）、目标平台与架构、分发渠道（Release / 制品库 / 内网共享）、（可选）现有 CI 配置与签名证书条件。
