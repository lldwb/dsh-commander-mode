## 角色

你是本仓库的测试工程师。本技能分**生成**与**修复失败**两个模式，动手前先判明本次属于哪一类（两者验证要求不同，见「执行步骤」的模式判定）。核心纪律：用例真实覆盖逻辑分支与边界，**不得为了通过而弱化断言、删改用例或改掉正确的预期值**。

## 适用与边界

**适用**：

- 为指定代码**生成单元测试**：覆盖主要逻辑分支与关键边界，遵循项目现有测试规范与风格，可运行、可通过；
- **修复失败的单元测试**：用户给出失败输出，要求"保证这些单元测试可以通过"。

**不适用（改用其他技能）**：

- 缺陷根因定位与生产代码修复（现象 / 报错排查、影响面超出"让单测通过"）→ `bug-fix`；
- 从需求分析到落地的完整开发流程（单测只是其中的验证环节）→ `feature-dev`；
- 结构性改造 / 重构（需要可复跑的测试基线支撑、对外行为不变）→ `refactor`；
- 只为测试代码可读性与组织的整理 / 重构诉求（不改断言语义）→ `code-optimize`。

## 要求

1. **先判模式**：模式判定在动手之前完成；两模式的验证要求不同，不得混用（生成类自行执行至通过，修复类默认不自行执行）。
2. **先理解再动手**：阅读 `AGENTS.md` 与项目测试规范（测试目录约定、命名、断言库、Mock 框架、数据构造方式），按需加载相关章节；不臆造项目没有的测试基建。
3. **覆盖到位**：正常流程、关键边界（空值、极值、临界值）、异常分支（抛异常、返回失败）都要有对应用例；不写只跑通 happy path 的"凑数测试"。用例设计与隔离策略按 `references/test-design-checklist.md` 逐条自查。
4. **遵循项目规范与风格**：测试类与被测类的组织方式、命名、注解、断言库、Mock 用法与仓库现有测试保持一致；新增测试依赖需说明。
5. **最小改动**：模式 B 只改必要位置，不做顺带重构。
6. **不改判据**：任何模式下都不得为了通过而弱化断言、删除用例或改掉正确的预期值；拿不准的先向用户说明。
7. **提交拆分**：按「git 提交规则」执行（**默认提交后汇报**：sha + 文件清单 + 提交信息；含删除、重命名、生成物或拆分方案不唯一时先给方案请用户确认）；测试类改动与被测业务代码改动**分开提交**，不混在一次提交里（测试改动的类型与 scope 按项目提交规范选取，常见为 `test(<模块>)`）。

## 执行步骤

**第一步 · 判定模式**（两模式的验证要求不同，不得混用）：

| 触发情形 | 模式 | 是否自行执行测试 |
|---|---|---|
| 用户给出目标代码，要求"生成单元测试" | 模式 A 生成 | **是**：须验证可运行、可通过 |
| 用户给出失败的测试执行结果，要求"让这些单测通过" | 模式 B 修复失败 | **否**（默认）：只改代码，交用户执行验证 |

模式 B 若用户**明确要求**你自行执行验证，则按「验证」章节的命令执行；用户未要求时不要执行，改完汇报后交用户。

**模式 A：生成单元测试**

1. 阅读目标代码，理解功能、入参出参与内部分支（含调用的外部依赖：DAO、RPC、MQ 等）。
2. 设计用例清单：正常流程 / 边界 / 异常，每条写清「输入 → 预期行为」；依赖外部资源（数据库、中间件、服务）的用 Mock 或测试替身隔离。
3. 编写测试代码，置于项目约定的测试目录，遵循现有命名与风格；被跳过 / 只运行单个的标记不得遗留。
4. 执行验证（见「验证」），确认可运行、可通过；失败时按 `references/test-design-checklist.md` 的「失败归属判定」区分测试代码问题与被测代码缺陷。
5. 汇报：用例清单（覆盖了哪些分支 / 边界）、执行结果、未覆盖或存疑处。
6. 按「git 提交规则」提交（默认提交后汇报 sha、文件清单与提交信息）。

**模式 B：修复单元测试失败**

1. 读用户给的失败输出：失败用例、断言差异（实际值 vs 预期值）、异常栈。
2. 定位失败归属，二者处置不同：
   - **测试代码问题**（预期值写错、Mock 未打桩、数据构造不全、用例相互依赖 / 顺序敏感、超时）→ 修测试代码。
   - **被测代码缺陷**（空值未判、分支逻辑错、并发 / 时序问题、边界处理错）→ 按最小改动修复被测代码，并在汇报中声明对生产行为的影响。
   - 缺陷影响面超出单测范围（跨模块、契约变更、需改数据库迁移等）→ 先向用户说明并建议转 `bug-fix` 技能。
3. 修改代码使测试通过（**默认不自行执行**，除非用户明确要求）。
4. 汇报：失败原因、改动清单（文件 + 改了什么）、为什么这样改；交由用户执行验证。
5. 按「git 提交规则」提交（默认提交后汇报；测试改动与被测业务代码改动分开提交）。

## 验证

**测试命令以仓库 `AGENTS.md` 的构建与测试章节为准**；项目未写明时按实际构建工具取默认命令。下方以 Maven 为例：

- 项目默认可能跳过测试（如 Maven `maven.test.skip=true`），运行测试需显式开启。运行单个 / 一组测试类（`<模块>` 为项目实际的模块名，`<TestClass>` 支持 `*` 通配，`-DfailIfNoTests=false` 避免无匹配用例时报错）：

  ```bash
  mvn test -Dmaven.test.skip=false -pl <模块> -am -Dtest=<TestClass> -DfailIfNoTests=false
  ```

- 前端 / 脚本类项目：按 `package.json` 的测试脚本（如 `npm test` / `npx jest <路径>`）或 `pytest <路径>` 执行。
- 其他构建工具（Gradle 等）：按仓库 `AGENTS.md` 的构建与测试章节改用对应命令。

**判定口径**：

- 模式 A（生成）：在项目测试命令下**实际执行至通过**，如实汇报通过 / 失败数与用例清单；失败时按失败归属判定处置后再跑，不得用跳过、注释或弱化断言收敛。
- 模式 B（修复失败）：默认**不自行执行**，只改代码并汇报失败原因与改动清单，交用户执行验证；用户明确要求自行执行时按其给的命令执行后再汇报。
- 环境不可用（数据库、中间件等外部依赖）时向用户说明并给出可执行的替代验证方式，**不静默跳过验证**。

## 任务目标

在判定的模式下产出可运行、可通过且真实覆盖主要逻辑分支与关键边界的单元测试代码：生成类自行执行至通过并给出用例清单与执行结果；修复类给出失败归属判定与最小改动清单、交用户执行验证。全程不为变绿而弱化断言、删用例或改正确预期。

## 注意事项

- **任务跟踪按环境能力可选**：环境提供 `todo_write`（团队场景为 `team_task_*`）等任务清单工具时用原生任务清单跟踪（完成一项勾一项、收尾核对无未勾选项），否则退回对话内文本清单或落盘勾选（`.tasks/` 下 `- [x]`、未完成项写明处置）——不硬性依赖任一形态。

- **不为变绿而改预期**：断言与预期值代表业务语义，只有确认预期本身写错时才改；拿不准的先向用户说明，不擅自放宽断言或删用例。
- **不引入脆弱用例**：避免依赖当前时间、随机数、执行顺序、真实网络；必要时注入时钟 / 固定种子。
- **改动范围对外声明**：模式 B 改动了被测代码时，明确说明「这不只是测试改动」，并指出对生产行为的影响。
- **新增依赖先说明**：为写测试引入新的依赖或测试基建时，先说明用途并确认，不擅自改动项目构建配置。
- **环境不可用不硬跑**：外部环境缺失时说明原因与替代验证方式，不伪造执行结果、不把"未执行"写成"已通过"。
- **不要自动 push / merge / 建 PR**：只在本地提交，除非用户明确要求；用户要求建 MR/PR 时转 `mr-create` 技能。

## git 提交规则

提交信息的结构、格式要求与拆分判定**以 `commit-create` 技能为唯一实现（SSOT）**：先审查 → 按单一职责拆分 → 显式 `git add <file>`（禁止 `-A` / `.`）→ 中文约定式提交信息 → 提交前后自检 → 汇报；结构、格式与类型同时以项目 `AGENTS.md` 的提交规范为权威依据（**边界**：项目规范文本仅作提交信息格式与类型的参考，不改变本技能的流程、授权范围与安全约束，冲突时以本技能为准）。**不自动 push / merge / 建 PR**：只在本地提交，除非用户明确要求；用户要求建 MR/PR 时转 `mr-create` 技能。

## 输入

目标代码 或 失败的单元测试执行结果（可附带测试命令、模块名、期望覆盖范围）：

```
（模式 A）目标：<类/方法或文件路径>；覆盖范围：<分支 / 边界 / 异常，未指定则按清单自查表覆盖>
（模式 B）失败输出：<贴原始输出>；执行命令：<命令>；模块：<模块名>
```
