# 单元测试设计与自查清单

> 供 agent 按需加载的参考件：**设计用例清单（模式 A 第 2 步）与编写测试代码前读**；模式 B 判断失败归属时回看第 5 节，收敛验证时回看第 6 节。本清单只给通用判据，测试目录、命名、断言库、Mock 框架、构建与测试命令一律以仓库 `AGENTS.md` 与项目测试规范为准。

## 一、用例设计

每条用例都必须能写成一句「输入 → 预期行为」，写不出预期行为的用例不写。

1. **正常流程**：主路径逐个覆盖，包含典型入参下的返回值 / 状态变更 / 对外交互（调用次数与参数）。
2. **边界**：
   - **空值**：`null`、空字符串、空集合 / 空数组、零元素分页；
   - **极值**：最大 / 最小、`0`、负数、超长文本、超大集合；
   - **临界**：区间开闭端点、阈值 ±1、分页首页 / 末页、数量恰好等于上限或下限。
3. **异常分支**：抛异常（参数非法、依赖返回失败或超时、状态不允许）；返回失败（错误码、空结果、布尔 `false`、违约提示）。
4. **等价类划分**：每个输入维度划出有效 / 无效等价类，每类取**一个**代表值，不为同一分支堆重复用例；多条件判定按关键组合（真值表中有代表性的组合）覆盖，不穷举笛卡尔积。
5. **覆盖自查表**：列出被测方法的分支清单，逐条标注「已覆盖（对应哪个用例）/ 未覆盖（原因：不可达 / 需环境 / 超出本次范围）」，未覆盖项写进汇报，不假装全覆盖。

## 二、隔离策略

单元测试只验证被测单元自身逻辑，**被测单元之外的一切都不真实依赖**：

- **外部依赖用 Mock 或测试替身**：数据库、缓存、中间件、RPC / HTTP 服务、文件系统、消息队列、第三方 SDK 一律替换为 Mock / stub / fake / spy，用项目既有的 Mock 框架与写法；替换的是**依赖的交互**，不是被测逻辑本身。
- **不依赖真实网络**：单测内不发起真实请求；确实无法隔离的用例属于集成测试，须单独标注与说明，不计入"单元测试通过"的口径。
- **不依赖真实时间**：时钟注入或冻结时间，不断言"距今多少秒""当天"这类随执行时刻变化的量。
- **不依赖随机**：固定随机种子，或把随机源替换为可控实现。
- **不依赖执行顺序**：用例之间相互独立、不共享可变状态；前置数据在用例自身或 `setUp` 中构造，不靠"前一个用例留下的数据"；断言不依赖并发调度顺序（必要时注入可控的执行器 / 线程模型）。
- **Mock 不打桩过宽**：只对本次用例关心的交互打桩；对非预期的依赖调用应让测试失败（严格 Mock / 校验多余交互），避免"桩打太宽把缺陷掩盖成通过"。

## 三、必须遵守

1. **可运行、可通过**：生成类须在项目测试命令下真实执行至通过；修复类默认由用户执行验证（见第 6 节）。
2. **遵循项目测试规范与命名**：测试目录、类名与方法名、注解、断言库、基类与工具类、参数化写法，与仓库现有测试保持一致。
3. **数据构造与仓库一致**：使用项目既有的测试数据构造方式与工具类，不新造一套并行基建；构造数据只包含本用例需要的字段。
4. **一个用例一个行为点**：一条用例只验证一个行为，失败时能直接定位；断言指向可判定的结果（返回值、状态、交互次数与参数），不只断言"没抛异常"。
5. **测试名称表达意图**：命名体现"场景 + 预期"，不用 `test1` / `testMethod` 这类无信息量命名。
6. **新增依赖先说明**：引入新依赖或测试基建前先说明用途并确认，不擅自改动项目构建配置。

## 四、禁止

- **为让测试变绿而弱化断言、删除用例、改掉正确的预期值**——这是本技能的第一红线。
- **恒真断言**：断言"结果不为 `null` 就行"、断言自己构造的期望对象、`assertTrue(true)` 式占位。
- **把被测逻辑抄进测试充当预期**：预期值须可由需求 / 接口约定独立推导，不得照抄实现的计算过程（否则实现错了测试也通过）。
- **脆弱用例**：依赖当前时间 / 时区、随机、执行顺序、真实网络、真实环境数据或机器性能（`sleep` 式等待）。
- **跳过式收敛**：用跳过 / 注释掉 / 只跑单个用例（`@Disabled`、`skip`、`.only`）让结果变绿，且不清理、不说明。
- **改动无关代码**：模式 B 顺手重构、格式化、调整无关配置。

## 五、失败归属判定

先分类、再动手，分类结论要写进汇报：

| 现象 | 归属 | 处置 |
|---|---|---|
| 预期值写错、Mock 未打桩 / 打桩不匹配、数据构造不全、用例相互依赖或顺序敏感、超时设置不当 | 测试代码问题 | 修测试代码，不改业务语义 |
| 空值未判、分支逻辑错、边界处理错、并发 / 时序问题、状态流转错 | 被测代码缺陷 | 按**最小改动**修复被测代码 |
| 跨模块影响、契约变更、需改数据库迁移、需改外部依赖行为 | 超出单测范围 | 先向用户说明，建议转 `bug-fix` 技能 |

补充判据：

- **改动被测代码时必须在汇报中显式声明**「这不只是测试改动」，并说明对生产行为的影响面（哪些调用方会受影响、是否需要回归）。
- **预期值 vs 实现，谁是权威**：预期值只可由需求 / 接口约定推导；若"看起来是测试写错了"但无法从需求独立推导，先向用户确认，不擅自把预期值改成实现的当前输出。
- **一个失败用例只归一类**：同一失败不既改测试又改实现；先归因、后动手。

## 六、验证循环

1. **模式 A（生成）——自行执行至通过**：执行测试 → 失败则按第 5 节判归属 → 修 → 重跑，循环至全部通过；每次重跑都跑本次相关用例集合，收尾至少完整跑一次。收敛过程中不得用第四节的任何禁止项换通过。
2. **模式 B（修复失败）——默认交用户执行**：改完即停，汇报「失败原因 + 改动清单（文件 + 改了什么）+ 为什么这样改」，交用户执行验证；用户**明确要求**自行执行时，按用户给的命令（或项目测试命令）执行后再汇报。
3. **收尾核验**（两种模式都做）：
   - 用例清单与代码逐条对得上，覆盖自查表无空项；
   - 无被跳过 / 被注释 / 仅单跑的用例遗留；
   - 执行结果如实汇报（通过数 / 失败数 / 未执行原因），**不伪造执行结果**；
   - 未覆盖与存疑处单列，供用户决策。
