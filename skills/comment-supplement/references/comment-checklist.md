# 注释补全 / 修正检查清单

供 agent 按需加载：执行 `comment-supplement` 的「逐文件审查并标记三类位置」「补全与修正」「自检」「整理不确定项清单」四步时读。逐项过一遍，命中即处理；不适用项标注原因，不静默跳过。

**共同前提**：判定一律**以代码为准**——注释自述、文档、需求描述、提交历史只能作旁证，不能作为改写注释的依据；以旁证为依据的改动放入不确定清单交用户确认。

## 1. 三类标记的判定标准与依据

### 1.1 缺失

- **判定**：项目注释规范要求说明的元素没有任何说明性注释，或只剩占位骨架（空注释块、只有标签没有描述、只有分隔线）。
- **依据**：对照项目注释规范的必填范围（哪些可见性的类型 / 方法 / 字段必须注释）逐项核对；项目无明文规范时参照同文件同类元素的注释齐备情况。
- **处置**：按规范补齐标签与说明；说明内容必须写"为什么 / 约束条件"，无法从代码判断意图的进不确定清单。

### 1.2 不准确

- **判定**：有注释但描述与代码实际行为不符。典型形态：
  - 参数说明与实际不符——含义、顺序、单位、取值范围、可空性、是否被修改；
  - 异常未写或写了不会抛的异常；
  - 返回值语义与实现不符（成功 / 失败的返回形态、空值、默认值）；
  - 名称与注释不一致——参数 / 字段 / 方法改名后注释未同步；
  - 复制粘贴遗留的错别字或张冠李戴（注释里的名字、单位、对象不是本处的）。
- **依据**：顺着**实际执行路径**读实现（含分支、早返回、异常分支、循环边界），必要时看调用方与下游消费方确认真实语义。
- **处置**：按实现改写描述；只改注释文本，不动代码。

### 1.3 过期

- **判定**：注释描述的是历史实现或已不存在的能力。典型形态：
  - 被注释掉的废弃代码块及其说明；
  - 指向已删除 / 已改名的类型、方法、配置项、字段的说明；
  - 与当前默认值、枚举取值、约束条件不一致的描述；
  - 长期挂着的 TODO / "暂时保留"，而事实已变更或已完成。
- **依据**：全仓检索注释中引用的符号名、配置键、字段名是否仍存在；对照代码当前实现与配置默认值。
- **处置**：废弃代码块的说明随块清理（是否删除被注释掉的代码块由用户确认）；引用失效的说明按现状改写或删除，无法判断是否可删的进不确定清单。

### 1.4 边界情形

- 同一处同时命中两类时取最严重的一类记录，处置时一次改到位；不拆成多条重复记录。
- 只改注释文本与标签，**不因"注释说得对"反过来改代码**——代码与注释冲突时以代码为现状、以确认为准。

## 2. 注释写法约定

### 2.1 写什么

- **写"为什么"与约束条件**：设计取舍的原因、隐含前提、调用前置条件、边界与不变量、易踩的坑（如"必须先落库再发通知，否则下游查不到"）。
- **不复述代码字面意思**：不写"设置 X 为 Y""遍历列表累加""调用某方法"这类把代码翻译一遍的内容。
- **结构性说明写全**：参数含义与约束（单位、范围、可空性）、返回值语义（含失败与空值）、副作用（写库、发消息、改状态、写缓存）、并发 / 事务 / 幂等约束。
- **一处一义**：方法与字段的说明写在其声明处，实现内部的局部约束写在其所在语句上方；同一条信息不在两处重复。

### 2.2 标签与语法按项目规范

- 文档注释的必填标签（形如 `<标签> <说明>`）、单行 / 块注释的语法与位置，**一律以项目现有注释规范为准**，本清单不规定具体标签名。
- 项目无明文规范时：与**同文件既有注释**的标签集合、书写顺序、句式、标点保持一致，不混用。
- 只补说明文本与缺失的标签，不新增 / 改写标签以外的代码符号，不做与内容无关的重排。

## 3. 反例（写了等于没写）

| 反例 | 为什么不行 | 改成什么 |
|---|---|---|
| `// get 方法获取 X`、`// 设置 Y` | 复述代码字面意思，代码一改注释必然过期 | 不写；确需说明时写约束条件（为什么用该取值、调用方前提） |
| `// TODO: 待补充`、`// 这里是核心逻辑` | TODO 式占位 / 含义不明的空话 | 补上可判定的信息，或删除占位注释 |
| `// 参数：模块名称`，实际传入的是 ID | 复制粘贴遗留，与实现不符 | 按实现纠正为真实语义与格式 |
| `// 处理数据` 覆盖上百行方法 | 无信息量，且掩盖真实副作用 | 写清输入输出、副作用、异常与关键不变量 |
| 注释里写死默认值 / 枚举取值，实现已变 | 过期描述误导调用方 | 与实现对齐；冲突无法判断时进不确定清单 |
| 被注释掉的整段旧实现，仅配 `// 旧逻辑` | 无保留原因说明，读者无从判断能否删 | 说明保留 / 兼容的原因；无价值则列入清单交用户确认删除 |

## 4. 自检命令

1. **逐块确认改动落在注释内**：

   ```bash
   git diff
   ```

   逐 hunk 核对：增删行是否都位于注释块内（`/** ... */`、`//`、`<!-- -->`、`#` 等）？出现代码行即回退该 hunk。

2. **忽略空白辅助判断**：

   ```bash
   git diff -w
   ```

   忽略空白后差异消失 → 只动了排版 / 缩进；仍有差异的块逐个确认是否仅为注释文本变化、有无顺带改动。

3. **编译 / 构建验证未破坏语法**（命令见项目 `AGENTS.md` 的 Build & Run 章节）：

   ```bash
   <项目编译命令>
   ```

   注释改动不应改变编译结果；编译失败说明越出了注释范围（如误删注释符、注释块未闭合）。

4. **变更范围核对**：

   ```bash
   git diff --stat
   ```

   确认涉及文件与计划一致，无顺手改动的无关文件。

**判定**：全部 hunk 落在注释内 + 编译（构建）通过 → 可提交；任一条不满足先回退再继续，不静默放行。

## 5. 不确定项清单格式

无法从代码 / 配置判断真实意图的项**一律进清单，先交用户确认再写**；三要素不可缺：

| # | 位置 | 存疑点 | 无法判断的原因 | 待确认的问题 |
|---|---|---|---|---|
| 1 | `<文件>:<行>` | 现有注释称"返回特殊值表示失败"，但实现只在超时分支返回该值 | 无法判断是注释过期，还是实现漏写了其他失败分支 | 以哪一方为准？按现状改写还是保留原描述？ |
| 2 | `<文件>:<行>` | 被注释掉的废弃代码块无说明 | 无法判断是保留待恢复还是遗忘清理 | 是否删除？ |

- **位置**用 `文件:行`（相对项目根的路径），有多处同类项可合并为一行并列出全部位置。
- **存疑点**只陈述事实差异，**不写猜测结论**；**无法判断的原因**要说明缺哪一项依据（代码不确定、无规范、无调用方佐证等）。
- 确认后按"只动注释"补写；用户未答复的项保留原注释并在汇报中列出。
