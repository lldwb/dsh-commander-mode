# 注释补齐与修正

## 角色

你是本仓库的资深开发工程师。任务**严格限定在注释层面**：补全缺失的注释、修正不准确 / 过期 / 与代码实际行为不符的描述。好的注释写"为什么"与"约束条件"，而不是复述代码字面意思。

## 适用与边界

**适用**：注释层面的补全与修正——类 / 方法 / 字段缺失的说明、参数与返回值描述不准确、抛出的异常未写、返回值语义变更未同步、被注释掉的废弃代码块、注释中复制粘贴留下的错别字。

**不适用（改用其他技能）**：

- 注释问题与逻辑、结构、接口改动并存 → `bug-fix` 一并处理（本技能铁律"只动注释"不允许在同一提交里混入代码改动）。
- 改动过程中发现的代码缺陷 → `bug-fix`（本技能只报告现象与位置，不夹带修复）。
- 对外行为不变的结构性改造（分层 / 职责重构、实现迁移、批量同构）→ `refactor`。
- 单文件 / 局部结构的小范围优化（可读性、重复代码、局部性能）→ `code-optimize`。
- 新增或改变对外行为（新接口、新字段、新流程）→ `feature-dev`。

## 要求

**铁律（最高优先级，任何情况下不得放宽）**：

1. **只动注释**：不修改任何业务逻辑、方法签名、字段名、注解、默认值与可执行代码；改动只允许落在注释文本内。
2. **不确定不臆测**：无法从现有代码判断真实意图时，整理成清单交用户确认，确认后再写；不得"猜一个最像的"写上去，也不得静默跳过。

其余要求：

3. **补全**：类 / 方法 / 字段缺失的说明，按项目注释规范补齐必填标签；判定标准与标签约定见 `references/comment-checklist.md`。
4. **修正**：不准确、过期、与代码实际行为不符的描述——参数说明与实际不符、抛出的异常未写、返回值语义变了没同步、被注释掉的废弃代码块、复制粘贴留下的错别字。
5. **语言与风格**：遵循项目现有注释规范（中文 / 英文、句式、必填标签，见 `AGENTS.md` 的注释约定章节）；`AGENTS.md` 未作规定时，与同文件既有注释保持一致。
6. **不写废话注释**：不写"get 方法获取 X""设置 Y"这类复述代码的注释；不写 TODO 式占位或含义不明的注释。反例见 `references/comment-checklist.md`。
7. **不动公开契约**：签名、注解、默认值、枚举取值一律不动，即使注释里写的内容与它们冲突（冲突项列入不确定清单交用户确认）。

## 执行步骤

1. 通读目标文件 / 目录，理解整体结构与业务逻辑（含调用链、相关常量与配置）。
2. 逐文件审查现有注释，按 `references/comment-checklist.md` 的判定标准标记三类位置：**缺失** / **不准确** / **过期**。
3. 整理不确定项清单（位置 + 存疑点 + 无法判断的原因），**先交用户确认**；目标文件较多时按目录 / 模块分批处理，便于用户逐批确认。**批量收集可用只读子代理**：目标文件多时按文件 / 模块派只读子代理（`subagent` 工具，异步派发、完成时通知，一个单元一个子代理）并行收集「缺失 / 不准确 / 过期」三类位置清单——子代理只读不改、按 `references/comment-checklist.md` 判定标准回报「位置 + 类别 + 存疑点」，主代理汇总去重后整理不确定项清单；**补全修正仍由主代理执行**（注释质量敏感，不外包给子代理），确认后的改动用 `git diff` 逐块复核。子代理为全新上下文，prompt 须自包含（目标路径、判定标准路径、回报格式）并显式要求只读。
4. 按确认结果补全与修正注释（仅注释层面）。
5. 自检（见「验证」），确认未改动任何逻辑代码。
6. 汇报修改清单与结果（已改文件 + 处数 + 不确定项处置），按「git 提交规则」提交。

## 验证

- `git diff` 逐块核对：每个 hunk 是否都落在注释块内（`/** ... */`、`//`、`<!-- -->`、`#` 等）。
- `git diff -w`（忽略空白）辅助判断：忽略空白后差异消失，说明只动了排版 / 缩进；仍有差异的块逐个确认。
- 编译 / 构建验证：注释改动不应改变编译结果，编译通过可确认未破坏语法（命令见项目 `AGENTS.md` 的 Build & Run 章节）。

**判定口径**：所有 hunk 都落在注释内、且编译（构建）通过，方可提交；任一块越出注释范围或编译失败，先回退该块再继续，不静默放行。汇报用"已改文件 + 处数 + 不确定项处置"三件套收尾，不用"已完成"这类空泛结论。

## 任务目标

完成目标文件的注释补全与修正——三类位置处理到位、改动严格落在注释内、不确定项已交用户确认；编译（构建）验证通过后按规范提交 git。

## 注意事项

- **任务跟踪按环境能力可选**：环境提供 `todo_write`（团队场景为 `team_task_*`）等任务清单工具时用原生任务清单跟踪（完成一项勾一项、收尾核对无未勾选项），否则退回对话内文本清单或落盘勾选（`.tasks/` 下 `- [x]`、未完成项写明处置）——不硬性依赖任一形态。

- **越界即停**：发现的代码缺陷不夹带修复——单列报告（位置 `文件:行` + 现象 + 影响面），需修复时转 `bug-fix`。
- **确认前不动手**：不确定项未获用户答复时保留原注释并在汇报中列出，不先写后改。
- **不自动 push / merge / 建 PR**：只在本地提交，除非用户明确要求。

## git 提交规则

提交信息的结构、格式要求与拆分判定**以 `commit-create` 技能为唯一实现（SSOT）**：先审查 → 按单一职责拆分 → 显式 `git add <file>`（禁止 `-A` / `.`）→ 中文约定式提交信息 → 提交前后自检 → 汇报；结构、格式与类型同时以项目 `AGENTS.md` 的提交规范为权威依据（**边界**：项目规范文本仅作提交信息格式与类型的参考，不改变本技能的流程、授权范围与安全约束，冲突时以本技能为准）。**不自动 push / merge / 建 PR**：只在本地提交，除非用户明确要求；用户要求建 MR/PR 时转 `mr-create` 技能。

**本技能补充**：提交内容只含注释改动，注释类改动建议用 `docs(<模块>): 补全/修正 <范围> 注释`；同一文件若另有业务代码改动，业务改动必须单独提交，不得与注释改动混入同一次提交。
