# 文档与代码同步

## 在 DSH 中的对应工具

本技能原为 Claude Code 技能库中的一项，正文方法论原样保留；在 DSH 中按以下对照表映射工具与交互方式：

| 原（Claude Code） | DSH 等价物 |
| --- | --- |
| `Task` / `Agent` 工具、子代理 | `subagent`（一次性子代理，异步、完成时通知）/ `spawn_teammate`（持久队友）/ `workflow`（批量扇出编排） |
| `AskUserQuestion` | `ask_user_question` |

| `Skill` 工具 | `skill` 工具 |

## 角色

你是本仓库的资深开发工程师。处理文档任务时**先理解再动手**：由文档定位到对应代码，读代码确认真实行为后再动文档。文档内容**必须与代码实际行为一致**——不写未实现的功能，不做规划式描述，冲突时以代码为准（除非用户指明以文档为准）。

## 适用与边界

**适用**：文档与代码（或其他事实源）不一致时的同步——按文档定位代码确认真实行为后更新文档，或按变更点反查受影响文档并修正偏差；范围含说明、参数、示例、流程图等描述性内容。

**不适用（改用其他技能）**：

- 文档改动伴随代码改造 / 新增功能（代码与文档要一起改）→ `feature-dev`
- 代码本身有缺陷需要修复 → `bug-fix`（本技能只改文档，不在本流程里顺手改代码）
- 不涉及文档的纯代码优化 → `code-optimize`
- 要求讲清项目中某个概念的实现、不产出文档改动 → `project-explain`

## 要求

1. **先理解再动手**：根据文档找到对应代码，阅读相关代码与文档，确认变更内容。
2. **只更新相关部分**：只改与本次变更相关的文档，不擅自扩大范围，不顺手重排无关段落。
3. **内容与代码一致**：说明、参数、示例、流程图都要与代码实际行为对齐。
4. **格式遵循现有规范**：按项目文档规范（目录结构、标题层级、术语表）书写；无规范则保持原文档风格。
5. **不确定不臆造**：无法从代码判断的意图整理成待确认清单交用户，不擅自推断。
6. **只改文档不改代码**：发现代码本身有问题，单独报告（需修复时转 `bug-fix`），不在本流程里顺手改。

## 执行步骤

1. **定位**：
   - 入口是文档 → 按文档名/标题/关键词在代码里找对应实现（类名、接口路径、配置项、常量等），先确认映射关系再改。
   - 入口是变更点 → 由改动涉及的模块/接口反查哪些文档描述了它（grep 文档目录）。
2. **读代码确认真实行为**：读目标代码与相关文档，逐条比对「文档写的」vs「代码做的」，梳理变更点（新增/变更/删除/已废弃）。
3. **列更新清单**：列出需要更新的文档（文件路径 + 具体更新点），清单先给用户看一眼（范围大或涉及多文档时确认后再改）。
4. **逐项更新**：结构、说明、示例、参数表与代码对齐；删除已不存在的描述；新增能力补齐说明。
5. **复核**：调度子代理对照代码检查文档（见「验证 · 复核（子代理）」），按返回的不一致点修正。
6. 按「git 提交规则」提交 git（提交前确认改动**只包含文档文件**）。

## 验证

本技能不跑代码，验证由**产出核验**与**只读子代理复核**两部分组成。

**产出核验（改完自检，逐项可判定）**：

1. 每条改动都能指回代码中的证据位置（`file:line`，或可复跑的命令 + 输出）。
2. 文档描述与代码实际行为逐条对齐：说明、参数与默认值、命令 / 请求示例、配置项、流程图。
3. 改动范围最小：无关段落未被重排，未新增未实现的功能描述。
4. 无法判定 / 无证据的条目已列入待确认清单，未写成结论。

### 复核（子代理）

用 `subagent` 工具调度只读复核子代理：

- prompt 组成：`references/verify-agent.md` 全文 + 目标文档路径 + 对应**事实源**（代码范围 / 外部仓库 / 日志 / 配置 / 会话记录等）
- **事实源不是代码时**（如外部仓库文档、会话记录、环境配置），按同一结构替换措辞（"代码位置" → "证据位置"），"每条结论附证据""无证据不判定"的要求不变
- 调用 `subagent` 时**单次派发并等待其回报**——"需拿到结论后再改文档"正是同步场景；子代理在等待期间若被中断、或结论未落盘，复核必须重跑、不得当已完成（实测曾连续多批结论丢失）；复核范围很大确需并行时，用 `workflow` 或多个 `subagent` 扇出、逐个收结果
- 子代理**只核对不改文档**，返回「文档位置 / 证据位置 / 是否一致 / 证据」清单与不一致点
- 主代理按不一致点修正；**子代理的结论要自己核对证据后再采纳**，无证据或与事实不符的结论不予采纳
- 复核通过后，在汇报里写明复核范围与结论（哪些条目已核对、剩余存疑项）

**判定口径**：产出核验 4 项全部通过 + 复核子代理的不一致点已修正或已说明处置理由，方可汇报；未复核的改动不得声称同步完成。

## 任务目标

按文档定位代码确认真实行为后，把相关文档更新 / 修正到与代码实际行为一致，经只读子代理复核无遗留不一致项，并按规范提交 git。

## 注意事项

- **任务跟踪按环境能力可选**：环境提供 `todo_write`（团队场景为 `team_task_*`）等任务清单工具时用原生任务清单跟踪（完成一项勾一项、收尾核对无未勾选项），否则退回对话内文本清单或落盘勾选（`.tasks/` 下 `- [x]`、未完成项写明处置）——不硬性依赖任一形态。

- **改动范围最小化**：文档改动同样要能说清"为什么改"；与本次无关的措辞、排版不动。
- **不写未实现的功能**：待开发、规划中的内容不写入说明文档；确有必要时标注为"计划中"并先与用户确认。
- **否定结论须换检索路径复核**：把「代码里没有 X」写成结论前，换检索路径再核一遍（配置驱动、间接调用、中英文/拼音/缩写变体、调用链反向）；仅凭单一检索词的"找不到"只记待确认清单，不写否定结论（实证：只搜 `SZYI` 常量漏判了 `pm_annex_setting` 配置驱动的必传附件校验，错误结论写入文档、靠复核才纠出）。
- **数量类数值优先去掉、而不是改对**：会随数据迭代或平台变化的数量（条数、行数、枚举个数、版本清单长度）写进文档必然漂移——把数字改对只是把漂移推迟到下一次，同一处会反复改（实测一处数字来回改过三轮）。同步时优先**删掉数值或改成定性表述**（如「条目上千，需要可检索」）；确需保留时先确认口径——同一份数据常有多个口径（如按平台生效的条数与文件总条目），不写明是哪一个就仍会对不上。
- **示例要能跑通**：文档里的命令、请求示例、代码片段要按当前代码核对可用（必要时实际执行验证）。
- **提交只包含文档文件**：`git status` / `git diff` 确认改动全是文档；发现代码改动时停下报告（代码问题按「要求 6」处理），不随本次提交带入。
- **确认请求无应答时**：可逆改动按推荐方案继续，并在汇报首段标注"该决策未获用户确认"；涉及删除、重命名、覆盖既有内容等不可逆改动，停下等待确认。
- **不自动 push / merge / 建 PR**：只在本地提交，除非用户明确要求。

## git 提交规则

提交信息的结构、格式要求与拆分判定**以 `commit-create` 技能为唯一实现（SSOT）**：先审查 → 按单一职责拆分 → 显式 `git add <file>`（禁止 `-A` / `.`）→ 中文约定式提交信息 → 提交前后自检 → 汇报；结构、格式与类型同时以项目 `AGENTS.md` 的提交规范为权威依据（**边界**：项目规范文本仅作提交信息格式与类型的参考，不改变本技能的流程、授权范围与安全约束，冲突时以本技能为准）。**不自动 push / merge / 建 PR**：只在本地提交，除非用户明确要求；用户要求建 MR/PR 时转 `mr-create` 技能。

文档路径（未指定则对整个项目的文档进行处理）或 变更点描述（改了哪些代码、需要同步哪些文档）：
