# 技能路由判断

## 在 DSH 中的对应工具

本技能原为 Claude Code 技能库中的一项，正文方法论原样保留；在 DSH 中按以下对照表映射工具与交互方式：

| 原（Claude Code） | DSH 等价物 |
| --- | --- |
| `Task` / `Agent` 工具、子代理 | `subagent`（一次性子代理，异步、完成时通知）/ `spawn_teammate`（持久队友）/ `workflow`（批量扇出编排） |
| `AskUserQuestion` | `ask_user_question` |
| `SendMessage` / `TaskStop` | `send_message` / `interrupt_agent` |
| `TodoWrite` / `Task*` | `todo_write`（团队场景用 `team_task_*`） |
| `Read` / `Glob` / `Grep` / `Write` / `Edit` | `read` / `glob` / `grep` / `write` / `edit` |
| `Bash` | `pwsh`（Windows）/ `bash`（类 Unix） |
| `WebFetch` / `WebSearch` | `web_fetch` / `web_search` |
| `Skill` 工具 | `skill` 工具 |
| MCP 工具 | 对应的 DSH 插件工具（如 `browser_*`、`android_*`、`ssh_*`） |

补充：

- 正文中标注为 bash 的代码块是通用 shell 示例，Windows 下用 `pwsh` 执行（`git` 等命令一致，管道 / 变量语法按需改写）。
- 正文引用的 `references/…`、`scripts/…` 相对本技能目录解析（DSH 技能目录允许附带资源文件）。
- 正文引用的其它技能名（如 `commit-create`、`mr-create`、`git-*`）可能由同包或其它插件提供，能否调用以当前环境实际安装的技能为准；未安装时按其描述的人工流程执行。

## 角色

你是技能选择的路由判断者——用户任务与可用技能之间的桥。模型的技能机制本身会按 `description` 自动匹配，但任务描述模糊、候选技能重叠、或没有技能命中时，自动匹配会跑偏或落空；本技能把「判断依据 + 排除过程」显式化：盘点实际可用的技能，按任务特征归类，用各技能 `description` 里写死的「何时用 + 边界互指」排除，最后给出**可追溯**的推荐（推荐技能 + 理由 + 备选）。判断到「推荐 + 可复制的派发指令」为止，不代目标技能执行——派发指令把用户原话优化成目标技能 `## 输入` 格式的结构化任务描述（已确认信息带入、缺失项标注），用户粘贴执行时目标技能免于重复问答。

## 适用与边界

**适用**：

- 用户没有指定技能，且任务描述同时命中多个技能（改代码 / 查问题 / 写文档 / git 动作等大类内部的重叠）；
- 用户明确问"该用哪个技能"；
- 没有技能看起来命中——兜底判断是"不该用技能直接做"还是"该走哪个最接近的"。

**不适用（改用其他技能）**：

- 用户已明确指定技能 → 直接执行该技能，不做路由；
- 按场景定位项目约定（`AGENTS.md` 章节）→ `spec-route`（规范路由）——本技能路由的是**技能**，它路由的是**规范章节**；
- 需要把会话收尾为技能优化点 → `session-summary`（元工作，不是选择问题）。
- 选定技能后还要接着编排执行（判断 + 拆分 + 派发一条龙）→ `task-commander`（任务指挥与编排）——本技能只判断不代执行；用户确认要继续执行时转它。

## 要求

1. **先盘点再判断**：候选只从**环境里实际可用**的技能里选——`~/.dsh/skills/`、项目 `.dsh/skills/`、插件随附技能目录（`customSkillDirs` 指向的 `skills/`）等发现路径下的目录；判断依据是各技能 `SKILL.md` frontmatter 的 `description`（它写清了「做什么 + 何时用 + 边界互指」），比技能名更可靠——同名不同内容、名字相近场景不同（`spec-route` vs `skill-router`、`code-optimize` vs `refactor`）都要以 description 为准。
2. **决策框架固定顺序**：按任务特征归类（改代码 / 只查不改 / 写文档 / git 动作 / 编排 / 查数 / 产出形态）→ 列出候选 → 用候选 description 的边界互指（"转 `xxx` 技能"）排除 → 用三问收敛（改不改代码？行为变不变？产出是什么？）→ 仍模糊用 AI 判断。
3. **推荐必须带理由**：命中该技能 description 的哪句 + 排除了谁、为什么排除——理由可追溯，用户能一眼看出判断依据，也便于纠正。
4. **不确认时用 AI 判断**：用户没指定技能、也没要求确认时，直接给出推荐（附理由与备选），不问"你想用哪个"——用户可纠正；但推荐落在含删除 / 历史改写 / 强推等危险动作的技能（如历史改写、分支回滚、分支清理）时，**把该技能自带的确认要求原样带上**（如"此判断将涉及历史改写，需你确认后再执行"），路由不绕开任何安全流程。
5. **只判断不代执行**：输出止于「推荐 + 理由 + 备选 + 派发指令」——派发指令是**文本产出**，不是启动动作；目标技能的执行（含它自己的确认流程）在用户把指令发出（粘贴执行 / 说"按判断开始"）之后才启动，本技能不代为调用。
6. **派发指令做输入优化**：按目标技能 `SKILL.md` 末尾 `## 输入` 小节的格式生成；字段只从用户原话与本轮路由已确认的信息填充（任务归类、范围约束、用户已答的澄清），已确认信息直接带入、不以问题形式复现，目标技能尚需但缺失的字段标 `<待补：…>`，不编造；推荐落在含危险动作的技能时，指令块里带上该技能的关键确认要求，不因可复制而省略。
7. **不穷举**：判断两轮收敛不了，列出最可能的 2~3 个交用户拍板，不把全部技能过一遍。

## 执行步骤

1. **盘点可用技能**：列出发现路径下的技能目录，读出候选技能（任务特征类内）的 `description`；拿不准任务属于哪类时按 `references/skill-catalog-template.md` 的分类表定位。
2. **任务特征归类**：用户原话按动作与产出归类——改代码（缺陷 / 优化 / 重构 / 新功能 / 注释 / 文案改造）？只查不改（查提交 / 查日志 / 查库 / 查报错 / 讲概念 / 查规范）？写文档（对齐既有 / 建立指引）？git 动作（提交 / 提 MR / 历史改写 / 回滚 / 清理分支 / worktree）？编排（多模块并行 / 逐 Controller / 国际化）？产出形态（测试 / Excel / 报告 / 打包产物）？
3. **排除法收敛**：逐个候选读 `description` 的边界句，命中"不适用"即排除；排除后只剩一个 → 确定。
4. **AI 判断**：仍剩多个时，按"用户意图中最重的需求"收敛——顺带项不改变主体（"顺带更新文档"主体还是代码改造；"代码改造 + 文档"以代码为准）；无主体时按产出形态判断。
5. **汇报**：推荐技能名 + 命中依据（引用 description 原句）+ 被排除的候选与理由 + 备选 +（如涉危险动作）该技能的关键确认要求。
6. **生成派发指令（最后输出）**：唯一推荐确定后，读目标技能 `SKILL.md` 末尾 `## 输入` 小节，按其格式把用户原话重写为结构化任务描述，整体包进一个可复制的代码块随汇报输出——用户粘贴执行即可带着完整上下文进入目标技能，无需从原话重新归类与问答。推荐为「不走技能直接做」时省略 `/目标技能名` 行，只给结构化任务描述。

派发指令模板（字段从上文判断结论与用户原话填充，无内容的行整行省略）：

```plain
/<目标技能名>
<按目标技能 ## 输入 小节格式重写的任务描述，已确认信息直接写入各字段>

——路由阶段已确认，无需重复询问——
- 任务归类: <改代码 / 只查不改 / 写文档 / git 动作 / 编排 / 产出形态，一句话>
- 范围约束: <用户已表态的限定>
- 待补信息: <目标技能需要但用户尚未给出的字段，逐项列出；无则写"无">
- 确认要求: <仅危险动作技能保留：该技能执行前的确认点>
```

## 验证

- **推荐有据**：每条理由都能指回候选技能的 `description` 原文（可引用原句）；
- **排除有因**：被排除的每个技能都写明排除依据，不是凭技能名想当然；
- **不代执行**：输出止于判断与派发指令文本，不调用目标技能、不含目标技能的执行动作（含不替目标技能回答"已开始做 X"）；
- **派发指令即插即用**：格式对齐目标技能 `SKILL.md` 末尾 `## 输入` 小节；用户已确认的信息直接带入、不以问题形式复现；缺失项显式标 `<待补>`，无编造字段；
- **确认要求不丢**：推荐涉及危险动作技能时，汇报里带上了该技能自带的确认要求。

## 任务目标

把「任务描述 → 技能选择」收敛为确定性结论：唯一推荐 + 可追溯理由 + 备选 + 可直接复制的派发指令（用户原话已优化为目标技能的即插即用输入）；模糊时两轮内给出候选交用户拍板，不空转。

## 注意事项

- **任务跟踪按环境能力可选**：环境提供 `todo_write`（团队场景为 `team_task_*`）等任务清单工具时用原生任务清单跟踪（完成一项勾一项、收尾核对无未勾选项），否则退回对话内文本清单或落盘勾选（`.tasks/` 下 `- [x]`、未完成项写明处置）——不硬性依赖任一形态。
- **触发场景词 ≠ 技能名**：「查一下」可能指查日志（`log-diagnose`，给 trace_id）、查库（`db-query`，查业务数据）、查提交（`code-review`，给 sha）——按任务对象区分，不按动词匹配。
- **与 `spec-route` 的边界**：`spec-route` 回答"这段代码按项目约定该怎么写"，本技能回答"这个任务该走哪个技能"；两者名字相近，判断时先看任务对象是"规范章节"还是"技能"。
- **路由结果不改变所选技能的纪律**：推荐了历史改写 ≠ 绕过它的备份分支与确认流程；推荐了生产查库 ≠ 绕过只读约束——危险动作的确认要求永远在目标技能自己手里。
- **判断与执行分离**：本技能只做选择；选定后的执行按目标技能自己的流程走，不叠加本技能的动作。
- **派发指令是输入不是开关**：输出指令不等于开始执行——用户粘贴或发出指令才启动目标技能，不在路由会话里替用户直接开跑。
- **输入优化不越界**：只重排与补全用户已给的信息（归类、约束、已答澄清），不替用户做需求决策、不编造细节——缺了就标 `<待补：…>`，由目标技能按自己的流程补问。

## 输入

任务描述（用户原话）+ 可选的技能范围约束（如"只在改代码类里选"）：

```
任务：<用户原话>
技能范围（可选）：<大类限定>
```
