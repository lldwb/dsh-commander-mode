# 项目整体评审检查清单

> **用途**：`code-review` 项目整体评审模式的专属核查参考件——评审对象是全仓横切面（不逐文件深读，看跨模块的一致性与健康度）。
> **读法**：先按 SKILL.md「执行步骤」做结构盘点，再按通用六维（`references/review-checklist.md`，按横切口径裁剪）+ 本清单七个维度逐项核查。
> **分级口径**：与 `review-checklist.md` 一致——严重 / 规范 / 建议。
> **结论口径**：分级报告 + **优先级路线**（按严重度排序，标注每项的整改收益与大致范围）。

## 使用方式

1. **结构盘点**：目录树与规模分布（哪些模块最大 / 最新）、技术栈与构建方式、对外入口清单（接口 / 任务 / 消息）、git 健康度概貌（近期提交规范一致性、异常大文件）。
2. **横切抽样**：每个维度选取 2~3 个代表性切面抽样检索，不追求全量——全量深读交给模块评审模式；抽样发现的问题按影响面外推时在结论中注明「抽样口径」。
3. **分片收集**：按模块 / 维度派只读子代理（一个单元一个子代理），主代理汇总写结论。
4. **结论输出**：分级报告，末尾优先级路线：先严重（缺陷风险 / 安全）、次规范（一致性 / 债务）、后建议。

---

## 一、横切一致性

### 怎么查

- 选 2~3 个横切面（异常处理、日志门面与格式、错误码 / 返回码、配置读取方式、时间 / 金额 / 编码处理），每面在多个模块各抽样一处对照。
- 同一横切面存在两套以上写法时，确认哪套是约定（`AGENTS.md` / 多数派 / 较新模块），偏离者计入问题。

### 命中后怎么写进结论

```text
[规范] <横切面> 在不同模块处理方式不一致
证据：<模块A>`文件:行` 用 <写法1>；<模块B>`文件:行` 用 <写法2>
影响面：维护时容易只改一处、漏另一处（<举一个具体后果>）
建议：统一到 <约定写法>，给出迁移范围估计（<涉及文件数>）
```

---

## 二、规范覆盖度

### 怎么查

- 通读 `AGENTS.md` 的代码约定与提交规范章节（按需按段读取），列出可机械核查的强制条目。
- 每条用 grep 抽样核对落实情况（如禁 `select *`、禁硬编码、注释要求、异常体系）；违反集中的模块单独点名。

---

## 三、技术债务分布

### 怎么查

- `TODO` / `FIXME` / `HACK` / `XXX` 标记：全仓统计密度与集中度（集中在一个模块 = 结构性问题；均匀分布 = 习惯性问题）。
- 废弃 API 存量：`@Deprecated`（或项目等价标记）统计，有无「废弃已久仍被大量引用」的热点。
- 重复模块 / 重复实现：明显的同构代码块、同一能力多套实现并存。

---

## 四、依赖健康

### 怎么查

- 三方依赖清单与版本集中管理核对（版本号是否散落多处、有无互不兼容的重复依赖）。
- 模块间依赖方向抽样：有无循环依赖迹象（A 引 B、B 引 A 的 import 链）、下层模块反向引用上层。

---

## 五、构建与测试健康

### 怎么查

- 构建脚本（`pom.xml` / `package.json` / `Makefile` 等）是否与实际模块结构一致，脚本声明与 README / `AGENTS.md` 的 Build & Run 章节是否相符。
- 测试分布：哪些模块有测试、哪些完全没有；测试是否与被测代码同步演进（抽查近期大改模块有无对应测试改动）。
- 只核对静态形态与可运行性迹象，不替用户实际跑全量构建 / 测试（如需实测转对应验证流程）。

---

## 六、安全与敏感信息

### 怎么查

- 凭据硬编码检索：密码 / token / 连接串赋值的常见形态（grep `password` / `secret` / `token` / `jdbc:` 等模式，按项目语言调整）。
- 敏感信息入库迹象：真实数据样例、内网 IP / 主机名、个人路径出现在源码或配置样例中。
- 命中即**严重**级，建议给出「移到配置 / 环境变量 + 从历史清除」的方向（历史清除属破坏性操作，交用户决策，不在本技能执行）。

---

## 七、文档与代码对齐概貌

### 怎么查

- `README` / `AGENTS.md` 声明的模块结构、命令、约定与仓库实际对照（抽查目录名、命令可执行性、模块清单）。
- 失配项按「文档过时」或「代码偏离约定」区分——修复归属（改文档用 doc-sync，改代码按问题性质转对应技能）在结论中写明。

---

## 项目扩展钩子

本清单是通用基线，**项目按以下方式扩展，不修改本文件**：

- 追加维度或条目：按「维度 → 约定出处 → 怎么查 → 命中后怎么写进结论 → 分级」同构追加。
- 覆盖优先级：追加条目与通用条目冲突时以项目规范为准，结论中注明依据出处。
- 不得放宽：扩展条目只用于提高要求，不得削弱「证据可回溯」「分级明确」「只检查不改代码」三条底线。
