# 提交 / 合并评审检查清单

> **用途**：`code-review` 的逐维核查参考件——**提交评审**（单个修订号）与**合并评审**（分支区间 / merge 提交）模式的核查清单，按「怎么查 → 命中后怎么写进结论」逐维度排查。模块 / 项目整体 / 架构评审用各自的对象清单（`checklist-module.md` / `checklist-project.md` / `checklist-architecture.md`）。
> **读法**：先按 SKILL.md「执行步骤」取数落盘，再按本清单的七个维度逐项核查（合并评审按末尾「合并评审差异点」调整第七维）；清单为通用基线，项目可在末尾「项目扩展钩子」追加条目。
> **分级口径**：
> - **严重**：可能引入缺陷（含语法 / 编译层面的明显错误）、破坏对外契约、造成数据或行为错误、或使提交误导追溯（提交信息与 diff 不符）与泄露敏感信息，须修复后再合入。
> - **规范**：违反项目 `AGENTS.md` / 仓库既有约定，应修正。
> - **建议**：改进方向，可后续处理，不影响合入。

## 使用方式

1. 通读 `summary.txt` 与 `raw.diff`，先给本提交归类（新增 / 修改 / 删除 / 重构 / 配置 / 文档），列出改动清单（`状态 路径`）。
2. 按七个维度逐项核查，命中即记录五要素：**维度 → 分级 → 证据（diff 行 / `文件:行` / 命令输出）→ 影响面 → 建议**。
3. 未命中的维度在结论中显式写"已核查、本提交未涉及"，不得静默跳过。
4. 汇总为二值结论：`存在问题` / `无问题`；存在问题按严重 → 规范 → 建议排序输出。

证据格式统一为 `<仓库相对路径>:<行号>` 或 `diff: <文件> @@ <块>`；行号以当前工作区代码为准，与提交时刻不一致时注明。

## 一、逻辑与边界

### 怎么查

- 先扫**语法与编译层面**的明显错误：括号 / 分号 / 引号是否闭合、方法或变量名是否与定义一致（grep 工具定义处核对）、导入或引用是否缺失、类型是否匹配；这类问题优先于逻辑推演，命中即严重。
- 对 diff 中每一处**新增 / 修改**的判断分支、循环、集合与 Map 取值、字符串处理、数值运算，逐一推演取值域：空值（null / 空串 / 空集合）、零与负数、上下界（含"取不取等号"处是否越界）、重复与并发调用。
- 对每一处**新增的假设**（如"该字段必非空""该集合必非空""该调用必成功"），用 grep 工具（pattern = 被改方法名，path = 源码目录）找出上游调用点，确认调用方传入的值域覆盖该假设；逐个用 read 工具读调用点上下文，判断是否存在破坏假设的调用路径。
- 对每一处**删除 / 挪走**的代码，确认其承担的职责（校验、兜底、清理、日志）已在新位置等价实现——用 read 工具对照改动前后的完整方法体，防止"顺手删掉了一个判断"。
- 异常路径：新增逻辑抛出的异常是否被调用链捕获、是否改变对外返回（原返回兜底值改成抛异常属对外行为变化）。
- 空提交 / 仅合并的提交：核对 `raw.diff` 为空的原因，不要凭 summary 的"无 diff"直接下"无问题"结论。

### 命中后怎么写进结论

模板：

```text
[严重] <文件>:<行> —— <问题一句话>
证据：diff 中新增分支未处理 <X> 为空；调用方 <文件>:<行> 会传入空值
影响面：<触发条件> 下 <报错 / 返回错误结果 / 数据不一致>
建议：<方向，如"补空值分支并返回既有兜底值">
```

分级参考：空值 / 越界 / 异常导致运行期报错或结果错误 = **严重**；边界情形处理不完整但当前调用方不会触发 = **规范**；可读性相关的写法（早返回、卫语句） = **建议**。

## 二、依赖影响面

### 怎么查

- 圈出 diff 中被改动的**对外可观测项**：方法签名与返回类型、常量与枚举取值、配置项 key 与默认值、公共工具方法的行为语义、被 `public` / 导出暴露的字段。
- 对每个符号做全仓检索，逐一核对引用方是否受影响（**不只是能否编译通过**）：
  ```bash
  grep -rn "<符号名>" <源码目录>
  ```
  按项目语言限定类型：`--include="*.java"` / `--include="*.ts"` / `--include="*.py"` 等；项目有代码检索工具时用工具等价检索。
- **字符串 / 配置驱动的引用**要再查一遍：反射调用的类名与方法名字符串、`*.xml` / `*.yaml` / `*.properties` / SQL 映射 / 模板里的符号名，按**字符串字面量**检索。
- 对每个受影响调用点判定：**需同步适配**（说明改哪）/ **不受影响**（写明原因，如"仅取用了未变的返回值"）。
- 交叉核对提交信息与文件清单：若提交声称"重命名 / 收敛调用"，核对该符号是否真的已无旧引用残留（grep 工具计数归零）。

### 命中后怎么写进结论

模板：

```text
[严重] <符号> 的行为/签名变更未覆盖全部引用方
变更点：<文件>:<行>（<变更前 → 变更后>）
受影响调用点：<文件>:<行>、<文件>:<行>（共 N 处，其中 M 处未适配）
建议：<同步适配的位置与方式；或回退该变更>
```

分级参考：调用方会因此报错 / 结果错误 = **严重**；引用方风格上应同步但当前无功能影响 = **规范**；可选的清理项（旧重载、过期注释） = **建议**。

## 三、分层与耦合

### 怎么查

- 先读项目分层约定（`AGENTS.md` 的架构章节；无显式约定时，按既有代码的目录结构与依赖方向归纳），明确"各层是什么、允许谁调用谁"。
- 对本提交新增的**注入、方法调用、import / require**，判断是否新引入以下典型形态：
  - 入口层（对外接口所在的层）直接调用同层组件；
  - 下层（服务 / 数据访问）反向依赖上层；
  - 跨模块直接访问对方内部实现（绕过其对外接口）。
- 用 grep 工具核对被新增依赖的类所处目录与层次，与调用方所处层次比较：
  ```bash
  grep -rn "class <被引用类型>" <源码目录>
  grep -rn "<调用方类型>" <源码目录>
  ```
- **区分"新引入"与"存量"**：只看本提交新增的行；存量同类耦合不在本次结论的严重项内，可作建议。
- 示例不构成通用规则：清单列举的形态只是检索线索，最终按项目分层约定判定。

### 命中后怎么写进结论

模板：

```text
[严重] 本提交新引入分层耦合：<文件>:<行> 直接调用了 <文件>:<行>
耦合形态：入口层直接调用同层组件（违反项目分层约定：<约定出处>）
建议：改由 <应承载该职责的层> 调用，入口层只做参数与结果转换
```

分级参考：跨越分层约束、导致职责与依赖方向被破坏 = **严重**；层内可容忍但不符合项目约定的写法 = **规范**；面向后续解耦的调整 = **建议**。

## 四、契约变更影响面

### 怎么查

- 识别本提交是否改动**对外契约**：接口 / 方法的签名与返回结构、统一响应包装、数据结构字段增删与类型变化（如通用容器收敛为专用对象、`Map` / 字典改为显式结构）、枚举取值与含义、路由 / 路径、序列化字段名与格式、数据访问的查询结果映射。
- 对每个变更点做全仓检索（**必须包含非源码载体**）：
  ```bash
  grep -rn "<字段名|类型名|路径>" <源码目录>
  ```
  覆盖范围：调用方、测试、SQL / XML 映射、配置、模板与前端调用点、接口文档。
- 逐个引用点判定兼容性：
  - 新增字段：是否破坏既有序列化 / 反序列化（严格模式、必填校验）；
  - 删除 / 重命名字段：下游是否仍在读取，是否属于破坏性变更；
  - 返回结构由通用容器改为具体类型：调用方取数方式（按 key 取值、遍历）是否失效；
  - 校验规则收紧（必填、长度、枚举范围）：既有数据 / 调用方是否会因此被拒。
- 破坏性变更必须有配套适配或明确的版本兼容说明；"重构只改了一半"是高频问题，重点核对**未覆盖的既有调用点**。

### 命中后怎么写进结论

模板：

```text
[严重] 对外契约变更未同步覆盖引用方
变更点：<文件>:<行>（<原结构> → <新结构>）
全仓引用清单：<文件>:<行>（已适配）、<文件>:<行>（未适配）
影响面：<未适配点在该变更后的实际表现>
建议：<需同步适配的位置；若属有意破坏性变更，需说明兼容方案>
```

分级参考：未适配的引用点会报错 / 取不到值 / 数据错乱 = **严重**；契约变更本身合规但缺少兼容说明或测试 = **规范**；字段命名与结构可优化 = **建议**。

## 五、废弃 API

### 怎么查

- 对 diff **新增**的每一处 import / 类型引用 / 方法调用 / 注解，检查被引用对象是否被标记废弃：`@Deprecated`、注释中的 `@deprecated` / `deprecated` 标记、项目自有的废弃标记或清单（按项目语言与约定替换）。
  ```bash
  grep -rn -B2 "<被引用符号>" <源码目录>   # 看定义处上方是否有废弃标记
  ```
- 区分**新引入**与**存量**：只对本提交新增的行计问题；判断依据是 `git show <sha> -- <文件>` 中出现 `+` 的行。
- 若被引用对象有明确替代实现，核对本提交是否本可直接用替代实现。
- 顺带记录本提交是否**清理了存量废弃引用**（清理是加分项，不是必须项，不得因此判问题）。

### 命中后怎么写进结论

模板：

```text
[规范] <文件>:<行> 新代码引用废弃 API <符号>
证据：<符号> 定义处 <文件>:<行> 已标注 <废弃标记>，替代实现为 <符号>
建议：改用替代实现；若因兼容无法替换，请在提交信息或注释中说明原因
```

分级参考：新引入废弃引用 = **规范**；该废弃 API 已声明即将移除且存在直接替代 = 升级为 **严重**；存量废弃引用未顺带清理 = **建议**。

## 六、风格与仓库约定一致性

### 怎么查

- 读 `AGENTS.md` 的代码约定章节（按需按段读取，不全文加载），列出与本提交改动相关的约定条目。
- 抽查 diff 中的常见约定点：日志写法与门面、常量定义与使用位置、魔法值、数值 / 金额计算方式、SQL 写法（`select *`、拼接）、命名与包 / 目录结构、异常处理与错误码、注释与文档。
- 与**本文件周边同类代码**（同目录、同层、既有实现）对照，判断是否与既有风格一致——一致性优先于个人偏好。
  ```bash
  grep -rn "<同类写法样例>" <同目录或同层目录>
  ```
- 注意区分"项目约定"与"提交者的个人习惯"：无约定出处时只能按「建议」评级，并在结论中写明"无明确约定出处"。

### 命中后怎么写进结论

模板：

```text
[规范] <文件>:<行> 与项目约定不一致：<具体差异>
约定出处：<`AGENTS.md` 章节 / 文件:行 的既有同类实现>
建议：<对齐方式>
```

分级参考：违反有明确出处的强制约定 = **规范**；与周边既有风格不一致但无强制约定 = **建议**；影响可维护性的结构性问题（重复逻辑、超长方法） = **建议**（若同时构成缺陷风险，按维度一评「严重」）。

## 七、提交信息规范

### 怎么查

- 读 `summary.txt` 的「提交信息」原文，核对：
  - 是否遵循约定式提交：`type(scope): 标题`，type 是否为项目允许的常规类别（`feat` / `fix` / `refactor` / `docs` / `test` / `chore` / `perf` 等），scope 是否指向真实改动范围；
  - 标题是否用中文、一句话说清"改了什么"；
  - 正文是否存在且说明了"为什么"，多行正文是否分点；
  - **标题与正文之间是否有空行**——缺空行会让正文并进标题。
- 用 git 交叉核对标题与正文是否真的分离（`%b` 为空即已被并进标题）：
  ```bash
  git log -1 --format='%s' <sha>
  git log -1 --format='%b' <sha>
  ```
- 核对提交信息与 diff **是否相符**：改了 A 却写 B、宣称"重构"实际含行为变更、宣称"修复 X"却未见对应改动，均属误导。
- 核对是否混入无关改动（一次提交里夹带格式化、无关文件、过程产物）。
- 核对是否携带敏感信息（凭据 / token / 内网地址 / 真实数据样例 / 本机绝对路径）与仓库禁止的尾注 / 署名。
- 抽查仓库既有风格做一致性对照：
  ```bash
  git log --oneline -20
  ```

#### 发版提交专项核查（被审提交为 `chore(release): 发布 vX.Y.Z` 时）

- **类型与标题**：是否为 `chore(release): 发布 vX.Y.Z`；其余类型（`docs` / `chore` / `feat` 等）承载版本号即不合规（发版内容只允许落在 `chore(release)` 提交）。
- **改动范围**：是否只动 `CHANGELOG.md` 顶部新条目、`marketplace.json` 的 `version` 与 README / PLUGIN_README 的呈现层——**不得夹带功能改动**，也不得夹带 `marketplace.json` 的 `skills` 数组（新增 / 改名 / 删除技能的分发同步应在前置功能提交里完成）。
- **位置**：是否位于该版本**最后一个功能提交之后**——其后不应再出现同版本的功能提交（发版即版本定案）。
- **条目不可变**：是否只**新增自己版本的顶部条目**、未修改任何历史条目（含补记、修订说明——发版条目一经创建不得在后续提交改动，补充内容只能记入下一个版本的条目）。
- **版本号对齐**：`CHANGELOG.md` 顶部版本、`marketplace.json` 的 `version`、注解 tag `vX.Y.Z` 三者一致。
- **时间语义**：author / committer 时间是否合理——历史重写（rebase / filter-branch）后的提交时间应恢复原提交时间，不应是重写当天的当前时间（除非原提交本就如此）。

### 命中后怎么写进结论

模板：

```text
[规范] 提交信息不符合 <约定>：<原文片段>
证据：git log -1 --format='%b' <sha> 输出为空（正文并进标题）；或标注为 refactor 但 diff 含行为变更
建议：<改写方向；如属夹带无关改动，建议拆分提交>
```

分级参考：提交信息与 diff 不符、夹带敏感信息 = **严重**（误导评审与追溯）；结构不合约定式提交、标题与正文未分离、正文缺失 = **规范**；措辞可更精确 = **建议**。

## 合并评审差异点（评审对象为分支区间 / merge 提交时）

合并评审的取数是**聚合差异**（`--range <base>...<head>` 的 merge-base diff，或 merge 提交的第一父级 diff），维度核查方式按以下差异点调整：

- **一至六维按聚合 diff 核查**：同一维度把区间内所有提交的改动合并来看（如「依赖影响面」对聚合 diff 中被改动的符号全仓检索），中间态不单独核查。
- **第七维替换为「提交序列规范性」**：
  - 区间内每个提交（`summary.txt` 的提交序列清单）：类型与标题合规、描述与实际改动相符、无夹带无关改动；提交多时优先抽查信息可疑（类型 / 范围与文件清单明显不符）的提交。
  - 提交拆分合理性：同一逻辑变更被拆散在多个提交（改了一半的中间态）或功能与格式化混杂在一个提交，按第七维同口径分级。
  - merge 提交信息与合入范围相符（合入了哪些分支 / 需求，信息可追溯）。
- **重复改动的呈现**：同一文件在区间内多次修改时，聚合 diff 只呈现最终形态——中间引入又被后续提交修复的问题不进结论，但可在「建议」中提示提交拆分改进。
- **区间核对**：确认 base 选取正确（三点 diff 是 merge-base 语义）；区间为空（无差异提交 / 无 diff）时先核实源分支是否已合入、base 是否选错，不得直接判「无问题」。

## 项目扩展钩子

本清单是通用基线，**项目按以下方式扩展，不修改本文件**（避免与上游更新冲突）：

- **追加条目**：`AGENTS.md` 中已有明确章节的规则，按「维度 → 约定出处 → 怎么查 → 命中后怎么写进结论 → 分级」追加到对应维度下；同一维度内编号顺延。
- **新增维度**：项目有本清单未覆盖的强制评审维度（如性能、安全、兼容性、国际化、数据迁移），按本清单同构新增一节（`## 八、<维度名>`），保持"怎么查 / 命中后怎么写进结论 / 分级参考"三段结构。
- **覆盖优先级**：追加条目与通用条目冲突时，**以项目规范为准**，并在结论中注明依据出处（`文件:行` 或 `AGENTS.md` 章节）。
- **不得放宽**：扩展条目只用于提高要求，不得削弱「证据可回溯」「结论二值」「只检查不改代码」三条底线。
