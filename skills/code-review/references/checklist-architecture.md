# 架构评审检查清单

> **用途**：`code-review` 架构评审模式的专属核查参考件——评审对象是全仓的**结构与依赖**（不看单行代码质量，看分层、边界、方向与演进能力）。
> **读法**：先按 SKILL.md「执行步骤」做结构盘点与依赖方向检索，再按通用六维（`references/review-checklist.md`，仅取与结构相关口径）+ 本清单六个维度核查。
> **分级口径**：严重（结构缺陷已在 / 即将造成缺陷或阻塞演进）/ 规范（违反已声明的架构约定）/ 建议（演进方向）。
> **结论口径**：分级报告 + 演进建议——每条建议标注「影响面 + 改造代价量级（小 / 中 / 大）」，供排期决策。

## 使用方式

1. **结构盘点**：从目录结构归纳层次（入口层 / 服务层 / 数据层 / 公共层…），列出模块清单与各自职责一句话；盘点对外契约面（接口 / 消息 / 定时任务 / CLI）。
2. **依赖方向检索**：对代表性模块抽样检索 import / 调用方向，构建「谁依赖谁」的近似矩阵（不必全量，主干模块必查）。
3. **分片收集**：按模块派只读子代理（一个单元一个子代理）收集依赖关系与结构证据，主代理汇总画结构结论。
4. **结论输出**：分级报告；演进建议单独一节，每条含「现状 → 目标形态 → 改造代价量级 → 风险」。

---

## 一、分层清晰度

### 怎么查

- 层次能否从目录结构清晰归纳（能一句话说清每层职责）？出现「说不清属于哪层」的目录 / 模块即信号。
- 各层职责与项目 `AGENTS.md` / 既有设计文档声明的架构对照——声明与实际不符时按实际记录，失配本身计入问题。
- 同层职责是否对等（服务层里混着纯工具类、数据层里混着业务判断等错位形态）。

### 命中后怎么写进结论

```text
[规范] <层/模块> 的职责定位模糊
证据：<目录>`文件:行` 同时包含 <职责A> 与 <职责B>；声明架构为 <X>（出处），实际为 <Y>
影响面：新代码落点不明确，层间依赖随时间发散
建议：<层次归位方向>
```

---

## 二、依赖方向

### 怎么查

- 抽样检索主干模块的 import / 调用：下层反向依赖上层、同层横向直达、绕过服务层直达数据访问层。
- 循环依赖迹象：A → B → A 的引用链（按模块 / 包级别核对，文件级误报可忽略）。
- 对公共层（工具 / 基础设施）反向被业务层污染的形态（公共层 import 业务模块）重点查——这是依赖发散的源头。

---

## 三、模块边界与内聚

### 怎么查

- 模块边界是否与业务边界对齐：一个业务变更要跨几个模块？（跨模块越多，边界越模糊）
- 跨模块访问对方内部实现（绕过其对外接口）的调用点检索——这是边界失效的直接证据。
- 「万能模块」（被几乎所有模块依赖、内含多域职责）与「孤儿模块」（无人依赖、职责与现状脱节）专项核对。

---

## 四、契约与扩展点设计

### 怎么查

- 对外契约（接口 / 返回结构）的稳定性：契约承载对象是否明确（前端？第三方？内部模块？）、有无版本化或兼容说明机制。
- 扩展点：新增一类业务 / 一种实现时的扩展方式是什么？（配置驱动 / 策略接口 / 继承）没有扩展点、靠 if-else 枚举业务类型增长的形态计入问题，并评估当前分支数量（分支数即债务余额）。
- 扩展点被绕过的形态：存在策略接口但调用方仍直接枚举实现类。

---

## 五、演进风险

### 怎么查

- 单点与难替换组件：强绑定三方服务 / 闭源二方库、无抽象隔离的直接调用点（替换 / 降级时的爆炸半径）。
- 与业务增长不匹配的结构：数据量 / 模块数增长后必然失效的设计（无分页的全量查询结构、单文件承载全部配置等）。
- 近期改动热区与结构的矛盾：改动最频繁的模块恰是结构最僵化的部分时，标记为高优先级演进对象。

---

## 六、架构约定落实

### 怎么查

- `AGENTS.md` 架构章节 / README / 设计文档中声明的架构约定逐条核对（分层规则、依赖规则、命名与目录规则）。
- 约定无落实证据（声明了但代码从未遵守）与约定被局部违反（多数遵守、个别绕过）区分记录——前者是约定失效，后者是违规点。

---

## 项目扩展钩子

本清单是通用基线，**项目按以下方式扩展，不修改本文件**：

- 追加维度或条目：按「维度 → 约定出处 → 怎么查 → 命中后怎么写进结论 → 分级」同构追加。
- 覆盖优先级：追加条目与通用条目冲突时以项目规范为准，结论中注明依据出处。
- 不得放宽：扩展条目只用于提高要求，不得削弱「证据可回溯」「分级明确」「只检查不改代码」三条底线。
