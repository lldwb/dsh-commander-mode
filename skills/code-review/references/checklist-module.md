# 模块评审检查清单

> **用途**：`code-review` 模块评审模式的专属核查参考件——评审对象是指定模块 / 目录 / 包（一个或多个）。
> **读法**：先按 SKILL.md「执行步骤」盘点模块（文件结构、规模、近期改动概貌），再按通用六维（`references/review-checklist.md` 一至六维，适用性按本模块实际裁剪）+ 本清单的专属维度逐项核查。
> **分级口径**：与 `review-checklist.md` 一致——严重（可能引入缺陷 / 破坏对外契约）/ 规范（违反仓库约定）/ 建议（改进方向）。
> **结论口径**：分级报告（每条发现含证据与影响面），报告末尾给按严重度排序的优先级清单。

## 使用方式

1. **盘点取数**：glob 清点模块文件结构与规模（文件数、行数分布），`git log --oneline -20 -- <模块路径>` 看近期改动概貌（改动集中的文件重点看），grep 盘点模块对外暴露的接口 / 类 / 常量。
2. **通用六维**：按 `references/review-checklist.md` 执行——模块评审无单一 diff，六维的核查对象是模块整体（如「依赖影响面」核查模块对外接口的全部调用方、「废弃 API」核查模块内存量与新增引用）。
3. **专属维度**：按本清单六个维度逐项核查。
4. **结论输出**：分级报告，每条记录「维度 → 分级 → 证据（`文件:行`）→ 影响面 → 建议」；末尾优先级清单按严重 → 规范 → 建议排序。

模块文件多时**派只读子代理分片**：按子目录 / 分层切分，一个单元一个子代理（不合并单元），子代理只读不改、回报「发现 + `file:line` + 影响」清单，主代理复核证据后汇总——不把全模块塞进主代理上下文逐文件深读。

## 一、模块内聚与职责

### 怎么查

- 从目录结构与命名归纳模块的核心职责（一个模块 = 一个职责域），列出与该职责无关却塞进来的文件 / 类。
- 对「杂糅」信号排查：一个类同时承担多种不相关职责（如同时做解析、存储、通知）、文件名与内容不符、超长文件 / 超长类集中地。
- 与项目分层约定（`AGENTS.md` 架构章节 / 既有结构）对照，确认模块的层次定位与职责边界。

### 命中后怎么写进结论

```text
[规范] <模块路径>:<文件> 职责杂糅：<实际承担的职责列表>
证据：该文件同时实现 <职责A> 与 <职责B>（`文件:行` 两处代码）
影响面：改动互相关联、测试与复用困难
建议：<按职责拆分的方向>
```

---

## 二、对外接口稳定性

### 怎么查

- 盘点模块对外暴露面：`public` / 导出的类、方法、常量、配置项；区分「模块内部使用」与「被外部调用」。
- 对每个对外符号用 grep 找出外部调用方，核对：签名与语义是否稳定、命名是否一致（同类能力命名风格统一）、有无重复暴露（同一能力两个入口）。
- 检查应收敛却未收敛的接口：参数随意（裸 Map / 大量布尔参数）、返回结构含糊（裸容器）。

---

## 三、重复与同构

### 怎么查

- 对模块内高频片段（相似的循环 / 校验 / 拼装逻辑）抽样检索，确认是否存在复制粘贴式重复。
- 同构文件（同一模板生成的多个类）核对差异点是否只是数据、逻辑是否一致——不一致的同构文件是缺陷高发地。
- 与项目其他模块对照，确认模块没有重复实现既有公共能力（公共工具 / 已有组件）。

---

## 四、模块内分层符合度

### 怎么查

- 按项目分层约定核对模块内部层次：入口 → 服务 → 数据访问的调用方向是否单向、有无反向依赖 / 跨层直达。
- 对模块内 import / 注入关系抽样检索，确认没有绕过本模块服务层直达数据层的调用。

---

## 五、测试与可验证性

### 怎么查

- 盘点模块的测试文件与被测代码的对应关系，列出核心逻辑无测试覆盖的部分（覆盖形态即可，不苛求行覆盖率数字）。
- 检查可测性障碍：静态方法 / 私有方法中埋核心逻辑、难以注入的外部依赖、测试必须依赖真实环境。

---

## 六、缺陷风险深读抽查

### 怎么查

- 抽样深读（不逐文件全读）：**入口文件**（对外入口、初始化）、**核心算法 / 业务规则**所在文件、**边界处理**集中地（参数校验、异常处理、空值处理）。
- 深读时按 `review-checklist.md` 第一维（逻辑与边界）的口径推演取值域与调用路径——模块级缺陷风险主要藏在这三类位置。
- 近期改动集中（git log 高频）的文件优先纳入抽查。

---

## 项目扩展钩子

本清单是通用基线，**项目按以下方式扩展，不修改本文件**：

- 追加维度或条目：按「维度 → 约定出处 → 怎么查 → 命中后怎么写进结论 → 分级」同构追加。
- 覆盖优先级：追加条目与通用条目冲突时以项目规范为准，结论中注明依据出处。
- 不得放宽：扩展条目只用于提高要求，不得削弱「证据可回溯」「分级明确」「只检查不改代码」三条底线。
