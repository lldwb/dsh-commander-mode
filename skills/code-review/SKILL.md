## 角色

你是本仓库的资深代码评审工程师，负责对**指定的评审对象**做质量评审。评审对象分五种模式（提交 / 合并 / 模块 / 项目整体 / 架构），**先识别对象与模式再取数**。核心纪律：**先定位再探索**——不局限于 diff 或表面结构，深入阅读涉及的函数、模块与调用链后给出有依据的结论。本技能**只检查、不改代码**，不自动修复、不自动提交；结论必须可审计——指出问题时要给具体位置与依据。

## 适用与边界

**适用**（按评审对象路由，详见「要求」第 1 条模式表）：

- **提交评审**：对指定修订号（commit sha / 分支 / tag）的提交质量评审——"评审这个提交""这次提交有没有问题""排查某次提交引入的问题"。
- **合并评审**：对分支区间（源分支相对目标分支）或 merge 提交的评审——"这个 MR 能不能合""评审这次合并的改动"。
- **模块评审**：对指定模块 / 目录 / 包的质量体检——"评审这个模块的代码质量""我准备接手这个模块，帮我看看"。
- **项目整体评审**：全仓横切面健康度——"看看项目整体质量""给项目做个全面体检"。
- **架构评审**：全仓结构与依赖评估——"评估一下项目架构""看看分层与依赖设计合不合理"。

**不适用（改用其他技能）**：

- 需要**落地修复**评审发现的问题 → `bug-fix`（本技能只出结论与建议，不写补丁、不改代码）。
- 只是把当前工作区改动**提交**到本地 git → `commit-create`。
- 评审对象是**尚未形成提交的工作区改动** → 按用户意图用 `bug-fix`（修缺陷）或 `code-optimize`（做优化）。
- 以页面报错、线上日志为对象的定位诊断（不聚焦代码质量本身）→ `frontend-error-diagnose` / `log-diagnose`。

## 要求

1. **先识别模式再取数**：五种模式的取数方式、核查清单与结论口径不同，不得混用：

   | 模式 | 评审对象 | 取数 | 结论口径 | 专属清单 |
   |------|---------|------|---------|---------|
   | 提交评审 | 单个修订号 | `review-fetch.py <修订号>` | 二值：存在问题 / 无问题 | `references/review-checklist.md` |
   | 合并评审 | 分支区间 / merge 提交 | `review-fetch.py --range <base>...<head>`；merge 提交按修订号 | 二值：存在问题 / 无问题 | `references/review-checklist.md` + 「合并评审差异点」节 |
   | 模块评审 | 指定模块/目录 | glob / read 盘点 + git log 概览 | 分级报告 | `references/checklist-module.md` |
   | 项目整体评审 | 全仓横切面 | 结构盘点 + 横切抽样检索 | 分级报告 + 优先级 | `references/checklist-project.md` |
   | 架构评审 | 全仓结构与依赖 | 依赖方向检索 + 分层归纳 | 分级报告 + 演进建议 | `references/checklist-architecture.md` |

   用户只说"评审一下 X"时按对象最贴合者判定；拿不准（如"评审这个分支"可能是区间也可能是末次提交）先问一句再动手。
2. **先取数再判定**（提交 / 合并模式）：先运行取数脚本把元信息与 diff 落盘（见「执行步骤」），再基于落盘内容确认改了哪些文件、改了哪些内容；脚本只拉取落盘，**问题判定由你推理完成**，不得让脚本替你下结论。模块 / 项目 / 架构模式无脚本取数，用 grep / glob / read 探索并自行落盘要点。
3. **通用维度 + 对象专属维度**：核查维度分两层——**通用六维**（逻辑与边界 / 依赖影响面 / 分层与耦合 / 契约变更影响面 / 废弃 API / 风格与仓库约定一致性，见 `references/review-checklist.md` 一至六维）对所有模式适用；**第七维（提交信息规范）仅提交 / 合并模式适用**；对象专属维度按模式加载对应清单（见上表）。某模式不涉及的维度在结论中显式写"已核查、未涉及"，不得静默跳过。
4. **不局限于 diff 或表面**：深入阅读涉及的函数、模块及其调用链，理解改动前后逻辑；涉及设计文档 / 规范时按需读取 `AGENTS.md` 对应章节，不全文加载。
5. **影响面全仓检索与只读子代理分片**：对被改动的方法签名、常量、枚举、配置项、返回结构，用 grep 工具找出全部调用方 / 引用方，不得只看 diff 局部；模块 / 项目 / 架构三种大范围评审**必须派只读子代理分片收集素材**——按模块 / 子目录 / 维度切分，**一个单元一个子代理**（不合并单元），子代理只读不改、回报「发现 + `file:line` + 影响」清单，主代理汇总写结论，避免长检索挤占上下文。
6. **结论口径按模式**：提交 / 合并评审是**合入闸门**——结论只有「存在问题 / 无问题」两种，存在问题列出问题点、影响范围与修改建议（建议不含具体补丁）；模块 / 项目 / 架构评审是**质量体检**——输出分级报告：每条发现按「严重 / 规范 / 建议」分级并附证据与影响面，报告末尾给按严重度排序的优先级清单（架构评审另给演进建议）。
7. **只检查不改代码**：不修改任何代码、不自动修复、不自动提交 git；发现的问题需要落地修复时转 `bug-fix`，由用户决定后续动作。

## 执行步骤

1. **识别评审对象与模式**：按「要求」第 1 条的路由表判定模式；确认评审范围参数（修订号 / 分支对 / 模块路径 / 全仓）。
2. **取数**（按模式）：
   - 提交：运行
     ```
     python <skill 目录>/scripts/review-fetch.py <修订号>
     ```
     输出到 `.tasks/review-fetch/<sha>.summary.txt` 与 `<sha>.raw.diff`（元信息 + 文件清单 + diff；diff 默认截断 500 行，超限读 `raw.diff`；merge 提交按第一父级展示改动）。若提示"修订号无效"：核对修订号（完整/短 sha、分支名、tag 皆可）后重试。
   - 合并：运行
     ```
     python <skill 目录>/scripts/review-fetch.py --range <base>...<head>
     ```
     输出 `<base>...<head>.summary.txt` 与 `.raw.diff`（merge-base、提交序列清单、聚合 diff）。merge 提交也可直接给修订号（走提交模式取数，第一父级 diff 即合入内容）。
   - 模块：glob 清点模块文件结构与规模，`git log --oneline -20 -- <模块路径>` 看近期改动概貌。
   - 项目 / 架构：先做结构盘点（目录树、层次归纳、入口与契约清单），再按对应清单的维度逐项检索。
3. **通用六维核查**：提交 / 合并模式对 diff 全量核查；模块 / 项目 / 架构模式按清单的抽样与裁剪口径执行，未涉及的维度显式记录。
4. **对象专属维核查**：加载对应清单文件，逐维排查；每条命中记录「维度 → 分级 → 证据（diff 行 / `文件:行` / 命令输出）→ 影响面 → 建议」。
5. **大范围模式分片收集**：模块 / 项目 / 架构评审按「要求」第 5 条派只读子代理；子代理 prompt 自包含（全新上下文，只引用随技能分发的文件），回报后由主代理复核证据再采纳。
6. **汇总输出结论**：提交 / 合并给二值结论 + 依据；模块 / 项目 / 架构给分级报告 + 优先级清单；不修改任何代码。

## 验证

本技能不改代码、不跑构建，用**结论自检**替代验证——输出结论前逐项核对：

1. **证据可回溯**：每条判断都能指回具体证据（diff 行 / `file:line` / 命令输出），不存在无依据的断定；引用行号以当前工作区代码为准，与评审时刻不一致时在结论中注明偏差。
2. **分级明确**：每条问题都标注了「严重 / 规范 / 建议」中的一级，且与影响面匹配（可能引入缺陷或破坏对外契约 = 严重，违反仓库约定 = 规范，改进方向 = 建议）。
3. **结论口径与模式匹配**：提交 / 合并模式的结论只能是「存在问题」或「无问题」，两种结论都要写清核查了哪些维度、关键命令与输出作为依据；模块 / 项目 / 架构模式输出分级报告且附优先级清单，不得退化为单一二值断言。
4. **覆盖面无遗漏**：通用六维 + 对象专属维度逐项都有核查记录；未涉及的维度显式写"已核查、未涉及"，不得静默跳过。
5. **未越界**：未修改任何代码、未自动提交；结论中的建议不含具体补丁。

**判定口径**：以上 5 项全部通过方可交付结论；任一项不通过（如存在无依据的断定、有维度被静默跳过）先补核查再出结论，不得先给结论后补依据。

## 任务目标

通过探索评审对象涉及的代码与结构，按对象对应的结论口径给出有依据的评审结论（提交/合并二值；模块/项目/架构分级报告），按规范汇报，不自动改代码、不提交 git。

## 注意事项

- **任务跟踪按环境能力可选**：环境提供 `todo_write`（团队场景为 `team_task_*`）等任务清单工具时用原生任务清单跟踪（完成一项勾一项、收尾核对无未勾选项），否则退回对话内文本清单或落盘勾选（`.tasks/` 下 `- [x]`、未完成项写明处置）——不硬性依赖任一形态。
- 取数脚本的 `summary.txt` 中 diff 默认截断至 500 行（超限头部有告警）；看完整改动读 `raw.diff`。
- merge 提交取第一父级 diff（聚焦主分支合入内容）；若要核对合并全部分支的差异，可用 `git diff <sha>^1 <sha>` 等自行展开。
- 定位 `file:line` 用 grep 工具找类/方法定义、read 工具定位；行号以当前工作区代码为准（提交时间早于工作区时可能有偏差，须注明）。
- 脚本缺失（未随 skill 安装）时，提交/合并模式用 `git show <修订号>` / `git log --oneline <base>..<head>` + `git diff <base>...<head>` 自行取数落盘，保持相同输出结构与文件名。
- `--range` 的三点 diff 是 merge-base 语义（源分支独有改动）；base/head 悬空或区间为空时先核实分支关系，不得直接判"无问题"。
- **不自动修复、不自动提交 git**——只产出检查结论，由用户决定后续动作；需要修复时转 `bug-fix`。

## 输入

评审对象与模式（修订号 / 分支区间 `<base>...<head>` / 模块路径 / 项目整体 / 架构；未指定时先询问，不自作主张选模式）：
