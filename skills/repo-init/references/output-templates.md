# 产出物模板与写作清单

本文件是 `repo-init` 的参考件：`AGENTS.md` 章节骨架、兼容 Claude Code 时的 `CLAUDE.md` 指向模板、合并既有内容的做法。骨架是**建议顺序**，按被初始化仓库的实际情况增删小节；没有内容的小节直接删掉，不写空壳。

## 一、AGENTS.md 骨架

````markdown
# AGENTS.md

本文件是在本仓库工作的 agent（DSH 及其它 agent）的指引；**本文件为唯一权威源**。仓库若需兼容 Claude Code，根目录 `CLAUDE.md` 只作指向。

## 仓库定位

这个仓库是做什么的、产出物是什么、由此推出哪些硬性约束（例：若是供其他项目复用的仓库，则正文须通用化、参数化）。
只写"决定了怎么写代码"的那部分定位，不写公司介绍。

## 常用命令

构建 / 测试 / 运行 / 打包 / 代码检查的实际命令，含"怎么只跑一个测试"。
无构建、无测试、无 CI 的仓库就如实写明，并给出替代的验证方式（手工脚本、`--dry-run`、`--help` 等）——**这句"没有"比编造一套命令有用**。

```bash
<构建命令>
<只跑单个测试的命令>
```

## 架构

2–4 条"读多个文件才能拼出来"的高层结论，每条一句话讲清是什么 + 为什么这样。
典型形态：分层与唯一入口、分发/部署路径、数据流向、外部依赖的边界。

### 跨模块共用约定（改代码时别破坏）

- 配置加载顺序、产物落盘规则、公共工具函数/共享模块、安全判定的唯一实现……
- 每条标注**改动时要同步什么**（例如"安全判定有两份实现，改动须同步"）。

## 已知坑

- 与直觉相反的既有行为、被忽略规则误命中的必需文件、本地存在但未入库的文件、会静默失败的兜底逻辑。
- 每条写清：现象 → 影响 → 当下的绕行方式。

## <仓库既有的其它规范>

（提交规范、编码约定等既有内容——原样保留，见「三、合并既有内容」）

### 提交规范小节里的可选条款：分支命名约定

规范条款是给项目的建议、不是读仓库读出来的事实，动笔前按 SKILL.md「要求 10」与用户对齐；对齐后示例：

```markdown
- **分支命名规范**：新建的本地开发分支按 `<type>/<内容>-<修改者>-<MMDD>` 命名，如 `fix/<模块>-<用户名>-<MMDD>`——`type` 限定与提交类型一致的词表（feat / fix / chore / docs / refactor 等），`内容` 用小写连字符短语概括改动主题，`修改者` 用 git 用户名，`时间` 用两位月两位日（MMDD）。`main` 分支与 `backup/` 类历史 / 备份分支不受此约束。
```

单主干、无并行分支协作的仓库可不写；存量分支默认只规范不动存量（不重命名既有分支）。
````

### 骨架里的反例（不要写）

| 不要写 | 原因 |
|---|---|
| "常见开发任务""开发小贴士""支持与文档"等章节 | 不编造：仓库里没写就别造 |
| "提供友好的错误提示""不要提交密钥""为新功能写测试" | 通用开发实践，任何仓库都成立，等于没写 |
| 逐目录的文件树、每个组件一句介绍 | 读一次 `ls` / `git ls-files` 就知道，不占指引篇幅 |
| 与代码不符的"应该这样" | 指引的唯一价值是准确；不确定就核实或删掉 |

## 二、CLAUDE.md 模板（仅兼容 Claude Code 时需要）

DSH 不需要 `CLAUDE.md`；仓库若要兼容 Claude Code，再按此模板写一份，标准英文前缀必须原样保留，其余只写指向、**不写正文**。

```markdown
# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

本仓库的全部工作指引——<列出 AGENTS.md 里的主要章节>——见 **[AGENTS.md](AGENTS.md)**。

以 `AGENTS.md` 为唯一权威源，本文件仅作指向，不重复其内容；两者冲突时以 `AGENTS.md` 为准。
```

既有 `CLAUDE.md` 若含实质指引内容：先把它并入 `AGENTS.md` 对应小节，**再**把 `CLAUDE.md` 收敛成上面的指向形态（顺序不能反，否则内容会丢）。

## 三、合并既有内容

`AGENTS.md` 已存在时：

1. 逐节读一遍既有内容，判断每节属于"保留"还是"合并"。
2. **保留**：只降层级，文本一字不改（`# 提交规范` → `## 提交规范`，其下 `## X` → `### X`）。降级前确认仓库内没有按锚点链接引用这些小节；有引用就不动层级，改为追加新章节。
3. **合并**：新正文与原小节讲同一件事时，合并成一节（选信息量大的那份为底，吸收另一份的独有内容），不要留两处近似表述——同一规则写两遍，迟早漂移。
4. 新正文放在既有内容**之前**（先"这个仓库是什么"，再"这个仓库的特殊规范"）。
5. 落盘后用 `git diff -- AGENTS.md` 复核：改动应只包含新增行与层级行，既有文本零改动。

## 四、动笔前的核验清单

| 要写的内容 | 动笔前怎么核实 |
|---|---|
| 构建 / 测试命令 | 读构建清单（`pom.xml` / `package.json` / `Makefile` …）；仓库里已有脚本就照抄脚本用法 |
| 哪些文件真正入库 | `git ls-files`（本地存在 ≠ 已入库，被 `.gitignore` 命中的必需文件是常见坑） |
| 某模块被谁共用 | grep 工具（pattern 匹配 import / require 该模块的语句，path 为源码根）全仓库搜引用，别只看一处 |
| "唯一入口""只改一处"类断言 | 必须有 grep / `git` 佐证；佐证不足就弱化表述 |
| 文件是否会被忽略 | `git check-ignore -v <路径>` |
| 提交信息风格 | `git log -n 10 --pretty=medium`（**不要用 `%s%n%b`**——那种格式看不出标题与正文之间的空行，抄进指引会让示例失真） |
| 既有 AI 规则要点 | 读 `.cursor/rules/`、`.cursorrules`、`.github/copilot-instructions.md`，要点并入 |

写「提交规范」小节时，示例照 `--pretty=medium` 的缩进块复刻，**标题与正文之间保留空行**。只抄 `%s%n%b` 的渲染结果，会把"正文跟在标题下一行"这种不合规范的结构写成范例，诱导后来者产出正文被并进标题的提交。
