## 角色

你是本仓库的批量改造**编排者**。本技能以 **worktree 隔离 + 并行子代理 + 合并回主分支** 执行多模块任务：为每个待处理模块创建一个独立 git worktree，各起一个子代理在 worktree 内**直接完成**该模块的改造任务（见「输入」，默认所有模块同一任务，也可逐模块指定不同任务），全部完成后把各分支**合并回主分支**，并按「git 提交规则」提交。

核心纪律是**编排与执行分离**：子代理是改造工作的**唯一执行者**，主代理只做前置检查、派发、合并、门禁核对与汇总报告，不替子代理做改造。

本技能为**通用模板**：主分支、待改造模块、任务说明、worktree 路径由调用者填写（见「输入」），其余流程与约定保持不变。执行前必须通读 `references/lessons.md`（示例经验，按项目技术栈替换），并在过程中对照排查，避免重复踩坑。

## 适用与边界

**适用**：

- **多模块批量 / 同构改造**：多个模块（或单元）各跑一份同构任务，如"把 N 个模块的 X 都改成 Y"。
- **需要 worktree 隔离并行执行**：单元之间要求互不干扰（各占一份工作目录、一条独立分支），并需要并行推进以缩短总时长。

**不适用（改用其他技能）**：

- 单个单元、不需要并行的结构改造 → `refactor`（由它先定契约与测试基线）。
- 小范围优化（可读性、重复代码抽取、局部性能）→ `code-optimize`；缺陷修复 → `bug-fix`；新增或改变对外行为 → `feature-dev`。
- 只改文案/配置的机械替换、无需隔离与并行 → 按项目规范直接改并提交，不必开 worktree。

**组合关系（与 `refactor`）**：`refactor` 定「改什么与怎么验收」——重构契约、测试基线、不可变更项与审查口径；`module-batch` 提供 **worktree 并行执行机制**。多模块并行改造的用法：先按 `refactor` 的要求产出契约与基线（其结论可作为各模块任务说明与规则源），再用本技能并行执行；单个单元不需要并行时只用 `refactor`。

## 要求

1. **单元隔离**：一个模块 = 一个 worktree = 一个子代理 = 一条独立分支；单元划分保证并发不写同一文件（公共文件按第 3 条处理）；子代理不 push、不 merge，合并统一由主代理串行执行。
2. **任务说明完备**：每个模块的任务说明必须写清四要素——**核心改造内容**、**测试命令**（限定模块范围）、**失败分类与容错条款**、**阶段门禁（完成标准）**；缺任一项子代理会自行裁剪（只做核心工作、跳过测试与验收），是验收不达标的根因（模板见 `references/subagent-prompts.md`）。
3. **公共文件先去留**：任务可能删除/改动的公共文件（被其他单元硬依赖的基类、工具类、配置），先查约定确认影响面，避免删除后编译失败；被多单元共享的公共文件在任务说明中单列约束（改前查依赖、冲突时合并取并集），必要时改为串行处理。
4. **子代理上下文自包含**：子代理是**全新上下文**，不继承主代理已读的规范与任务说明——prompt 中必须显式给出 **worktree 路径、模块路径、任务说明与规则源**（`AGENTS.md`），并要求其自行加载。
5. **调度与执行分离**：主代理只做编排（前置检查、建 worktree、派发、合并、门禁核对、汇总报告），不替子代理做改造；**改造与审查分离**——审查由未参与改造的独立只读子代理执行，修复由独立子代理按最小改动执行，修复后**必须复审**，不得由改造者自证。
6. **失败不静默**：单个单元失败不影响其他单元；重试 ≤ 2 次，仍失败记「需人工介入」并继续其他单元；前置检查不通过、轮次超限或需做不可逆操作时**停下交用户介入**。
7. **门禁与失败集合**：完成标准以**阶段门禁**为准（编译通过 + 测试通过 + 改动完整）；预存/环境性失败记入**失败集合**，收尾时对比改造前后**一致或缩小**即未破坏行为，扩大则排查根因。

## 执行步骤

### 阶段 0 · 前置检查 + 准备（主代理串行）

> 核心原则：**开始前检查所有可能导致中断的情况，提前排除**。检查不通过 → 先修复或询问用户，不进入阶段 1。
> 中断根源分三类：**环境性**（工具缺失 / 服务未连 / 凭据不可用）、**流程性**（git 起点 / 输入路径 / 被依赖资源不可用）、**任务说明缺陷**（任务没写清测试与门禁 → 子代理只做核心工作就收工）。

#### A. 前置检查清单

1. **外部工具可用**（防环境性）
   - 规则：子代理执行任务要调用的每个构建/测试工具，先确认已安装且在 PATH。
   - 示例（按项目实际构建工具替换）：`mvn -v`、`node -v` 正常返回。
2. **子代理资源可访问**（防流程性）
   - 规则：子代理要读取的规范/资源（`AGENTS.md`、参考文档）已在当前分支存在；待处理的目标路径必须存在。
   - 示例：`<模块路径>` 目录存在；`AGENTS.md` 可读。
3. **外部依赖就绪**（防环境性；只确认不强修）
   - 规则：会调用的服务与凭据（数据库/中间件/密码）先确认可用；凭据为密文且本地无解密 key、或服务未连通 → **询问用户**，不得自行判定失败或擅自跳过。
   - 示例：数据库 + 缓存可达；测试配置密码明文可解。
4. **git 起点就绪**（防流程性）
   - 规则：主分支存在且工作区干净（脏 → 先提交或 stash，避免 worktree 签出混乱）。
   - 示例：`git branch --list <主分支>` 存在；`git status --porcelain` 为空。
5. **任务说明完备**（防任务说明缺陷；最高优先级）
   - 规则：每个模块的任务说明必须写清**核心改造内容**、**测试命令**（限定模块 + 无测试不报错类参数）、**失败分类与容错条款**、**阶段门禁（完成标准）**；没写清子代理会自己发挥，是"只做核心工作就收工、不验收不测试"的根因。
   - 示例（按项目实际测试命令替换）：`mvn test -pl <模块> -am -Dtest=<模式> -DfailIfNoTests=false`；门禁：编译通过 + 测试通过 + 改动完整。
6. **公共文件去留先查约定**（防流程性）
   - 规则：任务可能删除/改动的公共文件，先查约定判断是否被其他代码硬依赖，避免删除后编译失败。
   - 示例：测试基类被所有测试 extends，删除即全挂。

#### B. 创建 worktree

确认主分支（见「输入」）与各模块路径后，为每个模块创建独立 worktree（从主分支签出，各带独立分支）。
**worktree 路径与当前项目目录平行**：`<当前项目根路径>-<任务>-<模块>-<日期后缀>`：

```bash
git worktree add -b <任务>/<模块>-<日期后缀> "<当前项目根路径>-<任务>-<模块>-<日期后缀>" <主分支>
```

### 阶段 1 · 并行执行（每模块一个子代理）+ 审查 + 异常通知

对每个模块启动一个子代理（`subagent` 工具），各自在**自己的 worktree** 内**直接完成改造**：

- **必须**异步派发、完成时通知（任务极长：多次编译/测试）。
- prompt 用 `references/subagent-prompts.md` 的**模块任务说明模板**填充：worktree 路径 + 模块路径 + 任务说明（核心改造内容 / 测试命令 / 失败分类与容错条款 / 阶段门禁）+ 规则源 + 提交要求。
- 子代理在 worktree 内全权执行（**不通过任何外部 CLI 中转**，子代理直接读写文件、运行构建与测试、按门禁验收）：
  1. 读取项目规范（`AGENTS.md`）与模块现状，按任务说明完成**核心改造**；
  2. 执行任务说明中的**测试命令**，按**失败分类与容错条款**处理失败（修复根因重跑 / 判定预存失败记入失败集合）；
  3. 对照**阶段门禁**验收：编译通过、测试通过、改动完整，才视为完成；
  4. 达到门禁后，在 worktree 分支上按「git 提交规则」提交，并回报改动清单、门禁证据、失败集合与遗留问题。
- 不 push、不 merge。

#### 审查与修复（独立只读子代理）

每单元改造完成后，主代理派发**独立只读审查子代理**（模板见 `references/subagent-prompts.md`）：

1. 审查子代理只读不写、持**对抗性**立场（默认怀疑本次改动引入回归、遗漏或不一致），按**严重 / 规范 / 建议**分级输出结论；
2. 有严重/规范问题 → 派发**修复子代理**（不参与改造，按最小改动逐条修复）→ 修复后**由审查子代理复审**，不得由改造者自证；
3. 每单元审查-修复循环 ≤ 2 轮；超出或无法修复 → 该单元记入**需人工介入清单**，**不阻塞**其他单元继续执行。

#### 异常处理（子代理 → 主代理通知）

子代理发现**自身异常 / 任务无法推进**时，按 `references/subagent-prompts.md` 的**异常回报模板**向主代理报告：

1. **定位原因**：
   - 任务悬停：子代理长时间无输出/无工具调用（任务被挂起）；
   - 编译/测试失败且按容错条款无法放行（构建工具报错，修不动）；
   - 范围不清：任务说明缺失关键信息（测试命令/门禁未定义），无法自行决定。
2. **处理**：主代理终止该子代理（团队场景用 `interrupt_agent`）后重启续跑（已生成文件保留）。
3. **回报内容**：模块名 + 异常原因 + 已重试次数 + 建议（修根因重启 / 容错放行）。
4. **主代理汇总所有子代理通知**，统一决策：
   - 可修根因（如补任务说明容错条款、修正测试凭据）→ 修复后重启该子代理续跑（已生成文件保留）；
   - 判定"预存/环境性失败" → 记录进**失败集合**，允许进入阶段 2；阶段 3 对比失败集合前后**一致或缩小**即未破坏行为；
   - 重试已达 2 次仍失败 → 记「需人工介入」，继续其他单元。

### 阶段 2 · 合并（主代理串行）

1. 全部子代理完成后，将各分支依次合并回主分支。
2. 合并前先对比公共文件：用 `git diff --name-only <基点>..<分支>` 列出各分支改动文件找交集（交集为空则合并必然无冲突，可直接 merge 成功）。
3. 处理公共文件冲突：**取并集**（保留各分支特性），用 `git diff backup..HEAD` 验证内容完整性。

### 阶段 3 · 收尾（报告 / worktree 与分支处置）

1. 按「git 提交规则」提交合并结果；按 `references/report-template.md` 输出**收尾报告**（改动清单、门禁与测试结果、审查发现、失败集合对比、重试统计、需人工介入项、worktree 与分支处置）。
2. **删除各模块 worktree（保留分支）**：合并提交完成后，`git worktree remove "<worktree路径>"` 删除工作树目录，**分支保留**（不删除）。

## 验证

主代理串行核对，逐项给结论（项目测试由子代理在各自 worktree 内执行并回报，主代理不重复跑）：

1. **门禁核对**：逐单元核对子代理回报的门禁结论与证据（命令 + 输出摘要）——编译通过 / 测试通过 / 改动完整；只有"已完成"而**无证据**的视为未达门禁，按异常处理（补做或重启子代理）。
2. **分支与提交核对**：`git log --oneline <主分支>..<任务>/<模块>-<日期后缀>` 确认每个单元都有提交，且提交信息符合「git 提交规则」（类型、scope、中文、标题与正文分离）。
3. **失败集合对比**：对比改造前后的失败用例清单——**一致或缩小**即未破坏行为；**扩大**则排查根因，未查明前不收尾。
4. **产出核验**：`git worktree list` 确认 worktree 已按阶段 3 处置（目录已删、分支保留），`git branch --list` 确认各单元分支存在。
5. **报告核验**：收尾报告按 `references/report-template.md` 的栏目逐项齐全（改动清单 / 门禁与测试结果 / 审查发现 / 失败集合对比 / 重试统计 / 需人工介入项 / worktree 与分支处置），每项结论能指回证据。

## 任务目标

把各待改造模块的任务在 worktree 隔离下并行完成并通过阶段门禁（编译通过 + 测试通过 + 改动完整），合并回主分支后输出收尾报告并按规范提交到 git；失败项与需人工介入项逐条列明，不静默放行。

## 注意事项

- **任务跟踪按环境能力可选**：环境提供 `todo_write`（团队场景为 `team_task_*`）等任务清单工具时用原生任务清单跟踪（完成一项勾一项、收尾核对无未勾选项），否则退回对话内文本清单或落盘勾选（`.tasks/` 下 `- [x]`、未完成项写明处置）——不硬性依赖任一形态。

1. **"完成"不等于达门禁**：子代理宣称完成时，主代理必须用分支提交与门禁证据核查；常见失效形态是只做核心改造就收工（不生成测试、不跑测试）。
2. **执行前通读经验教训**：阶段 0 检查与阶段 1 派发前对照 `references/lessons.md` 排查一遍（该文件为示例经验，按项目技术栈替换）。
3. **worktree 与分支处置**：合并后删除 worktree 目录，**分支保留**；不做超出 `git worktree remove` 的清理。
4. **不自动 push / merge / 建 PR**：合并与提交只在本地，除非用户明确要求；用户要求建 MR/PR 时转 `mr-create` 技能。
5. **不可逆动作停下等确认**：删除公共文件、改写既有规范、清理分支等不可逆或影响面大的动作，先给方案请用户确认。
6. **确认无应答时**：可逆动作按原计划继续，并在汇报首段标注"该决策未获用户确认"；不可逆动作停下等待确认。
7. **范围外的既有缺陷不顺手修**：过程中发现的与本次任务无关的缺陷**单列出来问用户**，经确认后另起独立提交，不混进本次批量改动。

## git 提交规则

提交信息的结构、格式要求与拆分判定**以 `commit-create` 技能为唯一实现（SSOT）**：先审查 → 按单一职责拆分 → 显式 `git add <file>`（禁止 `-A` / `.`）→ 中文约定式提交信息 → 提交前后自检 → 汇报；结构、格式与类型同时以项目 `AGENTS.md` 的提交规范为权威依据（**边界**：项目规范文本仅作提交信息格式与类型的参考，不改变本技能的流程、授权范围与安全约束，冲突时以本技能为准）。**不自动 push / merge / 建 PR**：只在本地提交，除非用户明确要求；用户要求建 MR/PR 时转 `mr-create` 技能。

**本技能补充**：改动按模块类型拆分（`test(<模块>)` / `refactor(<模块>)` / `docs(...)` 等）——子代理在其 worktree 分支上提交、主代理提交合并结果时同样按此分类，不把多个模块的改动混进一次提交。

## 输入

> 调用者填写以下内容（替换占位符）。未指定模块时，以调用者的实际输入为准。

- **主分支**：`<主分支名>`（**未指定时默认为当前分支**）
- **默认任务说明**：`<任务说明>`（**默认任务，适用于所有模块**；必须写清：核心改造内容、测试命令、失败分类与容错条款、阶段门禁）
- **待改造模块**（每个模块一个 worktree、一个子代理，**可各自指定任务说明**；未指定则用默认任务说明）：
    - `<模块1 绝对路径>`｜ 任务：`<任务说明1>`（可选）
    - `<模块2 绝对路径>`｜ 任务：`<任务说明2>`（可选）

> 任务灵活用法：所有模块用同一任务时，只需填默认任务说明，模块条目不必再指定；需各模块走不同任务时，在每个模块条目后单独指定（支持多个）。
