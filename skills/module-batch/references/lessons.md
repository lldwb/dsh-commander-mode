# 经验教训速查（对照排查）

本文件是 `module-batch` 的参考件：阶段 0 前置检查与阶段 1 派发子代理前通读一遍，执行过程中对照排查。

> **本文件条目均为示例经验，按项目技术栈替换**：条目里的框架、工具、配置项名称按项目实际改写；条目背后的**失效模式**（每条的"根因"）可直接迁移。

## 一、任务说明与验收

### 1. 子代理只做核心工作就收工

- 现象：子代理未生成测试、未跑测试就宣称完成。
- 根因：任务说明未把"完成"定义为可核对的证据，子代理按自己理解的边界收尾。
- 处置：主代理用 `git log` / 分支提交核查实际改动，按阶段门禁安排补做；**不接受无证据的"已完成"**。

### 2. 任务说明缺失测试命令与门禁 → 子代理自行发挥

- 现象：子代理跳过测试、不处理失败，验收不达标。
- 根因：测试范围与完成标准没定义时，子代理会自行裁剪任务。
- 处置：任务说明必须显式列出**核心改造内容、测试命令、失败分类与容错条款、阶段门禁**（模板见 `subagent-prompts.md`）。

### 3. 合并前对比公共文件

- 做法：合并前用 `git diff --name-only <基点>..<分支>` 列出各分支的改动文件求交集；**交集为空则合并必然无冲突**（可直接 merge 成功），有交集则预先安排冲突处理。

## 二、并发与公共文件

### 4. 并行子代理共享公共文件

- 现象：多个单元并行改动同一公共文件（如测试基类、公共工具类），先提交的改动能被合并，后提交的产生冲突。
- 处置：任务说明中明确"改动公共文件前先查约定/是否被其他单元依赖"；冲突在合并阶段**取并集**（保留各分支特性）后验证内容完整性；影响面过大时把该公共文件的改动改为串行处理。

## 三、测试失败排查（示例经验，按项目技术栈替换）

### 5. 测试凭据与已跑通单元不一致会触发账号锁定

- 现象：批量更新测试凭据时常只改了部分单元，其余单元仍用旧值 → 连接目标服务（数据库/中间件）连续失败触发**账号锁定**，需由凭据持有者或管理员解锁。
- 处置：解锁前**停止一切连接尝试**，避免刷新锁定时钟；测试连不上时先核对凭据是否与已跑通的单元一致，再判断是否已被锁定。

### 6. 测试基类的响应字符编码未设置会引发断言乱码

- 现象：断言响应内容/文案的用例"内容看起来一样却断言失败"。
- 根因：测试基类未显式设置响应字符编码（按项目框架查对应配置项，如响应编码 / 字符集设置）。
- 处置：新建或复制测试基类时必查该项；编码设置随框架不同而异，以项目既有可跑通的基类为准。

### 7. 测试数据长度/精度必须匹配存储的实际限制

- 现象：插入报错，或写入后被截断导致断言失败。
- 根因：实体/校验层的约束值不等于库表列宽、长度上限、精度等实际限制。
- 处置：插入前核对库表 DDL；按约定的数据格式写固定值，不使用越界数值或超长时间戳。

### 8. worktree 内读项目规范注意分支版本

- 现象：子代理在 worktree 内读取的规范（`AGENTS.md`）缺新分支刚补的内容。
- 根因：worktree 签出的分支较旧，规范文件是否存在**以 worktree 内实际为准**。
- 处置：任务说明中写明规范路径与版本要求；确需时从新分支的 worktree 复制补齐后再执行。
