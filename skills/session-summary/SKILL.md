# 会话总结与 skills 迭代

## 在 DSH 中的对应工具

本技能原为 Claude Code 技能库中的一项，正文方法论原样保留；在 DSH 中按以下对照表映射工具与交互方式：

| 原（Claude Code） | DSH 等价物 |
| --- | --- |
| `Task` / `Agent` 工具、子代理 | `subagent`（一次性子代理，异步、完成时通知）/ `spawn_teammate`（持久队友）/ `workflow`（批量扇出编排） |
| `AskUserQuestion` | `ask_user_question` |
| `SendMessage` / `TaskStop` | `send_message` / `interrupt_agent` |
| `TodoWrite` / `Task*` | `todo_write`（团队场景用 `team_task_*`） |

| `Bash` | `pwsh`（Windows）/ `bash`（类 Unix） |
| `WebFetch` / `WebSearch` | `web_fetch` / `web_search` |
| `Skill` 工具 | `skill` 工具 |
| MCP 工具 | 对应的 DSH 插件工具（如 `browser_*`、`android_*`、`ssh_*`） |

补充：

- 正文中标注为 bash 的代码块是通用 shell 示例，Windows 下用 `pwsh` 执行（`git` 等命令一致，管道 / 变量语法按需改写）。
- 正文引用的 `references/…`、`scripts/…` 相对本技能目录解析（DSH 技能目录允许附带资源文件）。
- 正文引用的其它技能名（如 `commit-create`、`mr-create`、`git-*`）可能由同包或其它插件提供，能否调用以当前环境实际安装的技能为准；未安装时按其描述的人工流程执行。

- **会话记录来源（DSH 适配）**：`scripts/extract-session.py` 解析的是 Claude Code 的 `~/.claude/projects/<项目路径转义>/<会话 id>.jsonl`。DSH 的会话不落这种格式，取证改用 `session_search` / `session_trace` / `session_event_search` / `session_event_read`（可指定会话 id），需要落盘再写到 `.tasks/`；脚本保留供 Claude Code 环境使用。
- **memory 说明**：正文中的 memory 指 Claude Code 的会话记忆文件；DSH 没有同名机制，按等价的落盘笔记理解。

## 角色

你是本仓库的**会话总结者与技能迭代者**。职责是把一次会话收尾为可行动的产出：**总结 → 审视 → 评估 → 审查 → 实施 → 自迭代（收尾）**。本技能服务于"技能仓库本身持续演进"——每次会话的实操都会暴露技能缺陷或新能力需求，沉淀回技能本体；**session-summary 自身也在这个闭环里**（自迭代在流程最后、以整个当前会话为输入执行），不因"改的是自己"绕过任何环节。

教训的落点由「**谁该记住它**」决定：**技能**该记的进本仓库（技能缺陷 / 能力缺口 / 通用于所有项目的规则），**项目**该记的进那个项目自己的 `AGENTS.md`——所以会话发生在别的项目仓库时，同一轮还要把该仓库实证过的教训回流进去。

## 适用与边界

**适用**：

- 会话结束时的总结（做了什么、发现了什么、留下了什么待办）；
- 审视当前 skills 是否可优化：本次会话暴露的问题、教训、新需求，对应哪个技能缺什么；
- 把经验固化为技能内容（新增 / 增强技能）或仓库规则（AGENTS.md）；
- **目标项目的教训回流**：会话操作的是别的项目仓库时，把该仓库本次实证的机制、边界与坑补进**它自己的** `AGENTS.md`。

**不适用（改用其他技能）**：

- 只评审某个提交 / 合并请求质量 → `code-review`；
- 只做历史提交改写 → `git-history-rewrite`；
- 实施已确认的优化：新增技能 / 能力 → `feature-dev`；修复缺陷 → `bug-fix`；结构调整 → `refactor`（本技能只做评估与方案，实施转对应流程）。

## 要求

1. **取证再总结**：总结必须基于会话的实际动作——`git log` 本次会话的提交（含信息、涉及文件）、改动的文件清单、关键决策与教训；不凭印象写。
2. **问题对应到技能**：每个发现的问题 / 教训都要回答"这暴露了哪个技能的什么缺陷"（技能缺该能力、写得不清楚、还是规则没固化）——无对应技能的新能力单独列出。
3. **教训按归属分流**：每条教训先问"该由谁记住"——**技能本身**的缺陷与能力缺口留在本仓库（进优化点清单）；**那个项目特有**的机制、边界、坑，回流到目标仓库自己的 `AGENTS.md`。两边都沾的（如同一处机制既暴露技能缺能力、又该被项目记住）两边各写各的，不互相代替；回流是本技能的固有环节，不另转 `doc-sync`。
4. **评估要量化**：优化点清单每项给「价值（高 / 中 / 低）+ 成本（改动面）+ 建议（做 / 暂缓 / 不做）」；推荐项给出具体改法（文件 + 改动点）。
5. **规则优先固化**：本次会话反复踩坑的约束（如发版规则）优先固化进 AGENTS.md 或对应技能的规则段，而不是只记在会话里。
6. **确认后实施**：优化点清单交用户确认；实施按对应技能流程（feature-dev / bug-fix / refactor）执行，不擅自扩大范围。**任何用户确认环节（优化点清单确认、回流提交、发版拍板）`ask_user_question` 无应答或流程中断时，一律停在草稿态（实施未开始 / 回流未提交 / 发版未执行），汇报「待拍板、可并入下次」，不默认继续**。
7. **审查与产出分离（对抗性审查）**：总结、教训落点、优化点清单与回流内容在**交用户确认 / 提交目标仓库之前**，必须经**未参与产出的独立只读子代理**对抗性审查（默认怀疑结论夸大、证据断链、归属错位、回流夹带未实证内容），prompt 用 `references/review-agent.md`；审查结论由主代理**逐条复核证据**后再采纳，无证据支撑的不采纳；🔴 级偏差（结论断链、归属错位、回流夹带未实证条目）修复后必须**复审**（由审查者复验，不由产出者自证）；🟡 级偏差修复不强制复审，随清单交用户；审查不通过不得进入确认与提交。
8. **自迭代收尾（本技能对自身无豁免）**：session-summary 自身的迭代**只在流程最后执行**——自迭代的输入是**整个当前会话**（从取证到实施完成的全过程，含审查与实施环节暴露的摩擦），提前触发只能拿到不完整的输入，所以第 3 步审视其它技能时**不**收集本技能问题，收尾时按普通技能缺陷同规则审视本技能、产出**自迭代清单**。自迭代不设特殊通道：清单同样过对抗性审查（复用第 6 步子代理与模板）、同样经用户确认后实施；**实施自迭代改过 `<skill 目录>\scripts\extract-session.py` 的，必须重跑 `<skill 目录>\scripts\selftest.py` 全部用例**（自测基线防止自迭代把脚本改坏——历史上两个脚本缺陷都是实际使用才暴露的，此前没有回归基线）。
9. **新增技能走发版流程，但发版必须用户显式拍板**：新增 / 增强技能后，按仓库发版规则（版本分级、发版提交、tag、Release、分发路径同步）收尾；**发版环节（是否发、版本号、推送与建 Release）一律先经用户显式确认**——`ask_user_question` 无应答或流程中断时停在本地提交、汇报「待拍板、可并入下次」，不默认继续发版（2026-09-20 用户明示「不要自动发版，以后发版都需要用户拍板」）。

## 执行步骤

### 第 1 步：取证会话动作

- `git log --oneline -N` 取本次会话的提交（按时间或用户指定范围）；`git show <sha> --stat` 看每个提交改了哪些文件；
- 会话中的关键决策与踩坑（从对话记录回顾；DSH 会话用 `session_search` / `session_trace` / `session_event_read` 取证，下列 `extract-session.py` 用法适用于 Claude Code 记录）：哪些操作出错、哪些操作反复调整、最终采用什么做法——记录文件常达十几 MB，用 `<skill 目录>\scripts\extract-session.py` 抽取后再读（**要落盘须显式 `--out <文件>`**——放 `.tasks/`，未指定时直接打印不落盘；`--user` 用户消息全文，上下文压缩摘要默认过滤、`--with-summary` 保留 / `--assistant N` 尾部 assistant 文本 / `--timeline` 逐条时间线 / `--transcript` 紧凑全文；**时间线 / 转录的时间戳为 UTC**，别当本地时间——实测曾差点因此写错会话时点），别整份读 transcript。给会话 id 时 `--project` 填的是**会话所属**项目路径——不在本项目目录下时先在 `~/.claude/projects/*/` 按 id 定位会话文件，再据时间线确认操作对象。**调用样例**：`<受管 python 全路径> <skill 目录>\scripts\extract-session.py <会话id或记录文件路径> --project <项目路径> --timeline --out .tasks/xxx.txt`——脚本路径**以技能目录（skill 的 Base directory）为基准**，不是当前工作目录（2026-09-30 实证：按相对路径到仓库根找脚本报 No such file）；会话 id 是**位置参数**（无 `--id` 选项，传了报 unrecognized arguments）；Windows 裸 `python` 可能是 Store stub（`--version` 无输出、exit 49），用受管解释器全路径；`--timeline` 缺省单条截断 900 字（出现 `[共 N 字]` 标记），关键结论核对用 `--limit 0` 取全文（2026-09-28 实证：位置参数与解释器两个坑连踩多轮）。
- **无会话 id 时，目标为当前会话**：当前会话的记录文件 = `~/.claude/projects/` 下本项目路径的**转义目录**（非字母数字字符转 `-`）里**最近修改**的 `.jsonl`——本会话逐回合追加，mtime 通常最新；定位到文件后把路径直接传给脚本（会话 id 与 `--project` 都不需要）。多会话并行时最近修改的可能不是本会话：取修改时间最近的几个候选，比对**文件尾部**是否含本次触发语与最近动作（当前会话的记录里应能找到刚刚发生的对话），拿不准时向用户要会话 id。
- **取证先查该会话产出是否已被零散沉淀**：会话结束后可能有后续操作已把其核心实证零散固化（目标仓库回流提交、技能仓库补坑提交、**产出 memory 被后续会话扩展**）——`git log` 目标仓库与技能仓库**会话结束时间之后**的提交（结束时间以会话记录文件 mtime 为准），识别该会话产出的提交与随后的沉淀提交；产出含 **memory 文件**时，比对 frontmatter `modified` 时间戳与会话结束时间、正文条目与会话实际动作——memory 会被后续会话继续更新（实证：`modified` 晚于会话结束约 1 小时，正文混入本会话明确未做的操作），不比对会把后续会话的功劳与教训误记进被总结会话；已被固化的教训在总结与回流时只做核验对照、不重复回流，产出文档注明去重基线（含沉淀提交号）。

### 第 2 步：总结会话

按「**做了什么 → 发现了什么 → 教训 → 留下的状态**」组织：

- **做了什么**：按提交/动作分点列出（类型、范围、涉及文件）；
- **发现了什么**：过程中暴露的问题（含用户指出的、验证发现的）；
- **教训**：可复用的经验（操作顺序、易错点、规则缺失）；
- **留下的状态**：当前分支、未推送的提交、备份分支、待办；**未提交的改动须注明去向**——会话结束时未提交的工作可能在会话后被 `git reset` / 覆盖 / 方案被否决而消失（实测发生过：产出未提交，会话结束不久即被 reset 丢弃、方案被后续会话否决），需要保留就先落盘快照再总结。状态逐项**两面核验**：**现存性**以实测为准（`git status` / `ls` / `find` 现查，不凭时间线记录推断）；**动作的归属时点 / 轮次**以时间线记录的时间戳逐项对照（时间线是唯一时点证据源，错在漏对照、不在记录本身）；**计数 / 统计数字与归因结论**逐一实测或核对口径与分母——会话内 AI 自报的数字（条数、大小、批次归因）与脚本统计行都是现成口径，照抄即失实（实证：凭据"11 处"实为 7 行凭据 + 6 处描述文字、"11 份明细"实为 9 份、"346 次工具调用全为读类"的 346 是全会话总数而非指向目标仓库的调用数——均被对抗性审查纠出）。**memory 归属**：会话产出的 memory 若在会话结束后仍被修改（`modified` 晚于会话结束时间，查法见第 1 步零散沉淀排查），其新增内容属后续会话，不列入被总结会话的产出与教训（实证：memory 被后续会话扩展混入 PATH 前移等本会话未做的动作，凭正文转述即误记归属）。**转述来源核验**：时间线里被截断的长汇报（`[共 N 字]` 标记）不作转述依据——验证结果与失败披露同源核对、评审处置与遗留清单按原始汇报归类核对、「已留档 / 已记录」类结论读被留档文档原文核对条目，不凭截断文本或自报归因转述（实证 2026-09-28：三条审查偏差同此根因——「单测全绿」转述丢失既有失败披露、遗留清单与方案实际条目错位、评审处置归类错误）。实测与落笔之间隔了多节产出时，状态类结论**落笔前复核**或注明实测时点，不加「至今 / 一直 / 尚未」等时间延展词——取证时点早于落笔，期间外部状态可能已变（实证发生过：取证时实测领先远程 2 提交，落笔写"至今未推"，期间用户已推送，产出即失实、被对抗性审查判 🔴）。

### 第 3 步：审视 skills

逐项对照教训找落点：

- **技能缺陷**：某个技能（SKILL.md / references / 脚本）写得不清楚、缺能力、与实操不符 → 记「技能名 + 缺陷 + 改法」；
- **本技能自身的问题此处不收**：session-summary 自身的问题（运行摩擦、被总结会话里发现的本技能缺陷）留到第 8 步**自迭代收尾**统一审视——自迭代的输入是整个当前会话，此处只走过半，提前入列拿不到审查与实施环节暴露的摩擦；
- **规则缺失**：教训应固化为仓库规则（AGENTS.md / 技能规则段）→ 记「规则 + 落点」；
- **能力缺口**：没有技能覆盖的常用流程（如历史改写）→ 记「新技能候选 + 核心流程」；
- **验证方式**：对每个候选，确认它在本仓库全部既有技能中的位置（是否与既有技能重复 / 互补 / 边界清晰）。

### 第 4 步：目标项目的教训回流（会话发生在别的项目仓库时）

被总结的会话操作的是**另一个项目仓库**（cwd / 提交所属仓库 ≠ 本仓库）时，先做这一步再做第 5 步——目标仓库有它自己的 `AGENTS.md`，本次实证的教训首选落点在那里。**目标库无 `AGENTS.md`**（非 git 文档库、主文档为业务文档等形态）时，不强行新立指引章节——回流落点为其主文档 / 索引中既有机制的对应位置，或仅列待办交用户拍板；已随任务固化的教训确认在位即可，不重复回流。总结本仓库自身的会话时跳过本步（落点已在第 3 步的"规则缺失"分支内）。注意：**会话记录文件所在的项目目录 = 会话启动时的 cwd，不代表操作对象**——文件落在本仓库目录、操作对象却是别的仓库（或反之）都可能出现，判断一律以**操作对象**（提交所属仓库 / 时间线里 `cd` 的目标仓库 / 讨论目标）为准，拿不准先查时间线再定；别因「文件在本仓库目录下」就跳过回流。

1. **读目标 AGENTS.md 全文**：摸清它的章节结构、语气与颗粒度——新内容要**长在既有结构上**（机制与边界归"架构"、踩过的事实归"已知坑"、流程约束归对应工作流节），不另立体系；已写过但不够清楚的，补证据或示例，不重复写。目标文档若是**主文件 + 分册 / 按需加载**形态（顶部有「何时读 → 读哪份」的索引表），先读那张索引表再定落点——常驻规则进主文件，特定时机才用的坑与流程进对应分册，分册的体例（文件头引用块、条目写法、引用措辞）照该仓库既有分册复刻。
2. **取证目标会话（别整份读 transcript）**：会话记录文件可能十几 MB，整份读会撑爆上下文——**抽取**（`<skill 目录>\scripts\extract-session.py`，以技能目录为基准；用 `--user` 取用户消息全文、`--assistant` 取尾部 assistant 文本消息；给会话 id 时用 `--project <目标路径>` 定位；**落盘须显式 `--out <文件>`**——放 `.tasks/`，未指定时直接打印）到 `.tasks/` 再读，配合目标仓库的 `git log --oneline` / `git show --stat` 还原实际动作，据此提炼教训。**memory 文件只作线索与对照，结论一律以时间线与 git 取证为准**——memory 写入时点可能早于事实澄清、正文可能保留后来被推翻的结论（实证发生过：某 memory 记了「runner 也中招」，17 分钟后同会话证实是误判，照抄即把失真结论当实证回流）；发现 memory 与取证冲突时，顺手修正该 memory（或把「memory 待修正」列入留下的状态）。
3. **只收"已实证 + 未固化"的教训**：本次**真实踩到**（有实测现象或失败记录）、且目标文档**尚未写**的才收；固化与否以第 1 步「查零散沉淀」的取证结果为准；通用最佳实践、推测性建议、一次性操作失误一律不收——`AGENTS.md` 是权威源，不是经验合集。
4. **写法对齐 + 脱敏**：沿用该文档的排版习惯（列表 / 加粗要点 / 代码块），插入位置贴住相关段落；目标仓库涉及对外分发或开源时，不写绝对路径、机器名、凭据、内网地址。
5. **先落笔、审查后再提交**：回流内容**暂不提交**——可先写入目标 `AGENTS.md` 工作区、或暂存于产出文档中，两种顺序均合规（草稿不在目标仓库时，审查派发的证据源要写明草稿位置）；先经第 6 步对抗性审查，通过后**经用户确认**（提交与否、是否推送）再按目标仓库的规范提交（提交类型 / 语言 / 署名，一律以**目标仓库的 `AGENTS.md`** 为准——不套用本仓库的发版与双远端规则；只提交本次涉及的文档改动，不夹带别的，目标仓库里另有未提交产物时单列说明，不代提）。审查挡在提交前的目的：避免向目标仓库提交夸大、未实证或与其结构不符的条目——提交后才发现问题只能再打一笔回退提交。
6. **汇报**：逐条列「教训 → 落点章节 → 新写 / 补充」，并说明未收录的教训及原因（已有覆盖 / 推测性 / 不属于该仓库）。

### 第 5 步：产出优化点清单

每项：**优化点 → 价值（高/中/低）→ 成本（改动面）→ 建议（做/暂缓/不做）→ 改法（文件 + 改动点）**；推荐项可直接进入实施。

### 第 6 步：独立审查（对抗性、只读子代理）

1. **派发**：用 `subagent` 工具**单次派发**只读审查子代理（全新上下文、等其回报后再继续），prompt 用 `references/review-agent.md` 全文 + 本次产出（总结、教训落点、优化点清单、回流草稿——落盘路径或对话内要点）+ 会话范围与证据源。**证据源必备五项**（2026-09-28 实证：缺清单时主代理凭经验组装，漏项会致审查者报「证据不可得」空转一轮）：① 会话记录文件路径（或会话 id + 所属项目路径）；② 受管解释器全路径与抽取命令样例（含 `--project` 与位置参数用法）；③ 目标仓库路径与会话产出提交号（及会话后沉淀提交号，供零散沉淀对照）；④ 清单涉及的技能文件路径（SKILL.md / references / 脚本，附相关行号更好）；⑤ 审查对象是否含自迭代清单的声明（自迭代按第 8 步时序另行审查）。
2. **处置**：主代理对审查报告**逐条复核证据**——成立的偏差修复后**回到本步复审**（修复不由审查者做，复验必须由审查者做——复审优先 `send_message` 恢复原审查 agent 复验，其上下文已含首轮审查证据；环境不支持恢复时，派全新只读子代理对修复后的产出整体复验；复审沿用首轮分级报告格式、聚焦修复项逐条复验）；无证据或与事实不符的审查结论不采纳并说明理由；🔴 问题（结论断链、归属错位、回流夹带未实证条目）修完并通过复审才算通过，🟡 问题可随清单一并交用户决策。
3. **轮次上限**：修复 → 复审默认最多 3 轮，超出停下交用户，不静默放行。
4. **通过后**：回流草稿**经用户确认后**按第 4 步的约定提交目标仓库；优化点清单交用户确认。本步审查的是**本技能产出的结论可信度**——实施环节的代码 / 文档质量由承接技能（feature-dev / bug-fix / refactor）各自的评审机制承担，本步不重复。

### 第 7 步：实施（用户确认后）

- 按改动性质转对应技能：新增技能 / 能力增强 → `feature-dev`；缺陷 → `bug-fix`；结构调整 → `refactor`；纯规则 → 直接改 AGENTS.md（docs 提交）；
- 新增 / 增强技能后同步分发：技能随宿主插件包分发（`skills/` 目录与 `package.json` 的 `files` 白名单）、发版按仓库规范（CHANGELOG + 版本号，发版提交）；原 Claude Code 技能库的 marketplace 清单在 DSH 插件下不适用。

### 第 8 步：自迭代收尾（最后执行）

session-summary 自身的迭代**只在流程最后执行**——自迭代的输入是**整个当前会话**（从取证到第 7 步实施完成的全过程，含审查与实施环节暴露的摩擦），提前触发只能拿到不完整的输入。第 7 步未实施或仅部分实施时本步照常执行（审视的是运行摩擦，不依赖实施结果）。

1. **审视本技能**：按第 3 步同规则审视 session-summary 自身——本次运行暴露的摩擦（脚本缺陷、步骤歧义、过滤误伤、审查模板问题）与被总结会话中发现的本技能问题，逐条记「缺陷 + 改法」，形成**自迭代清单**（每项价值 / 成本 / 建议 / 改法，同第 5 步口径）；无摩擦时空清单记「不适用」快速通过；
2. **同规则审查**：自迭代清单同样过对抗性审查——按第 6 步的方式派只读子代理（prompt 用 `references/review-agent.md`，审查对象 = 自迭代清单 + 会话证据源），🔴 修复并复审、🟡 随清单一并交用户；
3. **用户确认后实施**：按第 7 步同规则转派实施；改过 `<skill 目录>\scripts\extract-session.py` 的，完成后**重跑 `<skill 目录>\scripts\selftest.py`**，全部用例通过才算收尾；
4. **发版收尾**：全部实施（含自迭代）完成后按仓库发版规则收尾（中版本 = 新增 / 大改技能，小版本 = 小修小补；发版与否、版本号一律待用户显式拍板，见要求 9）。

自迭代一轮即止：本轮自迭代实施过程中新暴露的摩擦不回流本轮清单，留待下次会话总结——避免「审视 → 实施 → 再审视」的无限递归。

## 验证

- **总结可追溯**：每项总结都能指回提交 / 文件 / 会话事实，无凭印象的结论；
- **教训有落点**：每条教训都对应了「技能缺陷 / 规则固化 / 能力缺口 / 目标仓库 AGENTS.md」之一，没有"记在会话里就算了"的悬空教训；会话在别的仓库时，回流那一条有实际落笔，或写明了未收录的原因；
- **审查独立闭环**：审查由未参与产出的只读子代理执行、其结论经主代理逐条复核证据；🔴 偏差已修复并经复审通过（或超限已显式交用户）——**未经审查的总结不得声称完成**；
- **自迭代有回归**：本次自迭代改过 `<skill 目录>\scripts\extract-session.py` 的，`<skill 目录>\scripts\selftest.py` 全部用例通过；
- **自迭代在收尾**：session-summary 自身的问题在第 8 步以整个当前会话为输入审视，未在第 3 步提前入列；清单经对抗审查与用户确认后实施，无摩擦时记「不适用」；
- **清单可决策**：优化点清单每项有「价值 + 成本 + 建议」，用户可直接拍板；
- **回流守目标仓库规范**：目标 `AGENTS.md` 的改动按其仓库的提交规范与脱敏要求落地，不与本仓库的发版 / 双远端规则混用；
- **实施守规范**：实施部分按对应技能流程与发版规则执行（功能提交不带版本号、发版提交在版本最后、条目一次写全）。

## 任务目标

把一次会话收尾为：可追溯的总结 + 有落点的教训（技能落点，以及会话在别的项目仓库时对该仓库 `AGENTS.md` 的实证回流）+ **经独立对抗性审查**的 skills 优化点清单，确认后按规范实施——session-summary 自身同在迭代范围内，于**流程收尾**以整个当前会话为输入完成自迭代，如涉及新增/增强再完成发版。

## 注意事项

- **任务跟踪按环境能力可选**：环境提供 `todo_write`（团队场景为 `team_task_*`）等任务清单工具时用原生任务清单跟踪（完成一项勾一项、收尾核对无未勾选项），否则退回对话内文本清单或落盘勾选（`.tasks/` 下 `- [x]`、未完成项写明处置）——不硬性依赖任一形态。

- **教训的归属先于写法**：技能该记的进本仓库、项目该记的进目标仓库——把项目特有的机制写进技能会让技能带上具体项目色彩（本仓库技能一律脱敏、面向所有项目）；反过来把通用的约束只写进某个项目，其他项目就享受不到。归属拿不准时按"换个项目还成立吗"判：成立进技能，不成立进项目。
- **会话记忆不替代回流**：目标仓库的教训**先落它自己的 `AGENTS.md`**（随仓库走、协作者与他人可见）；会话记忆（memory 文件）是本机的补充，不是回流。实测踩过：同一轮会话把 4 条仓库级教训只写进项目 memory、`AGENTS.md` 只落了 1 条——换个机器或换个协作者就取不到。审视时逐条问"这条换台机器还看得到吗"，看不到的补进 `AGENTS.md`。
- **`tmp/` 等过程目录默认不固化**：gitignored 的 `tmp/`、`.tasks/` 里的中间脚本（探针、验证器、mock 测试）默认视作没有固化——清掉即失、下次会话不保证还在。但**反复复用**的中间脚本要**视情况固化**：参数化（去硬编码路径/凭据）、自包含后入库并登记用法——判据是「换个电脑还用得上吗」。审视会话时把「本会话反复复用的中间脚本是否固化」列入教训落点判断。
- **会话范围要界定**：用户未指定时，以本次会话的提交与对话为准；跨会话的长期状态（未提交的改动、历史遗留）单列说明。
- **不夸大教训**：一次性的操作失误与反复踩坑要区分——前者记进操作清单即可，后者才值得固化规则。
- **自迭代不设特殊通道**：session-summary 自身的问题与其它技能同规则——记录、对抗性审查、用户确认、按对应技能实施；与其它技能的差异只有时序与回归两点：审视在**流程收尾**执行（自迭代的输入是整个当前会话，第 3 步不提前入列，防止只拿到半程摩擦），实施改过抽取脚本的须重跑自测基线。不因"改的是自己"绕过任何环节，也不因"刚审查过别的产出"省略自迭代清单的审查。
- **优化点不无限发散**：只列与本次会话相关的优化点；无关的改进（即便有价值）另起会话。
- **审查成本按产出适配**：纯复述型总结（无回流、无优化点、教训为空）照常执行第 6 步，但空维度记「不适用」快速通过，不为空产出编造审查对象；审查报告与过程产物落 `.tasks/`（不入库）。
- **实施不擅自扩大**：用户只确认了清单中的部分项时，只做确认项。

## 输入

会话范围（可选，缺省 = 本次会话——即当前正在运行的会话）：本次会话 / 指定会话 id / 指定提交范围 / 指定技能：
