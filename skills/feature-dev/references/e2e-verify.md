# 端到端实测与取证

分层验证：编译 → 单元测试 → 前端语法 → **端到端实测**。前几层本地完成，但端到端实测是唯一能暴露跨域、签名、配置绑定、作用域、部署差异等集成问题的环节——不要用"编译通过"替代它。

## 一、部署与实测节奏（人在环）

- 改动需重新部署才生效时，明确告诉用户"请重新部署前端/后端/仅配置"，**等用户确认完成后再测**
- 每轮实测前刷新页面/重启客户端，确保加载的是最新产物
- 一次只验证一个改动点，拿到结论再进下一轮；不要在同一轮里既改代码又下结论
- 多路验证并行时，凡对同一外部状态有**写副作用**的任务（同一业务单据、同一配置项）必须串行——并行会互相覆盖数据与配置、互相污染结果，并列跑出的"通过/失败"都不可信；并行只留给只读或资源隔离的任务
- 每轮结束汇报：验证结果 → 发现的问题（现象 + 证据 + 根因）→ 已修复内容 → 下一步需要用户做什么

## 二、浏览器端取证（前端行为）

用浏览器类 DSH 插件工具（Chrome DevTools 插件）按序采集，避免只看表面现象：

1. `list_network_requests`：请求是否发出、状态码、URL 形态（关注重复斜杠、参数是否齐全、签名相关 query 是否含预期参数）
2. `get_network_request`：失败请求的**请求头 / 响应头 / 响应体原文**——CORS 缺头、签名不匹配、摘要不匹配（BadDigest）等的判定都靠原文，不靠推测
3. `list_console_messages`：JS 报错与堆栈（作用域/未定义变量类问题只看网络请求发现不了）
4. `take_snapshot`：页面状态（进度、弹窗文案、列表是否更新），作为业务结果的最终确认
5. `evaluate_script`：最小复现（同源直接调接口、读响应体），把问题范围从"页面交互"缩小到"接口本身"

判读要点：

- 请求返回 200 但业务失败 → 看响应体里的业务码/消息，不要只信 HTTP 状态
- 请求**根本没发出** → 前端在更早的分支中断，去控制台找报错
- 预检 `OPTIONS` 与真实请求（PUT/POST）分开看：一个失败不代表另一个
- 响应头里读不到的值（跨域未暴露的响应头）→ 从"前端读响应头"改为"后端自行获取"，是常见正解
- 浏览器类插件工具连不上调试端口时（插件固定从默认用户配置目录找端口文件，与独立 profile 启动的实例不匹配）：先用独立 profile 启动浏览器并尝试向默认配置目录写 `DevToolsActivePort` 存根重连；仍失败就改用最小 CDP 客户端脚本直连（`/json/version` 列页 + WebSocket 执行）取证，不在 MCP 重试上空耗

## 三、日志取证（后端行为）

- 有 trace_id：按 trace_id + 时间窗取日志上下文（可结合 `log-diagnose` skill）
- 只有片段：按时间戳就近取前后行
- 关注两点：**异常抛在哪一行**、抛之前的业务状态字段值是否符合预期
- 日志里的值本身就是证据（例如对象校验值的后缀、文件大小、返回码），引用原文而非转述

## 四、服务侧最小复现

浏览器链路干扰多（预检、缓存、前端逻辑）时，用 curl 等直接打目标服务：

- 注意模拟工具与浏览器的默认行为差异（自动附加的请求头如 Content-Type 会改变签名结果），结论要区分"工具差异"与"真实缺陷"
- 分别模拟预检请求与真实请求，定位到底哪一步失败
- 复现用只读或最小影响手段，避免污染业务数据
- **取证方式自检**：断言为空或为负时，先看原始产物（文件大小、`cat` 原文、响应体全文），确认不是取证方式写错（正则多写一个空格、分隔符、字段名），再怀疑被测代码
- **断言必须消耗真实证据**：统计类断言结果为 0（标记 0 条、解析 0 行、删除 0 条）不构成通过——为批量操作专门构造出有数据可断言的场景再跑；文件类断言解析内容本身（行数、字段值、逐字节比对），只比对响应头或文件大小等于没验
- 命令里不要写 `A | 解析器 || A` 这类兜底——解析器缺失时前半段已经执行，兜底会重复发起请求、污染会话数据；依赖的外部命令先 `command -v` 确认存在
- 同一组验证手工重复到第二次时，固化成可重跑脚本（脚本可被审查，手工命令不能）

## 五、自然语言 / 大模型驱动的链路：断言设计

链路每次的输出都可能不同（措辞、是否调工具、走几步），断言必须落在**确定性事实**上：

- 断言"工具被调用（名称与顺序）""工具返回的结构化字段""必须原文复述的信息"，**不断言自然语言的措辞与句式**
- 提问按"最小必然触发"构造：凡能用摘要、常识或上一轮结果答出的问法，都验证不到目标行为；需要多步协作时，提问必须只有读了原文 / 拿到工具结果才能答出
- 断言失败先分清"被测行为不符预期"与"断言写死了一种合理实现"——后者改断言与提问，不改被测代码

## 六、交付物验证（打包产物）

端到端实测跑的是源码运行态；"拿到就能用 / 零配置可运行"这类交付声明只有对**打包产物**实测才算验证：

- **干净环境启动**：只把产物放进空目录，不给本机配置与依赖，按交付文档交给使用者的命令启动，核对启动日志、预置数据与关键功能——本机配置被悄悄打进产物、产物实际不可独立运行，只有这一步能暴露
- **产物内容抽查**：`.gitignore` 只保证文件不入库，不约束打包行为——构建会把源目录下全部文件收进产物，被 ignore 的本机配置、密钥、测试数据照样进包。列出产物内文件清单逐项核对：应随包分发的在、不应分发的（本地配置 / 密钥 / 运行数据）不在
- **陈旧残留核对**：构建不带 clean 时产物目录只增不删，历史构建的旧资源会混进本次产物——核对产物内无上一轮的陈旧文件后再交付

## 七、收尾检查

- **残留检查**：旧接口名、旧术语、被替换的方法名/配置 key——代码与文档都要 grep
- **临时测试配置**：为测试临时改小的阈值/开关/分片大小是否已恢复（提交前必查）
- **测试数据**：实测产生的业务数据（上传的记录、新增的单据）提醒用户清理
- **未提交内容**：按用户要求保留在工作区的文件（前端、临时文件）在汇报中列明

## 八、汇报模板

```markdown
## 验证结果
<链路逐环节状态，引用关键响应/日志原文>

## 发现的问题（如有）
现象：... / 证据：... / 根因：...

## 修复内容
<文件 + 改动>

## 下一步
<需要用户执行的操作：部署前端/后端、确认后继续等>
```
