# 动手前的可行性核证

需求常依赖"看不见"的东西：三方组件的能力、配置项的生效方式、外部服务的协议行为、上下游的接口契约。这些**不能凭假设**——先核证再写代码，否则方案会在实测阶段成批返工。

核证结论写进方案，格式：

| 待确认点 | 核证方法 | 结论 | 对方案的影响 |
| --- | --- | --- | --- |
| <能力/配置/契约> | <怎么查的> | <实际是什么> | <方案怎么调整> |

## 一、三方组件 / 依赖库的能力（无源码时）

场景：需求要求调用某个依赖（插件、SDK、内部二方库）的能力，但源码不在当前仓库。

**先看版本**：涉及框架 / 依赖的**大版本升级**（某框架 3→4、某 JSON 库 2→3 之类）时，先核实际版本与命名——starter / artifact 名、包名、异常继承关系常随大版本改变。用 `mvn dependency:tree -Dincludes='*<关键字>*'` 确认真实版本，用 `unzip -l <jar>` / `javap` 看真实包名与类签名。按旧版本的记忆写代码，报错只会是"找不到符号"，不会提示版本差异。

按成本从低到高：

1. `unzip -l <jar>` 看结构、定位类；`javap -p <类全名>` 看方法签名，`-c` 看字节码（能确认内部实际调用链）
2. 反射探测：类名/方法名不确定时，列全部方法（`javap` 在方法位于父类/接口时常查不到，写个小程序反射 dump 方法名更可靠）
3. **看项目里的既有调用方**（最可靠）——别人怎么用、传什么参数、怎么处理返回值

要确认到：方法存在？参数与返回值形态？**行为是否与需求假设一致**？

反例（真实踩坑）：字节码显示某合并方法内部走"按上传 ID 列举分片再合并"，而当前分片是以普通对象方式分别上传、上传 ID 为空——据此判定该链路在真实服务上必失败。字节码级证据让方案直接改道，避免了先写完再实测返工。

## 二、配置项的生效方式（别猜 key）

场景：新增或修改配置项，或依赖某个开关的行为。

**坑：配置写对了 ≠ 生效**。配置 key 必须与代码里真实的绑定注解一致，猜 key 会导致"改了配置但行为没变"，且现象隐蔽（不报错，只是开关不生效）。

1. grep 项目内配置读取点（`@Value` / `@ConfigurationProperties` / `getProperty`）
2. 配置类在依赖库内时：`javap -v <类>` 提取 `RuntimeVisibleAnnotations`，看 `@Value("${...}")` 的**实际 key**（注意前缀可能与直觉不同）
3. **验证生效**：做一次最小实测反推——使目标参数参与/不参与某环节，看行为是否随之变化（例如不带某请求头发起请求仍成功，说明该头未参与签名）

反例（真实踩坑）：按直觉写的配置 key 与库内 `@Value` 的真实 key 不一致，开关保持默认值，实测表现为请求被服务端拒绝。修 key 后一次通过。

## 三、外部服务 / 协议的既定行为

场景：方案依赖外部服务的协议语义（存储、消息、缓存、开放 API）。

1. **官方规范文档**：定位到章节读原文（长文档用脚本按关键词检索页码再读该页），确认行为是协议规定还是实现细节
2. **最小复现**：用最短的请求/脚本直接打目标服务验证，而不是"按文档应该是"
3. **取材通道要有降级方案**：抓官方文档时 `web_fetch` 可能被域名安全策略拦截 → 改用本地 `curl`、抓取类 DSH 插件工具，或 `git clone` 取源仓库文档；换通道后仍要落到原文片段，不用摘要替代
4. **大文档先落盘再检索**：整页抓取可能超出回灌上限而被落盘成文件——直接在落盘文件里用 grep 工具按关键词取材，不要尝试整篇读入
5. 结论落到书面说明：把"协议为什么这样、为什么易漏"写进方案/文档，供后续维护者理解
6. **大文件下载 / 跨网络取资产：实测吞吐，别只核可达**——「能通」与「能用」是两回事，量级差会直接决定方案走向：一次取 293 MB 产物，直连返回 `206` 通、但只有 15 KB/s（下完要 5.5 小时），同一份走系统代理 593 KB/s（约 8 分钟）——只核可达就会把「方案必须自带代理 / 镜像能力」这一整块漏掉，到实测阶段成批返工。取一小段即可测出量级：`curl -sL -r 0-<字节数> -o /dev/null -w '%{size_download}B %{time_total}s' <url>`。

## 四、上下游契约（前端 / 调用方）

- 读调用方源码：传什么参数、期望什么响应结构、错误分支怎么处理、有无轮询/回调
- 契约要变更时，**调用方同步修改**；契约里的语义（字段是否必填、取值来源）以调用方实际行为为准
- 涉及跨域/签名/鉴权的链路，额外确认：请求头是否参与签名、响应头是否可读、预检是否放行

## 五、既有实现的覆盖范围（本仓库内）

场景：需求要判断**某能力对某业务是否已生效**。这是"复用优先"（第 0 候选"不做 / 复用既有"）的前提——判错的代价是把"已有但没接上"误当成"完全没有"，设计出一整套多余的组件。

**别按类名 / 包名 / 方法名推断适用范围**：类名带某业务前缀的组件，实现上可能对所有业务通用；反之亦然。判定要落到**注册与分发机制本身**：

1. **消息 / 事件**：按 topic / 事件名 grep **全部监听者**，逐个看是否有按业务类型分发或过滤的分支——"类名专属"不等于"作用域专属"；
2. **接口扩展点**：列出接口的**全部实现者与未实现者**。**default 空实现是最隐蔽的失效点**——门面照常调用、不报错、就是不生效；要逐个实现类确认是否 override，不能只确认接口"被引用了"；
3. **批处理 / 定时任务**：看 SQL 与代码里的**业务类型过滤条件**——硬编码排除（`NOT IN`、`if (类型) { return; }`）是常见形态，且常写在多处（SQL 一处 + Java 二次校验一处），改一处漏一处；
4. **取值映射**（按类型拼目标字段之类）：确认映射对**本次涉及的全部取值**成立，而不是只对参照业务成立——字符串截取 / 替换这类取巧映射，换个取值常直接失配。

**先找既有机制说明**：项目内的交接 / 对接 / 设计文档与模块 javadoc，常已写明"仅某类触发""某类未生效"，比通读代码更快；与代码冲突时以代码为准。

**缺口认定的写法**：结论落到 `file:line` 证据并写明**扫描口径**（扫了哪些监听者 / 实现者），作为待确认项交用户核对——"这个功能对某业务有没有"业务方最清楚。用户指正时先去代码核实再改结论，不盲从、也不盲拒。

反例（真实踩坑）：把监听通用 topic 的消费者按类名归为"某业务专属"，据此认定"另一业务无消费者、需新建链路"，方案里设计了新增 topic + 新增消费者 + 新增 DTO；实际该消费者本就通用，真实缺口只是"业务侧未实现接口方法"，整套新增设计作废。

## 六、边界

- 核证用**只读**手段（反编译、读源码、只读请求）；需要对环境做写操作时先获用户确认
- 三方组件的内部实现结论只用于**判断可行性**，不把内部细节写进对外文档
- 核证结论与需求假设冲突时，先向用户说明再调整方案，不自行改变需求目标
