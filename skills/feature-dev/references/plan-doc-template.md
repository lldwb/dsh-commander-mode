# 规划文档三件套（proposal / design / tasks）

出规划文档前读本文件：先按「一」判定形态（落盘三件套，还是只在对话里出方案），再照抄「三」「四」「五」的骨架。三件套是**同一份规划的三种视角**——做什么/为什么、怎么做、按什么顺序做；`tasks.md` 是实施期的唯一进度源，**完成一项立即勾选**，收尾核对无未勾选项。

## 一、何时落盘三件套、何时只在对话里出方案

| 判据 | 落盘三件套 | 只在对话里出方案 |
|------|-----------|-----------------|
| 范围 | 跨模块 / 跨前后端 / 涉及外部依赖与第三方组件，改动文件多 | 单点改动，文件少、一轮可完成 |
| 迭代 | 预期多轮迭代，中途可能中断或交接 | 一次会话内做完 |
| 决策点 | 多个关键决策点需用户确认 | 无决策点或仅一处 |
| 验收 | 需逐项核对完成度（清单式交付） | 结果自明，不必逐条核对 |
| 留痕 | 需留档供他人或后续自己复核 | 无需留痕 |

- **范围**与**迭代**两行是主判据：任一行落在左侧即落盘三件套，其余三行作为加权项。
- 折中形态：方案简单但需要留痕时，可只落 `proposal.md`；方案复杂但只需跟踪进度时，可只落 `tasks.md`（文件头写清目标与验收标准）。
- **用户指定优先**：用户明确指定文档形态 / 份数 / 路径（如"输出一份完整的方案文档"并给定文件名）时**以用户要求为准**——三件套与下面的位置约定都是**默认值**、不是硬约束；落单份文档时，内容仍须覆盖三件套的关注点（做什么 / 怎么做 / 待办与验收）。
- **单一事实来源（SSOT）**：落盘后以文档为准，不再在对话里另写一份；用户在对话里改了方案，先同步改文档再继续实施。

## 二、落盘位置

| 场景 | 位置 |
|------|------|
| 默认（需长期留存） | `<项目文档目录>/<需求名>/`，目录结构与颗粒度参照项目既有文档，随代码一并提交 |
| 仅跟踪进度（项目无文档目录） | `<项目根>/.tasks/<需求名>/`，过程产物不入库，提交时排除 |

`<需求名>` 取需求主题的短名，与分支名 / 任务名一致，便于检索。

## 三、`proposal.md`（做什么 / 为什么）

```markdown
# <需求名> · 提案

## 背景
<现状是什么形态、为什么要改：业务诉求与现状痛点，只写事实，不写方案>

## 目标
- <要达到的状态，一条一义、可验证>

## 范围
- **做**：<本次覆盖的功能点 / 接口 / 页面 / 模块>
- **不做**：<明确排除的部分 + 原因>

## 验收标准
- <什么操作 → 什么预期结果：可判定、可复现>
```

要求：目标说"达到什么状态"，验收标准说"怎么判定达到"——两者不重复；「不做」必须写，它是后续挡住范围蔓延的依据。

## 四、`design.md`（怎么做）

```markdown
# <需求名> · 设计

## 方案对比
| 方案 | 思路 | 可行性 | 代价 | 结论 |
|------|------|--------|------|------|
| A | <...> | <...> | <...> | 采用 |
| B | <...> | <...> | <...> | 不采用：<理由> |

## 选定方案
<分环节写实现思路：数据怎么流、关键处理在哪、时序如何>

## 接口与数据结构
- 对外入口：<签名 / 路由 / 入参 / 返回>
- 数据结构：<模型与字段、字段来源、取值边界>
- 契约变更：<调用方需同步修改的点>

## 影响面
<涉及文件与模块清单、上下游调用方、配置项、数据库与迁移脚本、前端契约>

## 风险与对策
| 风险 | 触发条件 | 对策 |
|------|---------|------|
| <...> | <...> | <...> |
```

要求：单一路线时保留一行并写明为什么没有备选；可行性结论要有核证证据（见 `references/feasibility-check.md`），不写"应该可行"。

## 五、`tasks.md`（按什么顺序做，逐项勾选）

```markdown
# <需求名> · 任务清单

> 完成一项**立即**改为 `- [x]`；收尾前核对无未勾选项。

## 1. <阶段：数据模型 / 服务层 / 入口层 / 前端 / 验证 / 提交>
- [ ] <动作 + 涉及文件 + 完成判据>

## 2. <下一阶段>
- [ ] <...>

## 未完成项
<收尾时填写：无法完成的项保持未勾选，写明原因与处置（转哪个技能 / 交用户决策）>
```

要求：

- 阶段顺序按实现单元（自底向上）切分；每条是一个可独立完成的动作，写清**改哪个文件、做完看到什么**。
- 一条含多个子动作时拆成多条；范围变更时**改条目**，不留过期项。
- 完成判据写"做了什么动作、看到什么结果"，不写"改完了"。
- 无法完成的项：不勾选、写明处置——**不得用删条目或提前勾选制造"全部完成"的假象**。

## 六、维护规则

1. **勾选即时**：每完成一项立即勾，不等到收尾批量补勾（补勾会掩盖中途的真实进度）。
2. **变更顺序**：需求变更先改 `proposal.md`（范围 / 验收标准）→ 再改 `design.md`（方案）→ 最后同步 `tasks.md`；三份互不矛盾。
3. **收尾核对**：`tasks.md` 无未勾选项，或有未完成项但已写明处置；`proposal.md` 的验收标准逐条对照验证证据给出结论。
4. **残留检查**：文档里的旧接口名 / 旧术语随实现同步清理，与收尾提交的残留检查同批次做。
