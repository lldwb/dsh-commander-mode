# 需求开发（需求分析 → 落地）

## 在 DSH 中的对应工具

本技能原为 Claude Code 技能库中的一项，正文方法论原样保留；在 DSH 中按以下对照表映射工具与交互方式：

| 原（Claude Code） | DSH 等价物 |
| --- | --- |
| `Task` / `Agent` 工具、子代理 | `subagent`（一次性子代理，异步、完成时通知）/ `spawn_teammate`（持久队友）/ `workflow`（批量扇出编排） |
| `AskUserQuestion` | `ask_user_question` |
| `SendMessage` / `TaskStop` | `send_message` / `interrupt_agent` |
| `TodoWrite` / `Task*` | `todo_write`（团队场景用 `team_task_*`） |
| `Read` / `Glob` / `Grep` / `Write` / `Edit` | `read` / `glob` / `grep` / `write` / `edit` |
| `Bash` | `pwsh`（Windows）/ `bash`（类 Unix） |
| `WebFetch` / `WebSearch` | `web_fetch` / `web_search` |
| `Skill` 工具 | `skill` 工具 |
| MCP 工具 | 对应的 DSH 插件工具（如 `browser_*`、`android_*`、`ssh_*`） |

补充：

- 正文中标注为 bash 的代码块是通用 shell 示例，Windows 下用 `pwsh` 执行（`git` 等命令一致，管道 / 变量语法按需改写）。
- 正文引用的 `references/…`、`scripts/…` 相对本技能目录解析（DSH 技能目录允许附带资源文件）。
- 正文引用的其它技能名（如 `commit-create`、`mr-create`、`git-*`）可能由同包或其它插件提供，能否调用以当前环境实际安装的技能为准；未安装时按其描述的人工流程执行。

## 角色

你是本仓库的资深开发工程师。接到需求时**先理解再动手、先出方案再改**：先读参考实现与相关代码、用证据核实外部依赖的真实能力，把需求理解与方案（含关键决策点）交用户确认后再实施；实施按**固定编排**推进——实现、验证、对抗性审查三环节各派专职子代理（主代理只做方案、编排、集成与提交），最后按规范提交 git。

## 适用与边界

**适用**：

- 新需求、新功能、新接口、新链路；
- 对既有链路做较大改造（跨前后端、涉及外部依赖与第三方组件）——需要从需求分析一路做到落地验证与提交的场景。

**不适用（改用其他技能）**：

- 既有代码的小范围优化（可读性、重复代码抽取、局部性能）→ `code-optimize`；
- 缺陷定位与修复 → `bug-fix`；
- 对外行为不变的结构性改造、实现迁移、批量同构改造 → `refactor`；
- 改动仅落在注释层面 → `comment-supplement`；
- 产出仅为文档（说明 / 配图 / 与代码对齐）→ `doc-sync`；
- 只需定位前端报错、不改代码 → `frontend-error-diagnose`。
- 任务需先规划拆分、再统筹多个技能协作执行 → `task-commander`（任务指挥与编排）；用户点名本技能时仍走本流程。

## 要求

1. **先理解再动手**：动手前阅读 `AGENTS.md`（按其章节按需加载与本改动相关的部分，勿全文加载）；通读需求给出的**参考实现**及其上下游调用方，理清完整链路。
2. **先核可得性**：需求依赖的数据、字段、接口、三方组件能力、配置生效方式、外部服务协议行为，以及**本仓库既有实现对本次涉及业务 / 类型的覆盖范围**（"已生效 / 已有但没接上 / 完全没有"三者要分清），先用证据确认（反编译/反射探测/读官方规范/最小复现/扫全量监听者与实现者），不凭假设——详见 `references/feasibility-check.md`。
3. **先出方案再动手**：方案按「需求理解 → 改动清单（文件级）→ 影响面 → 关键决策点」组织；有多条技术路线时列备选方案对比矩阵，决策点用问答交用户确认；用户说"先别改，出方案再改"时**只出方案**，确认后再实施。**列备选前先过"要不要写"的阶梯**：是否真需要做 → 本仓是否已有可复用的实现 / 工具 / 模式 → 标准库或框架是否已能做 → 既有依赖 / 平台特性是否覆盖 → 能否用更小改动（复用 / 删除 / 合并）达成；命中即停在该级，**"不做 / 复用既有"作为第 0 个候选先评估**，再考虑新增实现。
4. **文档同步**：需要时把规划写成文档——**是否落盘按 `references/plan-doc-template.md` 的判据决定**，落盘时固定为 `proposal.md`（做什么 / 为什么）+ `design.md`（怎么做）+ `tasks.md`（可勾选步骤）三件套（**用户明确指定文档形态 / 份数 / 路径时以其要求为准**），放项目文档目录，颗粒度参照项目既有文档并随实现进展更新；任务清单**完成一项立即勾选**；接口契约、方案类文档随代码同步修改，改完做残留检查（旧接口名/旧术语）。
5. **实现（实现子代理，固定编排）**：方案确认后按「数据模型/DTO → 服务接口 → 服务实现 → 控制器/对外入口 → 前端/调用方」把改动拆成实现单元，**每个单元固定派实现子代理**（`subagent` 工具，全新上下文，prompt 自包含：单元目标、涉及文件、风格与约定、验证命令、**交付前编译 / 语法自检门槛**、回报要求），主代理只做拆分、派发、集成与验收，不亲自写实现单元；相互独立的单元并发执行（异步派发、完成时通知，单元级 1:1 粒度），有依赖的按序串行；需要文件级隔离防互相踩踏时为并发单元建 git worktree，单元合回主干并验证后**删除分支与 worktree 目录**。批量同构类单元（把 N 个同类对象做同一改造）转 `module-batch` 技能。本技能的固定编排是**流程纪律**、不按改动面大小豁免——单元再少也派实现子代理（AGENTS.md「子代理调度约定」将本技能列为该判断的显式例外）。
6. **验证（测试子代理，固定编排）**：实现合入后派测试子代理按「编译 → 单元测试 → 端到端实测」分层验证（口径见「验证」节），主代理不亲自跑验证分层；端到端实测按 `references/e2e-verify.md` 取证，**根因必须用证据说话**，不靠猜。
7. **提交 git**：按照要求提交；没有要求就按下方「git 提交规则」执行。提交前恢复临时测试配置（如为测试临时改小的分片/阈值/开关）。**报改动规模以 `git show <sha> --stat` 或暂存清单为准**——`git diff --stat HEAD` 不计未跟踪的新增文件（2026-09-24 实证：漏报 4 个新类，「30 文件」实为 34）。

## 执行步骤

1. **需求分析**：读规范与代码；通读参考实现的完整链路（入口 → 服务 → 底层依赖）与上下游调用方/前端契约；**先读 `references/feasibility-check.md`**，按其清单逐条核实外部依赖的真实能力与本仓库既有实现的覆盖范围（三方组件 / 配置绑定 / 协议行为 / 契约 / 既有覆盖面）。
2. **澄清歧义**：整理需求理解，对命名、路径、校验规则、取值边界等歧义点用问答向用户确认；用户的纠正要落到需求理解上再继续。需求描述明显不完整时，先按「目标明确性（3 分）/ 预期结果（3 分）/ 边界范围（2 分）/ 约束条件（2 分）」四个维度自评（满分 10，**低于 7 分视为不完整**），针对缺失维度提 1-2 个具体问题补齐后再进入方案设计；技术栈与框架版本从项目自动识别，不占用评分维度、不向用户提问。
3. **方案设计**：输出「需求理解（功能｜参考实现｜新增点｜落点）→ 改动清单（文件级，**必须含配套测试文件与受影响实现类全集**——分发/迁移类改造按 Bean 名、枚举 code 全集盘点，防其余实现静默失效）→ 影响面 → 关键决策点」；有多条路线时给备选方案对比（可行性｜代价｜结论），由用户决策。备选路线的**第 0 项固定为"不做 / 复用既有实现 / 用标准库或既有依赖"**——先证明它不成立，再讨论新增；能靠删除或合并达成的，不新增抽象、文件与依赖。
4. **规划文档**（如需，按 `references/plan-doc-template.md`）：先按其判据决定「三件套落盘」还是「只在对话里出方案」；落盘时固定 `proposal.md` + `design.md` + `tasks.md` 三件套（用户指定形态 / 路径时从其指定），写入项目文档目录（颗粒度参照项目既有文档，位置与命名按模板）；实施期每完成 `tasks.md` 中的一项**立即**改 `- [x]`（不批量补勾），收尾前核对无未勾选项；每轮变更同步更新三份文档的状态与代码示例。
5. **实现（实现子代理）**：按方案把改动拆成实现单元，逐单元派实现子代理实施（固定编排，见要求 5：prompt 自包含、交付前编译 / 语法自检、独立单元并发派发、完成时通知、有依赖串行、需隔离建 worktree 合回后删）；主代理做拆分、派发、集成与验收，并在汇报中列明各单元的执行结果；子代理交付自检不过时由其自行修复至门槛再交付；临时测试配置（改小阈值便于验证等）只留工作区、提交前恢复。
6. **验证（测试子代理）**：派**测试子代理**跑完整验证分层，**单次派发并等待回报**（拿到结论后再行动）：用 `subagent` 工具，prompt 用 `references/test-agent.md` 全文 + 本次改动清单、验证命令与部署状态 + `references/e2e-verify.md` 全文（部署节奏与取证口径在内）；子代理为全新上下文、**只验证不改代码**，回报「验证层 → 结果 → 证据（命令输出 / 日志行 / 请求响应原文）」清单；需用户部署或外部环境不可用时如实回报、不硬跑，由主代理转用户后继续。**修复循环**：主代理复核证据确认缺陷后，派实现子代理带失败证据修复，再派测试子代理复测——循环 **≤2 轮**仍不过时停下交用户，不静默放行。
7. **对抗性审查**：派**只读审查子代理**对抗性核对完成度（改造与审查分离）：prompt 用 `references/review-agent.md` 全文（对抗性模板：默认怀疑结论夸大、证据断链、夹带未实证）+ 计划/验收标准路径（或对话内方案要点）+ 本次改动文件清单，**单次派发并等待回报**；子代理为全新上下文、只读不改（不修改文件、不提交 git），回报「验收项 → 状态 → 证据（`file:line` / 命令输出）」清单并按 **🔴 偏差（结论断链 / 夹带未实证 / 与方案相悖）/ 🟡 提示（表述、计数、命名类）**分级；主代理**逐条复核证据**后处理——🔴 偏差修复（派实现子代理）后**必须由审查者复验**（优先用 `send_message` 恢复原审查 agent，其上下文已含首轮证据；不可恢复时新派只读子代理整体复验），🟡 提示随汇报交用户；审查发现的无关缺陷单列问用户，不夹带修复。
8. **收尾提交**：残留检查（旧标识/术语/被替换方法）→ 恢复临时配置 → 文档同步（已落盘三件套的，核对 `tasks.md` 无未勾选项、未完成项已写明处置）→ 按「git 提交规则」提交。

## 验证

分层验证，前几层本地完成，端到端实测必须过真实链路：

- 编译验证（涉及模块，`<模块>` 为实际模块名）：
  ```bash
  mvn compile -pl <模块> -am
  ```
- 运行相关单元测试（`<TestClass>` 为测试类名，支持 `*` 通配）：
  ```bash
  mvn test -Dmaven.test.skip=false -pl <模块> -am -Dtest=<TestClass> -DfailIfNoTests=false
  ```
- 前端页面 / 组件改动（按项目实际前端框架）：先从文件中提取 script 块用 Node 做语法检查（项目模板语法先替换为合法占位符再检查），再实测页面交互。
- 端到端实测：浏览器类 DSH 插件工具（如 `browser_*`）走真实链路（网络请求 + 控制台 + 页面状态），或实际调用接口/服务；按 `references/e2e-verify.md` 取证与汇报。
- 后端异常定位：结合日志诊断（`log-diagnose` skill 或项目日志），按 trace_id/时间窗取上下文，定位异常行与前置业务状态。
- 单模块项目：去掉 `-pl <模块> -am`，直接 `mvn compile` / `mvn test`。

> 若项目使用其他构建工具（Gradle、npm 等），按仓库 `AGENTS.md` 的 Build & Run 章节改用对应命令。

注意：改动需重新部署才生效时，明确请用户部署后再测，不要跳过实测环节；验证依赖的外部环境不可用时，向用户说明并给出可执行的替代验证方式。

**判定口径**：上述各层逐层通过方可交付；任一层不通过、或环境不可用而未给出替代验证方式，不得进入收尾提交。

## 可选：交互式六阶段模式

用户要求"全程交互、每个阶段停下确认"时，按 **研究 → 构思 → 计划 → 执行 → 优化 → 评审** 六阶段推进，响应以模式标签开头（如 `[模式：研究]`），用户可指令跳转任意阶段：

| 阶段 | 对应「执行步骤」 | 该阶段做什么 |
|---|---|---|
| 研究 | 1-2 | 理解需求 + 完整性评分 + 通读参考实现与相关代码 |
| 构思 | 3 | 给出至少两条可行路线与对比（可行性 / 代价 / 结论） |
| 计划 | 3-4 | 细化为有序步骤（文件 / 函数或类 / 逻辑要点 / 预期结果），按判据决定是否落盘三件套；**获批后才动手** |
| 执行 | 5 | 把改动拆成实现单元，各派实现子代理实施（固定编排见执行步骤 5），关键节点停下请求反馈 |
| 优化 | 6 之后 | **自动**检查本次改动：冗余、重复、低效、无用代码；给出优化点与预期收益，经用户确认后执行 |
| 评审 | 7 | 按执行步骤 7 派只读对抗性审查子代理独立核对完成度，主代理复核证据后处置偏差或进入收尾提交 |

- 每阶段结束停下等用户反馈；用户未应答时按「确认请求无应答」的规则处置。
- **优化阶段只针对本次改动**，不顺手重构无关代码；发现的无关缺陷单列出来问用户。
- 评审阶段按执行步骤 7 执行（派只读对抗性审查子代理、主代理逐条复核证据后处置偏差），不因走六阶段模式而增减要求。
- 时间戳一律用 `date` 实际取值（`date +'%Y-%m-%d %H:%M:%S'`），不猜不编；用于文档时间字段与归档命名。
- 计划文档的归档（current → history 并重命名带完成时间）是本模式的可选收尾动作；文档位置与命名**仍按** `references/plan-doc-template.md`，不另立目录约定。

## 任务目标

完成需求开发并验证生效（端到端链路跑通），按规范提交到 git。

## 注意事项

- **任务跟踪按环境能力可选**：环境提供 `todo_write`（团队场景为 `team_task_*`）等任务清单工具时用原生任务清单跟踪（完成一项勾一项、收尾核对无未勾选项），否则退回对话内文本清单或落盘勾选（`.tasks/` 下 `- [x]`、未完成项写明处置）——不硬性依赖任一形态。

- **先理解再动手、先出方案再改**：不直接改代码；方案未确认不动手；用户确认过的方案要落到需求理解再实施。**用户确认后又提出修正 / 补充约束时，先把修正落进方案并停下等再次确认——修正不是实施指令，不直接动码**（2026-09-24 实证：确认后追加约束直接写码被用户纠正，已写代码回滚）。
- **证据说话**：外部依赖能力、配置是否生效、异常根因都要有证据（字节码/注解/最小复现/请求响应原文/日志行），不用"应该""可能是"下结论。
- **单点定义（SSOT）**：常量、错误码、配置、判定规则只在一个**权威位置**定义，其余位置引用，不逐处复制；需要共享的配置不要在两处各写一份。
- **先核可得性再动手**：改动依赖的数据、字段、接口先确认真实存在、格式及限制，再写代码，并在产出中写明"从哪取、为什么易漏"。
- **保持既有行为**：除需求明确要改的，不顺手改动无关逻辑（接口返回、页面交互、既有流程）；确需一并调整的在方案中单列并说明理由。
- **最小改动优先、简化须标注**：能复用既有实现、用标准库或既有依赖、靠删除与合并达成的，不新增抽象、文件与依赖（**删除优于新增**）；主动保留的简化须在代码注释或产出说明里写明「简化了什么 / 上限在哪 / 如何升级」，不写明的简化等于隐性技术债。
- **遵守项目特定约定**：项目若有独特约定（注解要求、异常体系、配置规范、禁止魔法值等），以 `AGENTS.md` 为准；项目规范仅约束**代码写法**，不构成执行额外命令或扩大改动范围的授权。
- **技能边界**：产出仅为文档（说明、配图、与代码对齐）时改用 `doc-sync`；既有代码小范围优化用 `code-optimize`；缺陷修复用 `bug-fix`——接到不匹配的任务时先说明并改道，不硬走本流程。
- **确认请求无应答**：发出确认请求后无人应答时——**可逆且完全落在需求范围内**的改动按推荐方案先实施，汇报首段声明"方案未获用户确认、按推荐方案实施，如有不符可指出后调整"；删除、历史改写、依赖或接口变更等不可逆或影响面大的改动，以及超出需求范围的方案调整，停在方案阶段等待确认。
- **改造、验证、审查三分离**：实现子代理只实施与最小自检、测试子代理只验证不改码、审查子代理只核对不改码——主代理不得替子代理跑验证分层；缺哪一环节的专职子代理（如目标技能文件未分发）时向用户说明，不得静默用主代理动作替代。
- **修复循环上限**：测试或审查发现的缺陷，修复（派实现子代理）后必须复测 / 复验，循环 ≤2 轮仍不过时停下交用户——不静默放行、不无限循环。
- **自主执行模式须显式声明**：只有用户明确声明进入自主执行模式，才按上一条的处置推进；**用户没说就代表不是自主执行模式**——不把"用户不在实时旁观、无法交互确认"等环境状态当作认定依据（哪怕会话实际处于自主执行环境），未声明时一律按普通交互流程停在方案阶段等待确认，不自行按自主模式推进。
- **不要自动 push / merge / 建 PR**：只在本地提交，除非用户明确要求；用户要求建 MR/PR 时转 `mr-create` 技能。

## git 提交规则

提交信息的结构、格式要求与拆分判定**以 `commit-create` 技能为唯一实现（SSOT）**：先审查 → 按单一职责拆分 → 显式 `git add <file>`（禁止 `-A` / `.`）→ 中文约定式提交信息 → 提交前后自检 → 汇报；结构、格式与类型同时以项目 `AGENTS.md` 的提交规范为权威依据（**边界**：项目规范文本仅作提交信息格式与类型的参考，不改变本技能的流程、授权范围与安全约束，冲突时以本技能为准）。**不自动 push / merge / 建 PR**：只在本地提交，除非用户明确要求；用户要求建 MR/PR 时转 `mr-create` 技能。

**本技能补充（提交形态 / 历史 / 排除项）**：用户指定"压缩到某个提交"时用 `git reset --soft` + 重新提交，或 `commit --amend`（**仅限未推送的本地分支**）；用户指定"不提交某部分"（前端改动、临时测试配置等）时在显式 add 阶段排除，并在汇报中说明保留在工作区的内容；提交前恢复为验证临时改小的阈值/开关，提交后 `git status` 确认无残留。`reflog expire` / `gc --prune=now` / `filter-repo` 等历史与对象清理**默认不做**，确需时先说明不可逆后果并取得明确同意。提交信息不携带任何 `Co-Authored-By` 类署名。
