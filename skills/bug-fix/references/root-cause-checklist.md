# 缺陷定位与取证清单

> 供 agent 按需加载的参考件：bug-fix 技能在**问题难以复现**、**需要系统性排查调用链**、**根因疑似在本机环境而非项目代码**、**需要判断失败是否由本次改动引入**时读取本文件。
> 使用要求：每条结论都要能指回证据（命令与输出、日志片段、数据查询结果、`文件:行`），不写"可能""大概是"式判断。

## 1. 运行期复现路径

从用户给出的入口开始，逐种手段试到能稳定复现或能取证为止：

- **日志**：按 `trace_id` + 时间窗取上下文（`log-diagnose` skill 或项目日志平台），定位异常行与前置业务状态；**看第一条异常**，后续多为连锁反应。记下异常类、消息、堆栈中的业务代码行。
- **接口**：重放请求（保留原始入参），对比预期与实际响应；记录路径、入参、状态码、响应体、耗时。
- **页面**：用浏览器类 DSH 插件工具复现，采集 console 报错、失败请求与调用栈。
- **任务 / 定时器 / 消息**：确认触发时间点与当时的输入数据；对照上一次执行成功的时间点与数据差异。
- **用户提供的截图 / 录屏**：先核验现象是否仍是当前状态（截图可能过期；程序可能仍跑着旧代码、改了源不等于现象已消失）——把"图上的事实"与"当前产物 / 代码的事实"分开记，两者不一致时以当前状态为准并在说明里写明。报告文字描述的是**结果**，截图常暴露报告没覆盖的**实际操作形态**——图里用户的真实操作路径（选了什么、点了哪一步）可能正是第二处根因所在，逐张核对操作细节再下结论。
- **抽样证据（几张截图、几个 case）**：不要逐个追着修——先在产物 / 数据侧枚举同一形态的**全部**出现位置与实例，归类后一次性处置。

复现结论用下面的结构写进定位说明，便于用户核对：

```
现象：<可观测到的错误表现>
入口：<接口 / 页面 / 任务>
复现步骤：1. ... 2. ...
证据：<日志行 / 请求响应 / 输出文件路径>
```

**复现不了不是跳过**：换手段（缩小输入范围、构造最小用例、直接调用下层方法）或转第 4 节的现状取证。

## 2. 数据状态核对

涉及业务数据状态（单据状态、逻辑删除标记、审批流节点、关联表一致性）时，先核数据再下结论：

- **手段**：`db-query` skill（生产只读）；项目未安装则用项目自身的数据库查询能力 / 脚本。
- **安全（不可放宽）**：生产环境只读、只查不改；测试环境写操作须先获用户确认。
- **核对顺序**：目标记录是否存在 → 关键字段值是否符合预期 → 关联记录是否齐全 → 状态与时间线是否自洽。
- **写入结论**：SQL 与查询输出文件路径一并引用，供复核。

## 3. 调用链与依赖排查

- **沿调用链逐层确认**：入口 → 业务层 → 数据层，每层回答两个问题："参数是否如预期传入""返回值是否被正确处理"。
- **全仓检索引用**：`grep -rn "<符号名>" <项目根>`，确认调用方数量与各自假设（改一处会影响谁）。
- **边界排查**：空值 / 极值 / 超长 / 特殊字符 / 时区与精度；异常分支与失败返回值是否被处理。
- **依赖排查**：依赖的**实际版本**与文档/记忆是否一致；不同环境配置项是否有差异；初始化顺序与并发时序。
- **对接外部产物 / 上游系统时，行为假设延伸到上游取证**：工具对上游产物的结构、协议形态、打包配置都有假设（如"安装目录下应有某文件"），疑点落在"是上游产物不符合假设、还是工具假设错了"时，去**上游仓库 / 官方文档拿裁决性证据**（上游的构建脚本、打包配置、协议文档），不凭猜测放宽或收紧校验——实测：报障表面像"校验误拦用户"，查官方仓库打包配置确认上游产物确为裸目录结构（`asar: false`），校验没错、根因转向引导文案与选择下探。
- **改动前先建基线**：修复前跑一次现有验证命令并记下失败集合（见第 5 节），否则无法区分新旧失败。

## 4. 静态缺陷的现状取证（无法运行期复现时）

适用：死代码、注释与实现漂移、规范偏差、配置与代码不一致。

- **全仓引用计数**：`grep -rn "<符号名>" <项目根>`，区分定义处与引用处，确认是否真无调用者。
- **定义处与调用处对照**：逐处确认实际行为与假设是否一致（含注释所声明的行为）。
- **规范对照**：把权威规范的原句与现状代码并列，指出偏差点。
- **必须写明**："**无运行期现象**"，并给出取证命令与输出——避免让用户误以为做过运行期验证。

## 5. 失败分类（本次引入 vs 既有无关）

改动前后用同一验证命令、同一范围跑，对比失败集合：

- 失败集合**只缩小或不变** → 本次改动未引入新失败。
- 出现**新失败项** → 属本次引入，必须修掉，或说明为何与本次改动无关（附证据）。
- **既有失败**（与本次改动无关）单独列出，不混入本次修复结论，也不借机扩大改动范围。

```
验证命令：<命令>
改动前失败集合：<用例 1、用例 2>
改动后失败集合：<用例 1>
新增失败：<无 / 列表>
归类依据：<证据：输出文件 / 日志行 / 代码位置>
```

## 6. 环境 / 工具链故障取证（根因不在项目代码时）

现象多为"命令无法运行 / 服务起不来 / 安装或构建失败"。此类根因常在本机环境而非项目代码，取证顺序如下：

- **隔离复现优先于溯源**：在临时目录用最小输入重跑失败命令（如 `npm install <包>`），先拿到稳定复现再谈调用方。找"谁触发的"往往耗时且非必需——根因常在包与外部依赖层。
- **复合报错拆到最内层**：外层文案常是包装（形如 `<工具> install failed with exit code <N>: <原始输出>`），真实错误在原始输出内；逐层展开嵌套输出，锁定第一条真实失败。
- **退出码语义**：`127` = 命令或文件找不到（npm 生命周期脚本中最常见）。先分清是"命令不在 PATH"还是"脚本文件根本不存在"，两者修法完全不同。
- **上游包缺陷的判定**：以**实际 tarball 内容**为准，不凭 `package.json` 里的脚本声明推断——用 `--ignore-scripts` 装一份即可查看包内实际文件，对照 `files` 白名单 / `.npmignore`，确认被调用的脚本是否真的随包发布。
- **受限网络下取依赖**：逐个探可达性（`curl -sS -o /dev/null -w "%{http_code}" <url>`），走可达的那条路取二进制（如 `api.github.com` 资产端点 + `Accept: application/octet-stream` 下 release 包）；优先**预热工具自身的缓存**绕过下载（如 prebuild-install 的 `_prebuilds/`，缓存键为 `sha512(下载 URL)[:6]-<文件名>`），而不是改全局配置或安装重型工具链。
- **验证口径**：以"命令可运行 + 关键运行时依赖可加载 + 服务状态命令正常"为准，不用编译 / 单测口径。

## 7. 证据产出与上下文节制

诊断脚本、批量比对、全量扫描的输出往往远大于能进上下文的分量，按下面口径处理：

- **落盘**：完整结果写进过程产物目录（项目过程产物目录 / `tmp/`），会话里只读回**摘要结论 + 文件路径**；结论引用文件路径便于复核。
- **截断**：单次读回超过约 200 行就先截断或分组读；脚本打印时只输出命中条数与前 N 条，其余略（"输出太多"本身就会让后续取证走样）。
- **口径写进摘要**：同一批证据若在两种基准上取数（如"改动前 vs 改动后""原件 vs 产物"），摘要里必须写明每个数字各自取自哪份基准——基准写反会让整条结论反过来。

## 8. 结论自检

提交定位说明前逐条自检：

- 能一句话说明"什么输入/状态触发了哪段代码的什么行为"？不能则是取证不足，回到第 1~4 节补。
- 每条判断是否都指回了具体证据（`文件:行` / 命令输出 / 查询结果）？
- 改动是否只覆盖了根因，没有顺手改无关代码？
- 失败分类是否明确（本次引入 / 既有无关）？
