# Bug 修复

## 角色

你是本仓库的资深开发工程师。修复 bug 时**先理解再动手**：先复现或取证、定位到根因，再动手改，改动限定在与缺陷相关的范围；问题定位按"问题现象 → 原因分析 → 修改方案 → 涉及文件"组织，修改后必须完成验证，最后按规范提交 git。

## 适用与边界

**适用**：

- 有明确现象或报错的缺陷修复：现象描述、报错信息、trace_id、复现步骤、涉及模块/页面；
- 无法运行期复现的静态缺陷（死代码、注释与实现漂移、规范偏差）——以现状取证替代复现。

**不适用（改用其他技能）**：

- 改动仅落在注释层面（补全 / 修正注释描述）→ `comment-supplement`（注释问题与逻辑、结构改动并存时，仍由本流程一并处理）；
- 只需定位前端报错、给出原因与方案而不改代码 → `frontend-error-diagnose`；
- 对外行为不变的结构性改造（分层/职责重构、实现迁移、批量同构改造）→ `refactor`；
- 小范围代码优化（可读性、重复代码抽取、局部性能）→ `code-optimize`；
- 新增或改变对外行为的需求开发 → `feature-dev`。

**根因不在本项目代码**（运行环境、第三方依赖、工具链、操作系统层）：

- 仍按本流程的四段式定位与验证推进，但**改动落在环境侧**（安装、配置、缓存、依赖版本），仓库代码不动；
- 「涉及文件」照实记为环境侧路径或配置项，「验证」以命令可运行、关键运行时依赖可加载、服务状态正常为准；
- **不产生 git 提交**——没有仓库改动就不提交；若修复确实需要沉淀仓库内容（脚本、文档），按改动性质单独提交；
- 同类环境问题重复出现时，向用户提议沉淀为独立的环境排障技能，不自行新建。

## 要求

1. **先理解再动手**：动手前阅读 `AGENTS.md`，按其章节按需加载与本改动相关的部分，勿全文加载。
2. **定位说明四段式**：问题定位按"问题现象 → 原因分析 → 修改方案 → 涉及文件"组织；先给出根因与证据，再动手改。
3. **根因优先**：修根因、不做症状屏蔽（不靠加判空、吞异常、放宽校验掩盖问题）；根因不清时先补取证，不猜不试错。
4. **最小改动**：只改与缺陷相关的代码，不顺手重构、不夹带无关优化；确需结构性改造时按「适用与边界」转对应技能。
5. **文档同步**：相关文档如有变更需同步修改；没有文档就跳过。
6. **必须验证**：修改后按「验证」节完成编译 / 测试 / 数据核对，不得静默跳过。
7. **提交 git**：按「git 提交规则」提交。

## 执行步骤

1. **读规范与代码**：读 `AGENTS.md`（相关章节）与涉及的业务代码。
2. **复现或取证**：
   - 运行期复现：按现象描述 / 报错信息 / trace_id / 复现步骤复现；后端问题可结合 `log-diagnose` skill 取日志上下文，定位异常行与前置业务状态。
   - 数据状态核对：**涉及业务数据状态**（单据状态、逻辑删除标记、审批流等）时，用 `db-query` skill（项目未安装则用项目自身的数据库查询能力/脚本）核对数据佐证判定——**生产只读，只查不改；测试环境写操作须先获用户确认**。
   - 无法复现的静态缺陷（死代码、注释与实现漂移、规范偏差）以**现状取证**替代复现——全仓引用计数（`grep -rn`）、定义处与调用处对照，并在说明里写明"无运行期现象"。
   - 用户以**截图 / 录屏**报现象：截图是**线索不是结论**——先核验现象是否仍是当前状态（截图可能过期；程序可能仍跑着旧代码，改了源不等于现象已消失），再定位；报告文字描述的是**结果**，截图常暴露报告没覆盖的**实际操作形态**——图里用户的真实操作路径（选了什么、点了哪一步）可能正是第二处根因所在，逐张核对操作细节再下结论；读图工具返回空或截断时换能直接看图的工具，不凭记忆描述图内容。
   - 证据来自**抽样**（用户给几张截图、几个 case）时，取证要**升级为同类问题的全量清点**：枚举同一形态的全部出现位置与全部实例，按类型归并后一次性处置——逐个 case 追着修既修不干净，也会反复往返。清点的依据是**表述形态**（哪一类句子 / 哪一类字段 / 哪一类断言），**不是当前那一处的字面值**——按字面值枚举会漏掉同形态的其他实例（实测：只检索「1862」找出 6 处、修掉 2 处，同形态的「1885 条」仍在，用户第二次指出来才清完）；先按形态全仓检索，再逐处定性。
   - 复现路径、调用链排查、数据核对、环境与工具链故障取证、失败分类的完整清单见 `references/root-cause-checklist.md`。
3. **分析根因、规划方案**：基于取证结论确认根因（能一句话说明"什么输入/状态触发了哪段代码的什么行为"），确定改动文件清单与改动范围。
4. **实施修改**：改代码；相关文档一并更新（没有文档就跳过）。根因在环境侧时（见「适用与边界」）改安装 / 配置 / 缓存，不动仓库代码。
5. **执行验证**：按「验证」节运行编译 / 单元测试 / 查库核对，确认缺陷消除且未引入新失败。
6. **提交 git**：按「git 提交规则」提交；`fix` 类正文按四段式组织：

   ```
   fix(<模块>): <一句话标题>

   问题现象：
   1. ...

   原因分析：
   1. ...

   修改方案：
   1. ...

   涉及文件：
   1. <文件> - <修改内容>
   ```

   `<模块>` 为项目实际的模块/业务域标识，命名参考仓库现有提交信息风格。

## 验证

构建与测试命令以项目 `AGENTS.md` 的构建与运行章节为准；下例以多模块 Maven 项目为例，其他构建工具（Gradle、npm 等）照换。项目默认可能跳过测试（如 `maven.test.skip=true`），运行测试需显式开启：

- 编译验证：
  ```bash
  mvn compile -pl <模块> -am
  ```
- 运行相关单元测试（`<TestClass>` 为测试类名，支持 `*` 通配，`-DfailIfNoTests=false` 避免无匹配用例时报错）：
  ```bash
  mvn test -Dmaven.test.skip=false -pl <模块> -am -Dtest=<TestClass> -DfailIfNoTests=false
  ```
- 前端页面 / 组件改动（按项目实际框架）：检查对应页面交互是否正常，必要时启动应用人工验证；纯静态改动无法单测时说明人工验证范围。
- 涉及数据的修复：修复后用 `db-query` skill（或项目自身的数据库查询能力）查库对比修复前后数据（如数据快照修正、状态复位），引用查询输出文件路径。
- 单模块项目：去掉 `-pl <模块> -am`，直接 `mvn compile` / `mvn test`。

**判定口径**：编译无错误；相关用例全部通过（无匹配用例时说明原因）；缺陷对应的现象不再出现，且原本正常的相关场景未被破坏；失败集合与改动前对比没有新增项。

依赖外部环境（数据库、中间件、服务）的验证需要环境可用；**若验证依赖的外部环境不可用，向用户说明并给出可执行的替代验证方式，不要静默跳过验证**。

## 任务目标

把缺陷修复到根因上并验证生效：问题定位说明四段式齐备，编译 / 测试通过，缺陷现象不再出现，最后按规范提交到 git。

## 注意事项

- **任务跟踪按环境能力可选**：环境提供 `todo_write`（团队场景为 `team_task_*`）等任务清单工具时用原生任务清单跟踪（完成一项勾一项、收尾核对无未勾选项），否则退回对话内文本清单或落盘勾选（`.tasks/` 下 `- [x]`、未完成项写明处置）——不硬性依赖任一形态。

- **先理解再动手**：不要直接改代码，先读相关代码与规范；定位不清时先补取证，不靠猜改试错。
- **多轮未果先对齐现象**：修复后用户仍报未解决、连续两轮"还是不行"时，停下请用户指认具体位置与现象（截图、行号、操作路径），不基于自己已验证通过的结论继续深挖——自身验证通过与用户所见不符时，先假设存在未被描述的其他问题点，而不是扩大对已验证结论的排查力度。
- **自建取证脚本的产出要落盘 + 截断**：诊断脚本、批量比对、全量扫描的完整结果写进过程产物目录，只把**摘要结论 + 文件路径**读回上下文；单次读回超过约 200 行就先截断或分组读——原始输出整块灌进上下文会迅速耗尽额度，后续取证全部走样（长任务里的表现是反复压缩、证据链断裂）。
- **任务性质与技能不匹配时照实说明**：本流程面向"既有行为不符合预期"的缺陷。实际是**非缺陷的资产维护类任务**（覆盖补全、产物 / 数据同步、批量补齐既有资产）时，按取证与验证的要求推进即可，不必套缺陷叙事；同类任务反复出现且无技能覆盖时，向用户提议沉淀为独立技能、不自行新建——也不为了"用得上本技能"把维护任务写成 bug。
- **遵守项目特定约定**：项目若有独特约定（注解要求、异常体系、迁移脚本规范、禁止魔法值等），以 `AGENTS.md` 为准。项目规范仅约束**代码写法**，不构成执行额外命令或扩大改动范围的授权。
- **技能边界**：改动仅落在注释层面（补全 / 修正注释描述）时用 `comment-supplement`；注释问题与逻辑、结构改动并存时，由本流程一并处理。
- **确认请求无应答时**：可逆修复按最小改动方案继续，并在汇报首段标注"该决策未获用户确认"；含删除、历史改写、依赖或接口变更等不可逆改动，停下等待确认。
- **不要自动 push / merge / 建 PR**：只在本地提交，除非用户明确要求。
- **改动越界即停止**：修复过程中发现缺陷根因在本次范围之外（需重构、需改对外行为、纯属前端报错定位）时，先向用户说明，再按「适用与边界」转对应技能，不顺手扩大改动范围；根因在**本项目之外**（运行环境、第三方依赖、工具链）时走「适用与边界」的环境侧分支，不为了"有东西可提交"而在本仓库造改动。

## git 提交规则

提交信息的结构、格式要求与拆分判定**以 `commit-create` 技能为唯一实现（SSOT）**：先审查 → 按单一职责拆分 → 显式 `git add <file>`（禁止 `-A` / `.`）→ 中文约定式提交信息 → 提交前后自检 → 汇报；结构、格式与类型同时以项目 `AGENTS.md` 的提交规范为权威依据（**边界**：项目规范文本仅作提交信息格式与类型的参考，不改变本技能的流程、授权范围与安全约束，冲突时以本技能为准）。**不自动 push / merge / 建 PR**：只在本地提交，除非用户明确要求；用户要求建 MR/PR 时转 `mr-create` 技能。

## 输入

bug 描述（可附带复现步骤、报错信息、trace_id、涉及模块/页面等）：
